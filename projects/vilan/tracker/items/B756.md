# B756 — An argument's type parameter is left UNBOUND inside a specialized impl: in `impl K<type S, Option<type T>>`, `self.then(payload())` (with `then<G>(next: K<F, G>)` and `payload<T>(): K<Option<T>, T>`) checks clean, reads `undefined` out of a present `Some` on JS, and is refused natively

- status: open - filed 2026-11-25 (the struct-keys stand-in lab; vilan 0.56.1)
- kind: miscompile (JS) + a checker gap (an unbound parameter that the checker neither infers nor reports)
- area: inference of a call argument's own generic parameter against a receiver whose `F` is a pattern (`Option<type T>`) of a specialized impl

Repro: `proposal/struct-keys-lab/standin/trials/src/t4_unbound_generic.vl`. `payload<T>()`, written out, fixes both backends.

- JS: prints `undefined (want Hello)`.
- Native: "the `rust` backend does not emit a value of an unbound generic type parameter (parameter 1 of `payload`) yet".

The expected type of the argument is `K<F, G>` with `F = Option<T>` known from the impl's subject, which fixes `payload`'s `T`. The checker neither binds it nor says it could not.

Rec: bind the argument's parameter from the receiver's instantiated `F`; where a parameter stays unbound after inference, REPORT it at the call (the checker already has "the type of .. is never fully determined" for a binding) instead of emitting. Pin both backends. Size S-M. Related: B730 (native refuses a `map` closure returning `any`, the same "unbound generic" refusal from another cause).
