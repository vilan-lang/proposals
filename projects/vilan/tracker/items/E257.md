# E257 — DEBUGGING vilan programs: a `dbg(..)` that takes any number of values and prints them well, a `dbg_stack()` that prints every binding in scope at that point (a stack snapshot), and a breakpoint debugger

- status: OPEN — filed 2026-10-03 (the owner: 'I want to have a talk about debugging programs. `print` is not great at the moment'); paper in papers-b-46
- kind: design discussion (paper) — the owner's
- area: LSP & tooling

The owner's three asks. (1) `dbg(a, b, ..)`: variadic, prints each value with its EXPRESSION TEXT and file:line, structured (struct names, enum variants, nested layout) rather than node's `util.inspect` of the JS representation; returns its argument(s) so it can wrap an expression; same output on both backends; stderr; stripped or refused in release builds? (2) `dbg_stack()`: every binding in scope at the call (name, type, value), which the compiler can expand statically since it knows the scope - a macro-like form; captures and views shown as such; reactive cells shown by current value without tracking. (3) A breakpoint debugger: source maps for the JS backend (does the emitter produce them?), a DAP adapter for VS Code (node inspector for JS, lldb/gdb with a pretty-printer for native), how monomorphized and generated code maps back, stepping through reactive turns. Also in scope: what `print` should be once `dbg` exists (F68's layout question), `Debug` derive coverage, and logging reactive graphs (who woke this effect). The paper: ground truth probed on v0.43.0, doors and recs, slices.
