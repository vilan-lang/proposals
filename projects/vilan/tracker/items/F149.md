# F149 — A NULL column read through `Row::integer`/`text`/`real`/`big_integer` answers the host's `null` on JS - an `i32` that prints `null`, a `str` that prints `null` - and the coerced `0` / `""` natively (`vilan-rt-sqlite`'s `Row::number`/`text` claim to be the JS reader's coercion; the JS `__db_column` does not coerce)

- status: OPEN - filed 2026-10-26 (std-55's find, Order 55)
- kind: miscompile (backend divergence) - std::db column readers
- area: Native targets & rendering

Met writing M165's pins. `db.vl` binds the four readers to one helper (`__db_column`: `row[name]`) and lets the signature supply the type, so a NULL arrives as `null` behind an `i32`/`str` on JS; native `Row::number` maps NULL to 0 and `Row::text` to "", calling that `Number(null)`/`String(null)`'s coercion - which the JS side never applies (and `String(null)` is "null", not ""). Doors: (a) coerce on JS to the native answers (`Number(v ?? 0)`, `v ?? ""`), split into per-reader helpers as the native emitter already splits them by vilan name; (b) make the readers `Option`-returning (`integer_or_null`) - a breaking surface change. Rec: (a) now, both backends answering 0/"" (the documented contract is "guard NULLABLE columns with `is_null`"), and the `SqlValue` follow-up's row half considers (b). `miscompile`.
