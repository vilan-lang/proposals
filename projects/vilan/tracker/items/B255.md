# B255 — `bind_each`/`bind_each_by` keep the LIVE list as `row_items` (`row_items.write() = list`, and the effect's `list` is the cell's storage), so an in-place `remove`/`insert` through `SignalCell::update` shrinks it under `row_keys` and `reconcile` panics at `old_items[index]` (kolt channel.vl:54: `index out of bounds: the length is N but the index is N`); an in-place element write leaves the row silently STALE (the reconciler compares the mutated array with itself and Keeps)

- status: OPEN — the owner's kolt find (2026-09-06)
- kind: bug
- area: std: reactive & ui

Two symptoms from one alias. `bind_each` (browser/ui.vl) stores the effect's `list` into `row_items` and later hands `row_items.read()` to `reconcile` beside `row_keys.read()` (a separate list built by `next_keys.push(key(item))`). `SignalCell::update` mutates the storage in place and notifies; the effect then reconciles a `row_keys` of the OLD length against an `old_items` that is the new array itself. For a `remove(0)` on six rows: `same(old_items[5], item)` reads past the end — `index out of bounds: the length is 5 but the index is 5` from `__at` (seven rows give the owner's 6/6). For `messages[0] = Message { .. }` through `update`: `old_items[0]` IS the new element, `same` says Keep, and the row never re-renders (DOM-stub repro: the tree still shows the old text, no `render` line). `bind_each_by` holds `row_items` the same way (its `same` is constant, so only the panic applies). The list-`set` path is untouched: a fresh array replaces the storage and the old one stays whole.

Interim std fix: snapshot what the binding keeps (`row_items.write() = list.map(|x| x)` or a `List` copy intrinsic) — O(n) per change, which the keys pass already pays. The principled fix is B256 (a `Shared::read()` result that obeys rule 1), after which `list` itself is a copy and the snapshot is redundant. Pin both symptoms in `ui_rows.rs` (one `update`-driven `remove`, one in-place element write) — the only existing pin that drives `update` beside a `bind_each` (`reactive_lifetimes.rs`'s cycle exemplar) only PUSHES, which happens to survive (a longer `old_items` is never read past `old_keys`).

Kolt workaround until then: replace instead of mutate — `self.messages.set(self.messages.get().filter(|m| !m.eq(message)))`; verified to reconcile cleanly and keep every surviving row's element.
