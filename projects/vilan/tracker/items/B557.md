# B557 — A blanket impl over the tuple family (`impl type T: (2..: Show) with Show`) satisfies a `T: Show` bound for a NON-tuple struct at the bound check, and emission then dies with "internal: a call resolved to `Show`'s requirement `show`, which has no body"

- status: OPEN
- kind: bug (solver; false acceptance then an internal error)
- area: Type system

Repro (vilan 0.44.0 e5e15ca7, JS backend):

```vilan
trait Show {
	fun show(self): str;
}
impl type T: (2..: Show) with Show {
	fun show(self): str { "tuple" }
}
impl i32 with Show {
	fun show(self): str { "i32" }
}
struct Opaque { tag: i32 }
fun needs<T: Show>(value: T): str { value.show() }
fun main() {
	print(needs((1, 2)));
	print(needs(Opaque { tag = 1 }));
}
```

Expected: `needs(Opaque { tag = 1 })` refused (`'Opaque' does not implement trait 'Show'`). Got: a clean check, then `internal: a call resolved to Show's requirement show, which has no body` at emission. The analyzer's impl selection admits the tuple-family blanket for any subject (the arity bound is applied only on the emission side, `tuple_bound_arities`). Found by debug-47 adding `impl type T: (2..: Debug) with Debug` to std for debugging.md S4 (E260's tuple case): with it in std, EVERY type satisfied `Debug` (pin `generics::b194_an_unmet_derived_bound_is_refused_at_the_use_site` went silent), so the tuple impl is held back and E260's `T: Debug` over a tuple waits on this.

- 2026-10-05 (solver-47's independent find of the same fault; it blocks B443): a TUPLE-bounded blanket subject (`impl type T: (2..: PartialEq) with PartialEq`) is admitted for receivers that are no tuple: with it in std, `==` on an `Option<usize>` (or a `ConnectionState`, a `Hash`) reached through a generic body is refused "'Option<usize>' is not a tuple: this argument's parameter is bound '(2..: PartialEq)'" — B443's fix is the two blankets (`compare.vl`'s position-by-position `eq`, `hash.vl`'s `canonical_hash`); with them `(1, "a") == (1, "a")`, a `(2..: PartialEq)` pack holding a pair and a tuple-keyed `HashMap` all compile and run on JS. But member selection for a generic receiver resolves `eq` to the blanket and only the instance's bound check refuses it, so a non-tuple `T: PartialEq` instance breaks (~1 in 20 inference pins went red). Rec: a subject binder's TUPLE bound filters admission (`impl_subject_admits` / the provided-trait index), as its trait bounds rank it; then land B443's blankets. Also: a caller's `T: (2..: PartialEq)` value is not itself `PartialEq` (`values == other` is refused "T is unbounded") — the element bound proves the blanket's subject bound, which the bound check does not read. Natively the blanket's body is `TupleKeys` (not emitted yet). Sizing M; solver (impl_select's admission is shared with perf-47's memo).
