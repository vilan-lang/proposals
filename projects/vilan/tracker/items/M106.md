# M106 — the compiler SUGGESTS how to make a slow program check faster — e.g. a type annotation where inference is measured to be exceedingly slow — as a warning or an info, never an error

- status: OPEN — filed 2026-10-02 (the owner's item)
- kind: feature (diagnostics; M — design first)
- area: Performance & footprint

Shape to decide (rec in each): WHAT is measured — a deterministic COST per declaration/expression (unification steps, candidate selections, fixpoint rounds, instantiations minted), not time, so the suggestion is the same on every machine and never flickers (rec: counts, with a threshold per kind); WHAT is suggested — an annotation on the binding/closure parameter/return whose inference dominated, a named type for a deep generic chain, sealing a long pipe chain into a named function, a narrower import that prunes a blanket's candidates — each only where the compiler can show the annotation it would write (a quick fix); SEVERITY — rec an `info` in the editor (a hint with a code action) and a line in `vilan check --timings`, promoted to a warning only past a much higher threshold, never an error, suppressible per site; WHERE it shows — LSP hint, `vilan check --timings` report (top N costs with spans), not the default CLI output. First step is the instrument: per-item cost attribution in the analyzer (also what M105's counters and the per-release 'top offenders' report need). Sizing M (instrument) + M (suggestions); a short paper or a section of M105's paper first.
