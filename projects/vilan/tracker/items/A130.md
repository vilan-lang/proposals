# A130 — a MODULE-LEVEL `.cell()` leaks by design (it is owner-tied and a module has no owner to release it — the strong root → record → node → root loop lives for the program), and the mistake is easy to make: should a separate `.cell_global()` carry that intention explicitly, with `.cell()` REFUSED in a module binding's initializer and steered ('build it under an owner, or say `.cell_global()`')?

- status: OPEN — filed 2026-09-25 (the owner's question at the Order 41 rulings)
- kind: design
- area: Reactive core & UI

Rec YES: the refusal is static and cheap (the analyzer knows a module binding's initializer from a function body; a `.cell()` reached from module init through a call is not caught, and need not be — the direct spelling is the common mistake); `.cell_global()` documents the lifetime in the name, the no-cycle gate excludes it by name, and reactive-pipeline.md §2.4 gets the sentence. Ships with A124 S2c in Order 42's reactive lane (the flip is where `.cell()` becomes common); ledger row for the refusal.

- 2026-09-25 (Order 42 GO): R-e RULED — the refusal is STATIC-ONLY (a `.cell()` in a module binding's initializer; one reached through a call from module init is the documented remainder). reactive-42, with the flip.
