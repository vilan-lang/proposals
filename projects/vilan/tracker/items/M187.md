# M187 — A region's `cut_row` makes a new DOM Range per row and never lets it go: closing a long list is quadratic, and everything after it is slowed until GC

- status: OPEN - filed 2026-11-02 (kolt, as M186; renumbered M187 at the sync - M186 was taken on main the same day by lane b693's find, the path-list copies)
- kind: performance (std::ui, browser; S)
- area: Reactive core & UI — DOM regions

`Region::cut_row` (vilan/std/src/browser/web/ui.vl:801) takes a row out with a fresh `create_range()` each call. `close` calls it once per row, and the order pass and row removal use it too. A DOM Range is *live*: until it is garbage collected, the browser updates it on every DOM mutation in its document. So a close of n rows leaves n live Ranges behind it, every later cut and removal pays for all of them, and the work grows with the square of the row count. The cost also spills past the close: everything the app does next (building the next page) pays for those Ranges until GC frees them.

## In kolt

On `next` (2f89bee9, with B693), on a 2,089-task organization, the Table page (one `each` of rows, an `each` of cells in each, 56,964 elements) opens in 1.3–1.6 s, but **leaving it takes 8.5–9.5 s**, every time. A profile of leaving it spends about 12.5 s of samples in `extractContents` (in `cut_row`), `remove` (in `drop_row`) and `remove` (in `close`, for `live` and the anchor), all under `dispose` → `advance` → `close`. Taking the table's `<tbody>` out of the document first barely helps (6.8 s), so the cost isn't layout.

## The cause, isolated

kolt session scratchpad `cdp/rangetest2.mjs`. Rows of (empty text marker, `<div>`) under one parent, all taken out, each way timed on a fresh `about:blank` in Chrome:

| rows | a Range per row (what `close` does) | remove each node directly (attached) | remove each node directly (detached) | one Range for the whole run |
|---|---|---|---|---|
| 2,000 | 40 ms | 1 ms | 1 ms | 1 ms |
| 4,000 | 143 ms | 1 ms | 1 ms | 1 ms |
| 8,000 | 598 ms | 2 ms | 2 ms | 2 ms |

And the spill-over: with 8,000 Ranges made and still held, removing 16,000 plain `<div>`s one by one takes **1,340 ms** (normally about 2 ms). Before this test isolated each way on a fresh page, the leftover Ranges from one run made every later way look quadratic too.

## Recommendation

- **No Range per row.** `cut_row` can walk siblings from `row.marker.nextSibling` to `end` into a `DocumentFragment`, or remove them. That gives the same nodes in the same order, with nothing live left behind. If a Range is kept, use one per region (or per pass), not one per row.
- **`close` doesn't need to cut rows one by one.** It throws the content away, so one removal of the whole run (marker of the first row to the anchor, with nothing kept) does the same in one step.
- **Better still, skip it under a closing ancestor.** When an enclosing region is closing (a page swapped away), the descendants' DOM leaves with it, so nested regions only need their bookkeeping cleared. Today each nested `each` (every row's cells) cuts its own rows first.
