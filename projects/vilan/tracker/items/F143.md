# F143 — A module-level `mut` binding handed to a call beside a later argument that writes it answers differently: `has(global, grow())` (`grow` pushing into `global`) prints `true` on JS and `false` natively; `lent(&global, grow())` the same; `global.push(reset())` (`reset` re-binding `global`) leaves 1 item on JS and 2 natively

- status: OPEN — filed 2026-10-15 (native-53's find, Order 53)
- kind: miscompile (JS vs native)
- area: Native targets & rendering

F129/F138's order is §6.9's, for CAPTURED bindings; a module-level `mut` binding is a place every function shares, and neither backend orders its arguments by that. Natively a by-value or `&` argument over it is copied out of its thread-local cell where it stands (so an in-place write by a later argument is missed, where the JS argument is the binding's object), and a `&mut` receiver over it borrows the cell after the hoisted by-value arguments (so a re-binding is seen, where JS writes the old object). Rec: the same rule as F138 for a module-level `mut` binding — read late on both when a later argument runs code (any call can reach the binding) — the estate counted first; the native half is `defers_its_cell_copy`'s `cell_spine` admitting a module root, the JS half `argument_order.rs`'s `is_captured` answering true for one.
