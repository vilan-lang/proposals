# B687 — M164's `the writer of a refused body stalls` case is flaky on windows under Node: the v0.53.0 release gate saw the writer get 56 MiB of a 64 MiB body out after the 413 (the case tolerates 16 MiB) while the same shard passed the case twice on the same tree within the hour

- status: OPEN - filed 2026-10-27 by the integrator at the v0.53.0 cut (the gate job was re-run; Order 56's tooling lane, after N186)
- kind: flaky test (windows + Node; S)
- area: Runtime & http

**The failure.** `m164_the_default_cap_refuses_an_oversized_body_without_reading_it_on_both_backends` panicked with `Node / the writer of a refused body stalls: the writer got 56557568 of 67108864 bytes out (failed: true): the server read the body`. The case (request_body.rs:376-408) sends a keep-alive POST head declaring 64 MiB, reads the `413 Content Too Large`, then streams 64 KiB pieces until the write fails, and passes only when the write fails with under 16 MiB out - the proof that the server stopped reading after the refusal. On windows under Node the write failed after 56 MiB; the native leg passed. **The evidence it is a flake, not a regression.** The release commit a4bbe8ce changes only CHANGELOG.md, perf/budgets.toml and perf/report-v0.53.0.md against the sealed c50a0a58; the same shard (windows-latest 2/4, same 2715-test partition) passed the case on the seal's CI (run 40433309903, 02:00) and on the release commit's own CI (run 40524090084, 15:04), and failed it on the release gate (15:05). **What to look at.** (1) Node on windows: after `req.destroy()`/the refusal the libuv stream may keep draining the kernel buffer for a while (the socket's receive window plus Node's own `highWaterMark` are not 56 MiB, so the server-side read continued past the refusal for some hundreds of milliseconds); whether `pause()` reaches libuv before the close, and whether the refusal path should `socket.destroy()` synchronously. (2) The case's 16 MiB tolerance is a guess at the windows socket buffers; measure the in-flight bytes on a passing windows run and set the tolerance from the figure, or make the case assert on the SERVER's count (the runtime can expose how many body bytes it read; zero is the contract) instead of the client's. (3) If (1) is Node-on-windows behaviour the runtime cannot change, mark the Node leg of this one case windows-skipped with the reason, keeping the native leg strict. Rec: (2) first - the contract is `the server read nothing`, and the client-side count measures the kernel, not the server.

**Recurrence 2026-11-02.** CI run 41486609884 on next 2f89bee9 (the B693 merge: store_core.vl, store pins, docs, CHANGELOG, budgets - nothing near http or the runtime's sockets), the same shard `test (windows-latest, 2, 4)`, the same case and leg: `Node / the writer of a refused body stalls: the writer got 27983872 of 67108864 bytes out (failed: true): the server read the body` - 26.7 MiB this time (56 MiB in October), the other three windows shards green. Re-run by the integrator once the run's queued ubuntu legs finished (ci-watch-b693-rerun.log). Two data points now: the in-flight figure is not stable, so rec (2) - assert on the SERVER's count - stands.
