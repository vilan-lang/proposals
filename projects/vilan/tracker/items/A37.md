# A37 — `[gone]` on a trait member: accessible only THROUGH the trait, never on the concrete type (discussion; value unclear)

- status: OPEN — discussion, NOT queued (the owner: "I'm not sure how valuable it really is")
- kind: design discussion
- area: Type system & the type solver
- source: the owner, 2026-09-03, recalled from an earlier discussion

```vilan
trait X {
  [gone]
  fun f() { 0 }
}
struct A {}
impl A with X {}

let a = A {};
a.f();            // error: does not exist on `A`
fun g(x: X) {
    x.f();        // ok: exists through the trait
}
```

Motivation: `impl type T with …` blanket impls put a method on every
matching struct; `[gone]` would keep such a member off the concrete
type's surface (completion, method resolution) while trait-typed
code still reaches it. Distinct from `[doc(hidden)]` (discoverability
only) and from module visibility (E124 — this is METHOD surface, not
module surface; it does not bear on the dead-code question). Open
questions if ever taken: `[gone]` on a REQUIRED member (the impl must
write it but cannot call it on `self`?); what `self.f()` inside
another member of the same impl resolves to; the steer under B175's
which-refusal rule. Leave open until a real case wants it.
