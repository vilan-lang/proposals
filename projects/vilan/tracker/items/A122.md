# A122 — the REVERSE of `reactive::combine` — `divorce<T: (2..)>(source: SignalCell<T>): (U in T: SignalCell<U>)`, one derived cell per tuple position (kolt channel.vl:19 writes the signature with `// TODO: Implement`) — cannot be written in userland OR std today: the tuple comprehension `(x in xs => e)` is the only way to iterate a tuple and it takes a MAPPED-TUPLE PARAMETER, not a value of type `T` (`a tuple comprehension's source must be a mapped tuple, got T`); and there is no INDEXED read of a generic tuple (`whole[pair.0]` / `whole.i` at a generic position). The 2-arity hand-written form works (`(source.map(|w| w.0), source.map(|w| w.1))` — probed live)

- status: OPEN — filed 2026-09-21 (the owner's question, mid-Order 39)
- kind: feature (+ a comprehension form)
- area: Reactive core & UI

Two missing pieces, either of which unlocks it:

**(1) A comprehension over a VALUE of mapped-tuple type with its POSITION in scope.** `(element, index in whole => …)` or `((i, element) in whole => …)` — B368 now admits a tuple pattern in a `for` header, so the comprehension binder can take the same production. With it: `fun divorce<T: (2..)>(source: SignalCell<T>): (U in T: SignalCell<U>) { ((i, _) in source.get() => source.map(|whole| whole[i])) }` — which ALSO needs (2).

**(2) An indexed read of a generic tuple, `whole[i]`, typed per position.** Today `.0`/`.1` exist only at a CONCRETE tuple type. At a generic `T: (2..)` the element type at position `i` is `U_i`, known only when the comprehension's `U` is in scope — so the read is legal exactly inside the comprehension that binds `U`, and nowhere else (the same rule that makes `(U in T: SignalCell<U>)` a type but `T[i]` not one). That is the typing work: `whole[i]` inside `(… in whole => …)` types as the comprehension's `U`.

Alternative without new syntax: std ships `divorce2`/`divorce3`/… by arity (the probed 2-arity form generalises mechanically), as `combine` would have had to before mapped tuples. Cheap, ugly, and it is what kolt would write today. Rec: (1)+(2) together as ONE feature — 'the tuple comprehension binds its position and reads by it' — because the same two pieces are what B183's zip form and A112's per-position derivations need; `divorce` is then a three-line std function beside `combine`, and its subscriptions are derivations (A110 door 2's `as_derivation` mark, once per output cell).

Pins: `divorce` over a 2- and a 3-tuple (values follow, each output cell fires only when ITS position changes — or state that it fires on every source change and why); a round trip `divorce(combine((a, b)))` re-deriving `a`'s and `b`'s values; the comprehension binder's pattern form; the indexed read refused OUTSIDE a comprehension with a message naming the rule.

- 2026-09-21 (the owner's pseudo-syntax, the same day): the owner proposes a std `tuple` module instead of new comprehension syntax: `import std::tuple::{ TupleKey, (impl _: (2..))::{ values, entries, get } }` (grammar uncertain), then `let signals: (U in T: SignalCell<U>) = source.get().values().map(|initial| Signal::new(initial));` and `source.effect(|fresh| { for (key: TupleKey<T>, value: T) in fresh.entries() { signals.get(key).set(value); } })`, with two named hazards — (1) `TupleKey<T>` indexes any tuple DERIVED from `T: (2..)`, (2) tuple `.map` must return a tuple typed as a derivative of `T` so it can be indexed later. The owner uses the fixed-arity form meanwhile (no rush). INTEGRATOR'S READ, recorded for the paper (B183's family): the shape is RIGHT and it is the same two pieces A122 filed, given library spellings — `.entries()` IS "a comprehension that binds its position" and `signals.get(key)` IS "`whole[i]` typed per position". Adjustments: (a) `TupleKey<T>` should be `TupleKey<T, U>` — a key carries WHICH tuple family it indexes AND the element type at that position, else `signals.get(key)` cannot type its answer as `SignalCell<U>` (the analyzer must already know per-position `U` for the mapped type `(U in T: F<U>)` to exist at all — that is the fact the key reifies); with `U` on the key, `value: T` in the loop header is wrong and becomes `value: U`; (b) `.values()`/`.map` on a value of type `T: (2..)` are exactly what the language refuses today ("a tuple comprehension's source must be a mapped tuple, got T") — the mapped-tuple TYPE is what `(U in T: F<U>)` gives, and a `.map` answering `(V in T: G<V>)` is the comprehension with the derivative typing the owner asks for in (2): so the design is 'tuple comprehension, spelled as methods on a std trait implemented for every `T: (2..)`' — the same typing work either way, with the library spelling winning on discoverability and on B183's zip (`a.entries().zip(b.entries())`); (c) the `for` header's tuple pattern is B368's, landed this order; (d) `(impl _: (2..))::{ … }` is not a grammar we have — the `[extern]`-free way to give every tuple methods is a blanket `impl type T: (2..) with Tuple` on a std trait, imported as `std::tuple::Tuple` (B318's selector `(impl _)` admits the impl); (e) each `signals.get(key).set(value)` write in ONE effect run is n writes per source change — fine, but it means every output cell fires on every change whether its position moved or not; the derivation-per-position form (`source.map(|whole| whole[i])`) gets the same, so the pin's claim is 'fires on every source change', unless a `PartialEq`-gated `set_if_changed` is wanted. REC for the paper: build the `Tuple` trait with `entries()`/`get(key)`/`map` and `TupleKey<T, U>`, make the comprehension its desugar (one mechanism), keep `combine` as is, add `divorce` beside it.
