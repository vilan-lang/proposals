# B659 — An integer literal passed alongside a closure to a generic method defaults to `i32` before the closure's known result type is unified: `opt.map_or(|it| it.depth, 0)` with `depth: usize` reports "Expected i32, but got usize" inside the closure

- status: OPEN — filed 2026-10-20 (kolt's rich text document: a list item's depth, `list.map_or(|item| item.depth, 0)`)
- kind: type inference (checker; S)
- area: Language

```vilan
struct Item { depth: usize }
fun main() {
	let item: Option<Item> = None;
	let depth = item.map_or(|it| it.depth, 0);
	let other: usize = depth;
}
```

vilan 0.52.0 (`vilan test`): "Expected i32, but got usize … convert with `.as_i32()`" at `it.depth`, then "Expected usize, but got i32" at `let other: usize = depth;`. `U` is pinned to `i32` by the literal's default, although the closure (the first argument) already determines `U = usize`. With an expected type the same call checks (`fun f(..): usize { item.map_or(|it| it.depth, 0) }`), so it is the literal default winning over the closure, not a missing unification.

Ask: settle an unsuffixed literal's type only after the other arguments have been unified, as with `let x: usize = 0` (a literal defaults to `i32` only when nothing else constrains it). The checker's advice to convert with `.as_i32()` points the user away from the fix (a `0usize` suffix).

**A second shape (2026-10-20, kolt's message editor):** a closure whose `ret` returns a `usize` and whose tail is a bare literal. `list.peek(|list| { for .. { found then ret at; } 0 })` with `at: usize` reports "this `ret` returns usize, but the closure's body yields i32" at the `ret`, and points to the tail `0` as "the tail it disagrees with". The same root cause, probably: the literal takes `i32` before the `ret`'s type is unified with the closure's result.
