# A183 — THE IMPORT FOUNDATION (paper): a path's head may be a ROOT VALUE - `(import pkg)`, `(import std)`, `(import dep)` - in every path position (expression, type, pattern, selector subject), the rest projections (`::name`, `::(impl T)`, `::*`); the `import` statement is `use` of such a path and a bare root head is sugar for the parenthesized root, so `pkg::m::S { x = 1 }` and `(import pkg)::m::S { x = 1 }` work inline; A181 and A182 are its first slices

- status: OPEN - RULED 2026-11-03 by the owner ('I like using the formal definition as the foundation our sugar is built on'); the paper for Order 56 (parser/solver lane writes it before A181/A182 build on it)
- kind: design (language; paper; L arc, S-M slices)
- area: Language

The paper: (1) the three primitives - a root value `(import X)` (X a package, std, a dependency; later a versioned or platform-conditioned root), projections (`::name` an item or module, `::(impl T)` the blocks whose subject unifies, `::*` everything), and `use` bringing a path's result into the file's scope - and the elaboration table: `import a::b;` = `use (import a)::b;`, `import a::{ b, c as d, self }` = three uses, `(impl T)` alone = `::(impl T)::*`, `only` = no impl projection, `export *` / `export import` = `export use`, the package prelude = uses every file begins with; (2) ONE keyword: `import` in statement position is the sugar, `(import X)` in path-head position is the root value - no `use` keyword in the surface, `use` is the spec's metalanguage; (3) a bare root head anywhere elaborates to `(import root)` (so inline `pkg::m::S` works; the explicit form for a shadowed head or a non-name root); (4) the ruling to make deliberately: an INLINE absolute path is explicit at its site and satisfies visibility.md §3.2's 'intent in one place' for items and for impl members named by path, while a bare method call on a receiver still needs the file to ADMIT the block (an import statement with a projection, or the prelude) - tooling's 'what does this file reach' reads both; (5) what the resolver becomes (one function over root values + projections; the type-named-prefix diagnostic retired; the three namespaces as projection kinds), what the LSP gains (hover shows the elaboration; references/rename over projections), the formatter (canonical sugar forms; the bare form of a one-selector set), the estate (nothing moves: every current spelling is a sugar form), and the slices: A181 (absolute subjects + the bare selector form + `*`), A182 (leaf-only admission + the prelude), then inline roots (S), then the dependency/platform roots (design). Owner Qs with recs. Sizing: the paper S-M; the arc L in S-M slices.

- 2026-11-03 (the owner's `self`/`super` questions; a paper section): PROBED on next - `import pkg::m as super; import pkg::m::a as self;` in src/m/a.vl compiles and runs today (`super::helper() + self::own()` prints 3): both are plain alias names now, and the spec never mentions `super`. In the foundation they are IMPLICIT, LOCATION-DERIVED bindings every file begins with - `use (import pkg)::<this file's path> as self;` and `use (import pkg)::<its parent> as super;` - so nothing is new in the resolver; the new things are (a) they are implicit and reserved (a user `as self` / `as super` is refused once blessed: 'the file's own module; it cannot be rebound'), (b) `self` in a set (`{ self, Theme }`) and `mod self;` are the same `self` in two positions, (c) uses beyond readability and shadowing: generated code (derives, macros) writes `self::Item` to name the host module hygienically whatever the file imports; a file with a directory body reaches its children as `self::child`; a file's own references become MOVE-STABLE. On moves: a move changes what `self`/`super` denote (which is the intent - the file now belongs there) and leaves absolute self-references pointing at the OLD path, so the LSP's move refactor rewrites absolute paths and leaves relative ones; `super` is stable within one parent. Rec: bless both; `super` ONE level only (no `super::super` - an absolute path past that, as Rust practice discourages chains); derives emit `self::`.
