# F1 — DISCUSSION: building GPU-RENDERED NATIVE APPS in vilan. Today the build model is `Target` = `Backend` + `Platform` (platform-model.md, implemented 2026-06-23) with ONE backend (the JS emitter) and the browser/node/deno/bun platforms; `std::ui` has two layers behind one public surface (browser = live DOM, process = SSR string tree — the precedent for a third). A native app needs FOUR things the project has none of: (1) a native BACKEND — emit Rust (rustc does codegen; vilan's affine moves, borrows and `own` map onto ownership) vs C vs wasm-in-a-host vs an interpreter; (2) memory without a GC — C14 (cells on Rc/owner arenas), real counting for `Shared`, closure captures (`capture-clones.md`), strings/lists with owners, `destruction.md`'s drops actually running; (3) a RENDER LAYER — a third `std::ui` twin building a retained scene tree rendered by a GPU renderer (wgpu + vello-class 2D, text shaping, a flexbox-class layout engine such as taffy) with `Style` mapped onto it (A95 conditions: `hover()`/`active()` become hit-test state, `media`/`sm..xl` become window queries, the `css` block a native style resolver) and events/input/windowing (winit-class); (4) std's platform layers (`[library.layer]`, `PlatformPattern`) admitting a `native` platform and the coloring rules deciding what a native entry may reach (no `std::dom`, no `fetch` shaped as the browser's). Prior art to measure against: Dioxus/Blitz (HTML+CSS semantics, vello-rendered), Makepad, Slint, GPUI (Zed), Flutter (Impeller)
