# B370 — MISCOMPILE (HIGH) + the law it breaks: an unsuffixed LITERAL takes its type from context EVERYWHERE (the owner's ruling, 2026-09-21) — but an EXPRESSION of literals in a typed position is re-typed AFTER its operator was dispatched: `fun rem(value: f64)` called as `rem(4 / 16)` prints **0** with no diagnostic (emitted `Math.trunc(4 / 16)`), as do `let x: f64 = 4 / 16`, a return, a method argument and a struct field — kolt writes `Length::rem(4f / 16)` to dodge it. Plus two positions where the literal is not re-typed at all: the LEFT operand of a binary operator (`1 + a`) and the elements of an annotated list literal

- status: OPEN — filed 2026-09-21 (the owner's ruling, mid-Order 39); I5's S1 depends on it
- kind: bug (MISCOMPILE, silent wrong value) + design
- area: Type system & the type solver

## The miscompile (the owner's report, reproduced on c3f7d1a38)

`Length::rem(4 / 16)` in kolt computed integer math "despite `rem` taking a float", so kolt spells `4f / 16` everywhere. Minimal: `fun rem(value: f64): f64 { value }` + `print(rem(4 / 16))` → `0`; `let x: f64 = 4 / 16;` emits `const x = Math.trunc(4 / 16);` while `4f / 16` emits `4 / 16`. The solver accepts the expression as `f64` — it re-types the literal operands from the context — but the operator's IMPLEMENTATION was chosen while they still read `i32`, and nothing re-dispatches. An `i32` VARIABLE in the same position is correctly refused, so this is exactly the literal path. `*`, `+`, `-`, `%`, unary `-` and parentheses give the right value only because the integer and float answers coincide; `/` is where they differ (and any overloaded operator whose `i32` and `f64` impls differ — `%` on negatives, comparison of a fraction). Positions reproduced: argument, annotated `let`, return, method argument, struct field.

Fix direction: the context's type must reach the literal operands BEFORE operator dispatch (push the expected type down through arithmetic nodes whose operands are all literals or literal expressions), or dispatch must be re-run when a literal operand's type is refined — one mechanism with gap 1 below (`1 + a`), which is the same ordering problem seen from the other side. Pins, each planted red: the five positions above with `/`; a nested expression (`rem((1 + 3) / 16)`); a mixed one that must stay REFUSED (`rem(n / 16)`, `n: i32`); the emitted JS carries no `Math.trunc`. Kolt after the fix: every `Nf / M` may drop its `f` (a census, the owner's word).

The law: a literal with no suffix has NO type of its own until its context gives it one; `i32` (and `f64` for a fractional literal) is only the DEFAULT when the context is silent. That is what the solver does in an annotated `let`, an argument, a return, a typed-LEFT binary operand, a comparison, a struct field, an enum payload, a generic method argument, a closure return, a match arm, an if branch, a compound assignment and an index position (all probed green).

**Gap 1 — the literal on the LEFT.** `a + 1` works and `1 + a` does not: the operator family resolves on the LEFT operand's admitted set (B179's principle), and a bare literal on the left has already defaulted to `i32` by the time the right is seen. Fix direction: a literal operand defers — when exactly one operand is an unsuffixed literal, the OTHER operand's type decides, then B179's membership check runs as today; two literals default together.

**Gap 2 — a list literal's elements.** The expected type `List<u53>` is not pushed down into the element positions, so the literal is typed bottom-up as `List<i32>` and then compared. The same push-down is owed wherever a CONTAINER literal meets an annotation — census them: list, tuple (`let p: (u53, str) = (1, "a")` — probe it), a `Map`/`Set` built from a list literal, nested lists, a list literal as an ARGUMENT (`takes(List<u53>)` called with `[1, 2]`), a list in a struct field, an `Option<List<u53>>`.

**Census the rest, by probe, before calling it 'everywhere'**: range bounds (`for i in 0..n` with `n: u53`), `match` PATTERNS that are literals against a typed scrutinee, default parameter values, `const let` initializers, a literal inside an i-string hole (no context — defaults), a negative literal against an UNSIGNED context (must be a refusal that names the type, not an `i32` mismatch), a literal out of the context type's RANGE (`let b: u8 = 300` — refuse at the literal), `as_*` receivers (`5.as_f64()` — defaults, by design).

Pins: one per position in the probe table (14 regression guards + the 2 gaps planted red) plus one per census row. I5 (`usize`) rides on this: every `list[0]`, `take(3)`, `slice(0, n)` stays unsuffixed only if this law holds in those positions — most already do.
