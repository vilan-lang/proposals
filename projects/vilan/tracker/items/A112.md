# A112 — INCREMENTAL COLLECTIONS: a collection-valued signal reruns its derivation for EVERY element when one changes (`list.map(|l| l.map(g))` is N calls of `g` per push; a per-element cache is still N checks). The formal shape is a CHANGE STRUCTURE — a small op vocabulary per collection SHAPE, a delta-source trait (op log + cursors), and operators written ONCE as derivatives over the ops — and std already has half of it in the wrong layer: `KeyedCell`'s log/cursor machinery (A54, rpc.vl). PAPER; the receiver question is PROBED and answered (both spellings work)

- status: OPEN — filed 2026-09-21 (the owner's `map_collection` question); paper first
- kind: design (paper) + feature
- area: Reactive core & UI

## What was asked

```
let my_list: Signal<List<str>> = Signal::new(List<str>::new());
let my_nums = my_list.map_collection(|x| { print("ran"); x.parse_f64().unwrap_or(0f) });
my_list.push("10.5"); // only one "ran"
```

…and a worry: doing it by intertwining signals and lists (`Signal<List<T>>.push`, `.map_collection`) means re-implementing every collection method — anti-DRY. Is there a generic system, and does it extend to derivations of a different type?

## The theory, in one paragraph

Incremental computation over changes (Cai/Giarrusso et al., "A Theory of Changes for Higher-Order Languages"; shipped relatives: Jane Street `Incr_map`, .NET DynamicData changesets, Solid `mapArray`, differential dataflow). A type `A` gets a change type `ΔA` and an apply `⊕`; every operator `f: A → B` gets a derivative `f': A → ΔA → ΔB`; the law is `f(a ⊕ da) == f(a) ⊕ f'(a, da)`. For `map g` the derivative of `Insert(i, x)` is `Insert(i, g(x))` — `g` runs once and nothing else is looked at. Not N cache checks: zero.

## What std already has

`KeyedCell<K, T>` (A54, rpc.vl) IS this: writes append `Delta<K, T>` to a bounded log (`keyed_log_limit`), consumers hold a `KeyedCursor` and drain `since(cursor)`, a lagging cursor degrades to `Reset`, and the cell is a `Source<List<T>>` so `each` takes it. Its own doc comment states the principle — "only the MUTATION knows what changed". Two limits: it demands `T: Keyed<K>` (a `List<str>` has no keys, and may hold duplicates), and it lives in `std::rpc` because `Delta` is a wire type with one consumer.

## The generic system — three layers

1. **An op vocabulary per SHAPE, not per method.** Sequence: `Splice(at, removed, inserted)`, `SetAt(at, value)`, `Reset(list)` (+ `Move` if a reorder should not be a Reset). Map: `Put`/`Delete`. Set: `Add`/`Remove`. POSITIONAL is the sequence primitive; keyed addressing is a position index on top (exactly `KeyedCell.positions`).
2. **One delta-source trait** in `std::reactive`: `Source<C>` + `cursor()` + `since(cursor): List<Op>` — `KeyedCell`'s machinery lifted out. rpc's keyed forward becomes one CONSUMER translating `SeqOp` + keys → `Delta<K, T>`; `Delta` stays the wire vocabulary and `std::reactive` still imports nothing from `std::wire`. Writes in one turn coalesce for free: one notification, the consumer drains every op at settle.
3. **Operators written once against the ops.** What an operator costs is decided by its algebra — this is the "derivations of different types" answer:

| operator | extra state | per op |
|---|---|---|
| `map_each(g)` | the output list | 1 call of `g` per inserted/updated element |
| `filter_each(p)` | kept flags + index translation (Fenwick) | 1 call of `p`, O(log N) |
| `sort_by(key)` | order-statistic tree | O(log N) |
| fold over a GROUP (`sum`, `count`, `mean`) | the accumulator (needs an inverse) | O(1) |
| fold over a MONOID only (`min`, `max`, `concat`) | segment tree | O(log N) |
| arbitrary fold | — | O(N) rerun, honestly labelled |
| `index_by` / `group_by` (List → Map) | the map | O(1), emits map ops |

Joins / `flat_map` are differential-dataflow territory — out of scope. **`each` is one more consumer**: it applies ops to its rows directly instead of `reconcile`-ing the whole list per change, which for UI is the bigger win than `map_each` (A98's settled-run scan stops being needed on the delta path).

## The receiver question — PROBED (vilan 0.40.0, 0fa109eb7)

The DRY answer is "method names are trait DEFAULTS over one primitive per shape": `push(x)` is `splice(len, 0, [x])`, `remove(i)` is `splice(i, 1, [])`, `clear` is `splice(0, len, [])` — a dozen one-liners, written once, shared by every cell kind (local, keyed, optimistic-remote). The open question was the receiver: `List`'s mutators are `external fun push(&mut self, ..)`, a cell handle's are `self`.

- **Probe C — `self` receivers, the owner's exact spelling. WORKS.** `trait SequenceCell<T> { fun size(self): i32; fun splice(self, at, removed, inserted: List<T>); fun push(self, value: T) { self.splice(self.size(), 0, [value]) } .. }`, `impl ListCell<type T> with SequenceCell<T>` writing only `size` + `splice` (log the op, `set` the value). `let my_list: ListCell<str> = ..; my_list.push("10.5")` on a plain `let`. With `map_each` draining the log on notification: three pushes print `ran` exactly three times; a `remove(1)` runs `g` zero times; the derived list reads `10.5, 12.4`.
- **Probe A — `&mut self` receivers inside `cell.edit(|&mut list| ..)`. WORKS.** `trait Sequence<T>` with a `&mut self` primitive; a `Tracked<T>` recorder implements only `size` + `splice` and inherits `push`/`insert`/`remove`/`clear`; `edit` hands out `&mut Tracked<T>`, then appends the ops and sets once. Four mutations in one `edit`: ONE notification, four ops logged, correct contents. This is the batch spelling, and the one that lets a body written against `Sequence<T>` run on a recorder.
- **Probe B — `List<T>` ITSELF adopting the `&mut self` trait, so generic code serves a plain list and a recorder alike. TYPE-CHECKS, MISCOMPILES → B359.** A default body's `self.push(..)` is HIJACKED by the implementing type's inherent `push`, and when that inherent is `external` the emit calls a function that was never emitted (`ReferenceError: $b is not defined`). Through a generic bound (`fun fill<S: Sequence<str>>(target: &mut S)`) the same call reaches the trait's `push` correctly. Until B359 is ruled and fixed, the `&mut self` trait's method names must not collide with `List`'s inherent ones on a `List` impl — which does not block this item (the recorder and the cell are the implementors; `List` need not be).

So ONE trait cannot serve both receiver kinds, and it does not need to: `SequenceCell<T>` (`self`) is the everyday surface, `Sequence<T>` (`&mut self`) is the `edit` surface, and both stand on the same single primitive. The duplication is the default one-liners twice — a macro can stamp both from one list if that itches.

Side note from the probes: inside `impl ListCell<type T>`, a bare `ListCell::new()` binds `T` from `Self` even against a `ListCell<U>` annotation ("Expected ListCell<U>, but got ListCell<T>"); `ListCell<U>::new()` is the spelling. Probably intended (`Type::func` inside its own impl reads as `Self::func`), recorded in case it is not.

## Design points the paper owes

- **Purity.** `g` runs once per element, so it must be pure IN THE ELEMENT. A `g` that reads other signals wants Solid's per-element owner: minted on insert, disposed on remove/`Reset`, all under the enclosing boundary — the `each` row discipline, and A110's ordering applies to it.
- **The compat path.** A plain `set(whole_list)` records `Reset` (N calls of `g`), or — with `T: PartialEq`/keys — a diff into ops (N cheap compares, zero derivations for retained elements; `reconcile`/`keyed_diff` exist). A plain `SignalCell<List<T>>` adapts through the same door.
- **Cursor lifetime.** A derived cell's cursor pins the log; it is dropped by the owner the derivation was made under (`register_with_owner`'s rule), and a derivation with no subscribers should hold no cursor.
- **Naming.** `map_each` / `filter_each` beside `each` (A99's naming argument), not `map_collection`.
- **`KeyedCell` after the lift:** a `ListCell` + a key index + the wire translation; its public surface and the `Patch` frame do not move.

## Pins owed

- THE LAW as a property test: after every settle, `derived.get() == source.get().map(g)` against the naive rerun, over random op sequences (incl. several ops per turn, `Reset`, a lagging cursor past the log limit);
- call counts: k pushes → exactly k calls of `g`; a remove → zero;
- a delta-driven `each`: one push into 1 000 rows builds one row and runs no reconcile pass (M-section measurement beside A98's).
