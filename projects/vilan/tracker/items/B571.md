# B571 — type ascription in expression position — `EXP as TYPE` — `SignalCell::new([1, 2, 3] as List<usize>)`, and per stage of a chain: `a() as A .b() as B .c() as C`

- status: OPEN — filed 2026-10-05 (the owner's idea; a paper in Order 48 beside B570, no build before it is ruled)
- kind: language design (M) — paper first
- area: Type system

The owner's sketch:

```
let x = SignalCell::new([ 1, 2, 3 ] as List<usize>);

let y = a() as A
    .b() as B
    .c() as C;
```

It names a type where no `let` is at hand, and in a long chain it pins each stage, which with B570's `auto` (`a() as auto A .b() as auto B`) becomes an inlay hint that lives in the file and localises a type error to the first stage that disagrees.

Facts and questions for the paper (the integrator's first read):
1. `as` is NOT an expression operator today: `let a = 1 as f64;` is a parse error on next @db2df5f1 (`as` is a contextual keyword for import aliases only). So this is new syntax, with no estate to break.
2. ASCRIPTION, never a cast. `EXP as T` means what `let tmp: T = EXP` means: it directs inference (a literal `5 as f64`, an empty `[] as List<str>`, `None as Option<i32>`) and refuses a mismatch. A reader from Rust or TypeScript will expect `n as f64` to convert and `x as Foo` to assert; both must be REFUSED with a steer to the conversion. Say whether that confusion is worth a different word.
3. Coercions: whatever an annotated `let` does, this does - in particular `stage as dyn Flow<i32>` erases, which gives E261's two-stage `match` an inline spelling.
4. Precedence. The chain example needs `as T` to bind as a POSTFIX, with `.b()` continuing after the type; that makes `a + b as T` mean `a + (b as T)`. The type's end must be unambiguous: `x as usize < y` (Rust's known trap: `<` read as a generic list), a closure type `|T| U` followed by more expression, a tuple type followed by a call's parentheses.
5. Whether the result is a place (`(p as Point).x = 1`) or always a value.
6. The formatter's layout for a chain with an ascription per stage, and the editor's: hover, go-to-definition on the type, a quick fix that inserts the inferred type at the cursor's stage.
7. Diagnostics: the mismatch names the stage and both types, and the solver's "cannot infer" steers gain "or ascribe it: `.. as T`".

- 2026-10-05 (the owner): RULED: `as` is a type CONSTRAINT (ascription) only, NEVER a cast. For `x as usize < y`: the owner proposes that a `<` opening a generic list must follow the type name with no whitespace (`List<usize>`), while `as usize < y` with whitespace is a comparison; the formatter writes both canonically. The integrator's reading: keep the word `as` - Swift's `as` is exactly this (a guaranteed coercion, with `as!`/`as?` for casts), TypeScript's is close (an assertion, not a conversion), and only Rust/Kotlin read it as a cast; a numeric `n as f64` is refused with a steer to the conversion, which teaches the difference once. The whitespace rule is sound because vilan has a formatter (there is one canonical spelling) and the parser already reads `<` as a generic list in type position; `as (T)` is accepted as the escape hatch. No better word found: `:` (as in `let x: T`) collides visually with labels and reads badly in a chain. Editor half: E278 (per-stage inlay hints on a multi-line chain, in this spelling). Both to the Order 48 paper.

- 2026-10-05 (the owner): RULED FINAL on the spelling: `EXP as T`, the whitespace rule (`List<usize>` tight opens a generic list; `as usize < y` spaced is a comparison), and `as (T)` accepted as the escape hatch. Considered and declined: `of` (reads as membership, a new contextual keyword), `of<T>`/`as<T>` (nested `>>` fights the lexer), `as(T)` required (sound, the integrator's second choice, but two characters on every use for an edge the formatter normalises).
