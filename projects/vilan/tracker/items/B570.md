# B570 — `auto` type annotations the toolchain keeps current — `fun f(): auto i32 { 0 }` becomes `fun f(): auto str { "hi" }` on format/save; a bare `: auto` is filled in

- status: OPEN — filed 2026-10-05 (the owner's idea; a paper in Order 48 beside M110's S5, no build before it is ruled)
- kind: language + tooling design (L) — paper first
- area: Type system

The owner's sketch: an annotation marked `auto` is written by the toolchain, not the author. Editing the body so the inferred type changes rewrites the annotation at format/save. A bare `auto` (`let x: auto = ..`, `fun f(): auto { .. }`) is filled in. The owner's four aims: (1) the compiler may skip, or defer until save, type work it would otherwise do; (2) the author writes `auto` and gets the type; (3) it does the job of inlay hints but lives in the file, so a non-IDE reader sees it, highlighted and navigable; (4) an opt-in to insert `auto` types everywhere a type is not written.

The integrator's first read, for the paper:
1. The real compiler win is the INTERFACE, not the check: an inferred return forces a function's body to be analysed before its callers know its type. An `auto T` return is a signature that can be read without the body, which is what M110's interface firewall (S5) needs and what incr-47's S0 fingerprints approximate. That argues for returns and module bindings first, locals last.
2. A stale `auto` must not be trusted silently. Treat it like a lockfile: the editor rewrites it; `vilan check` and `vilan build` either verify it and REFUSE a stale one with a `--fix` (so CI catches drift), or rewrite in place. Say which, and what callers were checked against in between.
3. `vilan fmt` is syntactic today and formats a file that does not check. Filling types needs the whole analysed world and cannot run on a broken program, so the rewrite belongs to `vilan check --fix` and an editor on-save action, not the formatter - or the formatter gains an analysis mode; say the cost.
4. Churn: every inferred-type change becomes a diff line and a merge-conflict site. Long stage types (`Derive<SignalCell<i32>, i32, i32>`) are the ones vilan hides behind opaque returns; say what `auto` writes there (the opaque form, `impl Flow<i32>`-like, or nothing).
5. Whether an `auto` annotation directs inference (as a written annotation does) or is output only. Output only is the safe reading: otherwise a stale `auto` changes what the body means.
6. Aim (4)'s opt-in: per package in `vilan.toml`, exported items only by default.

- 2026-10-05 (the owner): the integrator's six points are accepted as the paper's starting position: returns and module bindings first; a stale `auto` is refused by check/build with a `--fix` (lockfile reading); the rewrite lives in `check --fix` and an editor on-save action, not the syntactic formatter; say what is written for long stage types; `auto` is output only and does not direct inference; the opt-in is per package, exported items by default.
