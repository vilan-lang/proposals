# F14 — `to_lowercase_ascii` is not ASCII: the suffix lies, and the rename is `to_lowercase`

- status: OPEN — RULED 2026-08-29, building as Order 21's late ninth lane:
  the rename (`to_lowercase_ascii` → `to_lowercase`) PLUS genuinely-ASCII
  polyfill siblings (`to_lowercase_ascii`/`to_uppercase_ascii`, real
  ASCII-only implementations) beside the full pair, all four carrying doc
  comments that name the difference. Note the shape this gives the break:
  the name `to_lowercase_ascii` never stops compiling — it starts MEANING
  what it says — so the breaking half is behavioral, uncatchable by a
  rename diagnostic, and acceptable on the zero-app-caller census; the
  entry must say so loudly. std's five call sites migrate per intent,
  recorded per site.
- kind: bug
- area: std surface
- source: the owner's question, probe + transformer read, 2026-08-29

The owner asked why `to_uppercase` lacks the `_ascii` its lowercase sibling
carries. The probe answered with the opposite finding: BOTH are the host's
full-Unicode case mappings — `Intrinsic::StrToLowercaseAscii` lowers to
`native_method("toLowerCase")` beside `StrToUppercase`'s `toUpperCase`
(transformer.rs ~6023), and `"STRASSE-Ǳ".to_lowercase_ascii()` returns
`strasse-ǳ`, case-mapping U+01F1 as no ASCII operation could (while
`to_uppercase("Straße")` expands ß to SS, the full-Unicode tell on the other
side). The suffix is a name-lie in the F13 class — a promise of a narrower
operation than the one performed — and the docs inherit it.

The fix is the rename, not a new binding: `to_lowercase_ascii` →
`to_lowercase`, mirroring `to_uppercase`; the intrinsic's own name follows.
Family BREAKING (a spelling that compiles today stops), alpha-cheap, the
compiler naming the rename at the call site the way the `css`-keyword
renames did. Census 2026-08-29: five std callers (`string.vl` the
declaration, `markdown.vl`, `process/document.vl`, `process/http.vl`,
`process/build.vl`), one analyzer mention, the docs page — and ZERO app
callers (kolt's one use died with its hand-rolled mime table in the 0.38.0
migration; the website has none). Decide-and-record whether an
`_ascii`-narrow pair is wanted at all (no caller asks for one today; YAGNI
says no, and if one arrives it can be built honestly).
