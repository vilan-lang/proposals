# B185 — a `mut` rebinding of a trait-default closure parameter loses a CONTAINER type

- status: OPEN — pre-cut find (2026-09-01), the website migration's clean-build gate; FIX-NOW lane
- kind: bug
- area: Type system & the type solver
- source: vilan-website playground.vl:519 (`console_lines.set_with(|lines| { mut next = lines; … })`)

The discrimination, probe-proven with the Order 23 tip:
- `Signal::new(1)` → `set_with(|v| { mut w = v; w + 1 })` — CLEAN
- `Signal::new([1])` → `set_with(|values| { values.push(2); … })` —
  param INFERRED (the mutability refusal names it properly)
- plain closure, list param, `mut next = values` — CLEAN
- `Signal::new([1])` → `set_with(|values| { mut next = values;
  next.push(…) })` — `next` is UNKNOWN; `push`/`len` refuse on it.
  Same through `SignalCell::new` and with a B161 annotation.

So: the closure parameter's type arrives through the trait-default
dispatch (`set_with` has a default body on `Signal<T>`), and a `mut`
REBINDING of it grounds only when `T` is a scalar — a container `T`
(List, at least) loses through the rebind. The copy-update-return
idiom (`mut next = lines; …; next`) is exactly what `set_with` is
FOR, so this ships broken code in v0.40.0 unless fixed first — the
cut is held on it. Discriminate en route: required-method closures
(`set`? `sub`'s subscriber?) vs default-bodied; inherent
`SignalCell::update`'s closure; nested containers; `Map`.
