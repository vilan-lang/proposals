# B188 — an under-supplied type argument is ERASED, not inferred or refused: `fun read(h: Holder)` for `struct Holder<S>` accepts a `str` and prints `seven1`

- status: OPEN — papers lane's find (2026-09-01) on B184's path; LIVE MISCOMPILE with an ICE twin; FIX-NOW lane
- kind: bug
- area: Type system & the type solver
- source: proposal/trait-typed-fields.md's probes

`struct Holder<S> { … }` named as `Holder` with NO type argument in an
annotation position is accepted with the parameter erased: `fun
read(h: Holder): i32` takes a `Holder<str>` and prints `seven1`
through the declared `i32` return. The same shape ICEs ("please
report this program") when the erased parameter's method is a
body-less trait requirement. OVER-supplied arguments ARE checked —
only under-supply escapes. Same class as reactive-traits §8.1/§8.2
(argument substitution holes). Rule: an under-supplied type
application in any annotation position REFUSES, naming the missing
parameters ("`Holder` takes 1 type argument, 0 given: `Holder<S>`"),
unless a defaulted parameter exists; inference from context is NOT
attempted at annotations (B161's family: annotations are checked,
not inferred). The papers lane recommends fixing this hole BEFORE
B184's sugar is reconsidered.
