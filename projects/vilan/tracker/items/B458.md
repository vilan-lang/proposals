# B458 — `Context::clear<U>(self, body: || U): U`: `run`'s inverse — for the dynamic extent of `body` the context is NOT established: `get()` inside is refused by the coverage check exactly as outside any `run`, `get_safe()` answers `None`, and a closure created inside captures the cleared state, not the enclosing value

- status: OPEN — filed 2026-09-29 (the owner's item, from kolt's `reactive2.vl` sketch)
- kind: feature (context intrinsic; S)
- area: Type system & the type solver

**Why.** The sketch's tracked-read layer is a context: `derive`/`effect` open a tracking scope with `run`, and `Source::track()` reads it to register a dependency. Its `untrack` is this: code a derivation calls that must NOT subscribe (a callback it hands out, a helper that reads for logging), without opening a dummy scope. Because the threading pass CAPTURES the context into closures created within a `run`, a callback minted inside a tracking scope and invoked later would otherwise register with a scope that has already closed. `clear` is the one-line fix at the site that mints the callback.

**Shape.** An intrinsic beside `run`/`get`/`get_safe`: the threading pass rewrites `ctx.clear(body)` to `body()` with the hidden parameter set to its uncovered flavour — a strict `get` region inside is a coverage error (the same message as no `run` at all, naming the `clear`), and a `get_safe` region receives `None`.

Questions: (1) does a `run` INSIDE a `clear` re-establish (yes — nearest wins, as nested `run`s do); (2) the coverage diagnostic's steer when a `get()` is reachable only through a `clear`.

Related: `std::context`; `proposal/reactive-turns.md` §5.1 and `ambient-owner.md` §2.1 (`get_safe`); B146 (coverage refinement).
