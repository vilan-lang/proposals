# M18 — a function attribute marking a bundle boundary (`[split]` on `lucide_icon`)

- status: OPEN — owner-proposed 2026-09-01, exploratory ("I haven't pushed it to the extremes yet")
- kind: design
- area: Performance & footprint
- source: the owner, off the lucide reachability measurement (038: +984,510 bytes for string dispatch vs +1,525 for per-icon calls)

The owner's idea, verbatim intent: bundle splitting's key issue is
finding the boundaries; a function ATTRIBUTE could mark one — the
compiler sees calls to `lucide_icon` and arranges: fetch the separate
bundle first, then run the code. The string-dispatch icon lookup is
the motivating exhibit — the whole 1791-icon table moves off the
critical path and downloads on first use, restoring the by-name
component's ergonomics without its bundle cost.

What exists already: ROUTE-based splitting (app.chunks.json +
`Route_*.js`, fetched on navigation — the split fixture). So the
mechanism (chunk registry, fetch-then-run, retry on failed fetch) is
built; the novelty is USER-DECLARED boundaries at function
granularity instead of the router's structural ones.

The crux to push on — the call site's type. A call across the
boundary must await a fetch. Three doors:
(a) the attribute makes the function async — honest but infectious
    (views are sync; every caller awaits);
(b) suspense-shaped: a boundary function returning `View` returns a
    placeholder that FILLS REACTIVELY when the chunk arrives — no
    type change, and the reactive system is unusually well placed
    (a Source<View> that starts empty; the A32 trait work makes the
    return spellable);
(c) restrict `[split]` to already-async positions (event handlers,
    route bodies) — the router's existing trick, generalized.

Also to hold up under extremes: nested boundaries; code SHARED
between chunks (dedup into a common chunk vs duplicate — M16's
emitted-body comparison is reusable here); SSR (the server renders
synchronously, so the boundary must inline server-side and split
client-side only); HMR re-fetch semantics; and how chunks enter the
build record/stamp. A paper when the owner wants it pushed.

## Paper 2026-09-01 — proposal/bundle-boundaries.md: door (b), on shipped primitives

Recommended: the suspense-shaped door for `View` returns — the
boundary call returns immediately and fills reactively through the
already-shipped `View.when`; sync signature throughout; probe P8
built and ran it. Door (a) REFUSED on a hard fact (view render
parameters are declared `sync`; an async boundary would not compile
at any reactive mount). Two extremes BREAK: nested boundaries (M20 —
the registry's by-value snapshot; fix independently valuable) and
"shared goes eager" (measured 18 KB → 959 KB when a second call site
shares the lucide table; recommend duplicate-by-default with M16's
comparator reporting the mass). Lucide repriced under a boundary:
18 KB eager vs 953 KB whole vs 13 KB per-icon. Nine determinations,
seven owner questions; Q7 asks whether M20 goes first — yes.
