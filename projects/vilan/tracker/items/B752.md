# B752 — `unwrap_or_else(|| &0)` over an `Option<&i32>` is refused as `a view cannot escape its scope`, with nothing telling the author to write `|| 0`

- status: open
- kind: diagnostic (a correct refusal that gives no way forward)
- area: the view-escape check's message for a closure body that returns a `&literal` or `&local`

The refusal is probably right (the closure's `&0` would be a view of its own temporary), but `unwrap_or(&0)` beside it is ACCEPTED (B649: the fallback is evaluated in the caller), so the author who moves from one to the other gets a memory-model error for what looks like the same thing. Say what to write: when the escaping view is of a literal or a fresh value and the expected type is the generic's `T` at a view, name the by-value closure (`|| 0`) if that types, or `unwrap_or(&0)`. Check first whether `|| 0` does type there; if not, that is the real gap.
