# B605 — A generic function returning `dyn Pipe<Option<P>>` built from `value.derive(|v| v)` is refused natively — "the `rust` backend does not emit a value of an unbound generic type parameter (parameter 1 of `pipe_of`) yet" — while the same body at a concrete type builds and runs; it is why a mirrored store's `states()` (and any `TransientSource::states()` over a generic) does not build natively

- status: OPEN — filed 2026-10-10 (store-50's find, Order 50)
- kind: native: a generic dyn Pipe (S–M)
- area: Native backend

Repro: `sweeps/order50/store-50/finds/generic-dyn-pipe-native/main.vl` — `fun pipe_of<P>(value: dyn Source<Option<P>>): dyn Pipe<Option<P>> { let pipe: dyn Pipe<Option<P>> = value.derive(|v| v); pipe }`, called at `P = str` and observed with `effect`: JS prints `-` then `x`; `vilan run --backend rust` refuses at the call. The same function written at `str` builds and prints the same on both backends (the `combine` form too). Met building A153 S2's `RemoteStoreSome::states()` (`impl RemoteStoreSome<type P> with TransientSource<P, RpcError>` in `std::rpc::mirror`, whose pipes are `combine((leased, told)).derive(..)`): the JS pin is `reactive_channels::a153_s2_a_remote_handle_tells_pending_ready_absent_and_failed_through_states`; the native differential probe leaves `states()` out until this is fixed (it should then gain one). Likely the dyn-pipe construction's closure types are not substituted at the instance. Sizing S–M; vilan-rust / mono.
