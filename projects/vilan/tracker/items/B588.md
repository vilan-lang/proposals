# B588 — a value whose type is a parameter bounded `(2..: PartialEq)` is not itself `PartialEq` — `values == other` is refused "`==` on `T` needs `T: PartialEq` … `T` is unbounded" — although std now provides `impl type T: (2..: PartialEq) with PartialEq` and every instantiation of the parameter meets that blanket's subject bound

- status: OPEN — filed 2026-10-08 (solver-48's find, Order 48)
- kind: design (language question; S)
- area: Type system & the type solver

B173 (RULED) makes an abstract value's DECLARED bounds the only answer, never an impl: a blanket could be outranked by a more specific impl at instantiation. A tuple bound's CONTAINMENT in a blanket's subject bound (`(2..: PartialEq)` inside `(2..: PartialEq)`) is a proof about every instantiation, which is the case B173's reasoning does not cover — but `impl (i32, i32) with PartialEq` written by a user would still outrank the blanket at that instance. A ruling first: does a tuple bound's containment count as declared (then `tuple_bound_violations`' containment test answers the bound check for the abstract value, and the dispatch stays per instance)? Sizing S once ruled; solver.

- 2026-10-09 (Order 48 sweep): the integrator's recommendation: YES, a tuple bound inside a blanket's subject bound is a declared bound under B173 (otherwise the new tuple blankets are unusable from generic code). Awaiting the owner.

- 2026-10-09 (the owner): RULED: YES - a tuple bound inside a blanket's subject bound is a declared bound under B173, so an abstract `T: (2..: PartialEq)` value is `PartialEq`. Order 49 solver.
