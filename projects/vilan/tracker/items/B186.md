# B186 — `fun f(x: Trait)`: the parameter-position trait annotation as an implicit generic

- status: OPEN — owner-ruled WANTED 2026-09-01 ("useful for the same reason `let x: Trait` is. Is this supportable?"); Order 24 lane
- kind: design
- area: Type system & the type solver
- source: the reactive paper's §7.3 (unbuilt since Order 23), now asked for directly

Supportable, and the semantics are settled by the paper: `fun f(x:
Trait)` reads as `fun f<T: Trait>(x: T)` — an implicit generic
parameter, monomorphized per call like any other, so `x` keeps its
concrete type inside the body exactly as B161's `let` does. NOT
B184's field rule (one instantiation program-wide) — a parameter is
per-call by nature. The paper's cost concern (silently-generic
functions → one emitted copy per type) is largely answered by M16:
bodies that don't mention `T` share one copy; the lane measures the
residue on the estate. Also resolves the `Optimistic::over(signal:
Signal<T>)` signature; the stored FIELD still needs the arity change
the owner accepted. Refusal wording today should steer to the
sugar once it exists. Return position and nested spellings
(`List<Trait>`) stay refused — say so in the spec sentence.
