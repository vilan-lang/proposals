# G24 — `const let` and `const fun`: compile-time-known CLOSURE bindings and declaration-gated const functions, so `const let add = |a: f64, b: f64| a + b;` and `const fun scale_step(rem: f64): |f64| Length { |n: f64| { Length::rem(rem * n) } }` + `const let space = scale_step(0.25);` are expressible and `space(2f)` works both inside later `const` expressions and at runtime. Today (probed on 9b22ec36): a closure RESULT is refused by design ('a `const` result must be plain data; this evaluates to a closure' — const-eval.md §1, §8.1), a `const` expression cannot read a runtime binding at all ('`space` is a runtime value; a `const` expression reads only compile-time-known bindings'), `const let x = e;` parses as the `const` prefix over a `let` STATEMENT and dies in the evaluator with a RAW message ('statement node in expression position: ConstVariable(Variable { .. })' — a leak to row), and `const fun` is a parse error ('found `fun` expected an expression'); only the immediate application `const scale_step(0.25)(4f)` works, because its result is data. The design: (1) `const let NAME = EXPR;` evaluates at build time like `let NAME = const EXPR;` but admits a CLOSURE result whose captures are const data (transitively) — const-known, so later const expressions call through it, and EMITTED as a snapshot for runtime code: the closure's own JS with its captured environment bound to literal values (the evaluator's `Value::Closure` is body + env scope, §10.7 — lower env as literals); (2) `const fun` checks its body const-evaluable AT THE DECLARATION — a spanned error naming the runtime capability it reaches — instead of at a distant call site; NOT a coloring requirement: plain `fun`s stay const-callable (§1's Zig-shaped rule stands), `const fun` is the opt-in guarantee

- status: OPEN — filed 2026-09-14; RULED 2026-09-14 (R1–R3 as recommended; R2 with a steering diagnostic)
- kind: design
- area: Macros & const

Grammar (parsing.rs): `const let NAME[: T] = EXPR;` and `const fun NAME(..)[: T] { .. }` at module level (and `const let` locally per R3); `const mut` refused with a curated row ('a compile-time value has no runtime mutation'). Evaluator (`const_eval.rs`): `ConstValue` gains a closure variant (the closure node's id + its env as const values, closures nested transitively); `Program::const_results` folds a `const let` binding as it folds `let x = const e` today, so `walk_entity_inner`'s first arm hands the transformer the snapshot; `check_value_escapes` (§8.1) still refuses an R (emit-reaching) closure as a result — pure closures only; a captured runtime value is the existing 'reads only compile-time-known bindings' refusal at the capture. Transformer: lower a closure snapshot as the closure's emitted function with its env bound to literals (an IIFE over the captures, or substitution when every capture is a literal); the snapshot's identity is fresh per emission (vilan has no reference equality — fine). `const fun`: the analyzer runs the body through the const capability check at the declaration (the call graph's R-membership + the runtime-binding rule) and reports there, spanned, naming the capability (`fetch`, `dom`, a `Shared` write, ..); the function is otherwise an ordinary `fun` (callable at runtime with runtime args). Diagnostics ledger rows: the raw `ConstVariable` leak retired; `const fun` body reaching a runtime capability; `const let` capturing a runtime value; `const mut`; `const let` in a type-parameter-dependent body (§9.1's rule, explicit form). Pins: `const let add = |a, b| a + b;` then `const add(1f, 2f)` folds to `3` and `add(x, y)` at runtime calls the snapshot; `const fun scale_step` + `const let space = scale_step(0.25)` + `let s = const style().padding(space(2f))` folds the padding to `0.5rem` and `space(n)` at runtime is one emitted closure with `0.25` baked; a `const fun` reaching `fetch` errors at the declaration; a `const let` capturing a runtime `let` errors at the capture; the §8.1 R-closure pins stay red; the corpus differential (§9.7) reports no change for programs that write neither keyword. Docs: const-eval.md gains §11 (`const let`/`const fun` — the closure result and the declaration gate; §1's 'result must be plain data' amended to 'plain data, or a closure over plain data'); the language reference's const page. Paper-sized? Small: the evaluator already models closures internally (§1: 'internal use during evaluation is fine'); the new work is the snapshot lowering and the two grammar rows — a lane, not a paper, once R1–R3 are ruled.

**RULING 2026-09-14 (owner):** R1 accepted — a `const fun` folds only where a `const` context reaches it (plus §9's inference for pure data bindings); no per-call-site folding. R2 accepted — explicit `const let` is REQUIRED for a closure-valued compile-time binding; inference never admits closure results — "but maybe the diagnostic could push them towards the correct form": so the existing refusal '`space` is a runtime value; a `const` expression reads only compile-time-known bindings' gains a STEER when the binding's initializer would evaluate (a closure, or data inference declined) — "declare it `const let space = ..` to make it compile-time-known" — with a quick fix that rewrites the declaration; the same steer on 'a `const` result must be plain data; this evaluates to a closure' at a `let x = const ..` site ("write `const let x = ..`"). R3 accepted — local `const let` inside function bodies, §9.1's type-parameter-dependent rule as the author's responsibility. Companion: B340 (call-operator overloading) covers the DATA-shaped callable (`const let space = Scale::new(0.25)` is a plain struct result today); G24 stays for genuine closures.
