# B695 — `str::substring` that splits a UTF-16 surrogate pair diverges between the backends: `"😀".substring(0, 1)` is half a pair on JS and the whole emoji natively, while `len()` is 2 on both

- status: OPEN - filed 2026-11-02 (lane std-56's find)
- kind: bug (std str; backend divergence on surrogate halves)
- area: Standard library (strings)

The native backend's `substring` must answer what JS answers at a surrogate boundary (the language's string is UTF-16-indexed: `len()` says so), i.e. a lone surrogate half, which the native str cannot hold as UTF-8 - or the language rules that a cut inside a pair is refused/rounded on BOTH backends (a spec question: strings.md). Rec: find every `str` operation that takes a UTF-16 index (`substring`, `char_at`, `index_of`'s answers, slicing) and pin them on the differential at a surrogate boundary; rule the semantics once (rec: a cut inside a pair answers U+FFFD-free: the half as JS does is unrepresentable natively, so the honest rule is the code-point rounding on both, which changes JS).
