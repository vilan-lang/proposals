# B294 — `_` as the ANONYMOUS TYPE BINDER: `impl Source<Option<_: Source<type U>>>` for today's `type _: Source<type U>` — the pattern wildcard's spelling (`Some(_)`, `let _`) in the impl-subject position. Today `_` in a type position is refused 'cannot find type `_`' and `_: Bound` is a parse error at the `:` (only the `type` keyword reaches `parse_type_binder`, parsing.rs:4430/4495), while `type _` and `type _: Bound` both compile — so the anonymous binder exists and only its spelling is heavy

- status: OPEN — the owner's ask (2026-09-11); Order 32 (smalls-32)
- kind: feature
- area: Type system & the type solver

**Today.** `parse_type_atom` (parsing.rs:4430) routes the `type` keyword to `parse_type_binder` (:4495: `type NAME (: A + B)?` → `Node::TypeBinder(name, bounds)`), and nothing else in a type position may carry a bound. `_` is an ordinary identifier there, so `impl Source<Option<_>>` fails name resolution ('cannot find type `_`') and `impl Source<Option<_: Source<type U>>>` fails to parse at the `:` ("found ':' expected ',' or '>'", then a cascaded '`Option` takes 1 type argument, 0 given'). `impl Source<Option<type _>>` and `impl Source<Option<type _: Source<type U>>>` both compile — the anonymous binder is already a thing, spelled with the keyword.

**The change.** In `parse_type_atom`, an `_` identifier in type position, optionally followed by `: bounds`, parses as the SAME `Node::TypeBinder("_", bounds)` the keyword form produces — one node, one analyzer path, no new semantics. `type _` stays accepted (the formatter canonicalises it to `_` — or the other way; pick the wildcard, it is what the owner asked for and what `Some(_)` reads as). A NAMED binder keeps its keyword (`type U` — the keyword is what says 'this introduces a name' in a position that otherwise reads a type).

**Check before building (a pin either way):** what two anonymous binders in one head mean today — `impl Pair<type _, type _>` — are they ONE parameter named `_` (an aliasing bug the wildcard must not inherit) or two fresh ones? `Some(_, _)` binds nothing twice; the type form must be fresh each time. Also: a bare `_` OUTSIDE an impl head (`let x: List<_> = ..`, an inference placeholder in an annotation) is a DIFFERENT feature — out of scope here; the refusal it gets today ('cannot find type `_`') should instead say what `_` is for after this lands (a curated message, one row).

**Estate.** spec/grammar.md:249 and spec/types.md:318 document the keyword form — add the wildcard beside it; the EBNF gate (`grammar_ebnf`); `vilan fmt` prints the chosen canonical form (a formatter pin); the TextMate grammar needs nothing (`_` is not a keyword; E161 is the highlighting item for these heads). Pins: the owner's exhibit with `_:`; the two-wildcards-fresh pin; `type _` still accepted; the `let` placeholder refusal text.
