# B671 — `vilan fmt` declines a file with a `match` statement whose arms have values (`match … { … };`), and can name the wrong line

- status: OPEN — filed 2026-10-22 (kolt's task table: a map kept in step with `insert`/`remove` arms)
- kind: formatter (S)
- area: LSP & tooling

```vilan
import std::hash_map::HashMap;

fun note(held: HashMap<i32, str>, id: i32, found: Option<str>) {
	match found {
		Some(let text) => held.insert(id, text),
		None => held.remove(id),
	};
}
```

→ `declined g.vl:7  reprinting it would have changed the code at this line, so the reprint was thrown away (the formatter's own safety net): '};'` (v0.52.0). `vilan check` accepts the file.

The statement form, a `match` whose arms give values that are thrown away with `;`, seems not to survive the reprint. The safety net catches it, so nothing is broken, but the file is left unformatted.

In a 400-line file (kolt `src/task_table.vl` at commit ee88ab1), the same construct was reported at line 6, `import std::compare::Ordering;`, far from the `match` at line 120. Only cutting the file down found the real place.

Recommendation: print the statement form as written (keep the `;` after a `match` in statement position). Separately, a decline should name the first line whose reprint differs, not an earlier one.
