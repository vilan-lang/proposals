# M88 — DEVIRTUALIZE `dyn Trait` when the program coerces exactly ONE concrete type into it: the `(value, vtable)` pair collapses to the bare value and every dispatch through it becomes the direct (monomorphized) call, so a `dyn Trait` FIELD costs nothing until a second implementor actually reaches it — a build-time optimization only; the analyzer, the LSP and the types are untouched

- status: OPEN — filed 2026-09-27 (the owner); a rec, not a ruling; paper-sized (a section of trait-objects.md) before a lane
- kind: perf (design; build-time optimization)
- area: Performance & footprint

**The idea.** `dyn Trait` is the honest spelling for a field whose implementor the author does not want to name (A124's `dyn Source<T>`, B4's heterogeneous containers), and today it always costs the pair: `note_dyn_coercion` (analyzer.rs:35576) records every coercion site into `dyn_coercions: HashMap<Id, (TypeId, Id, Vec<TypeId>)>` — the expression, the concrete type erased, the trait, its arguments — and the transformer builds `(value, vtable)` at each (`emit_vtable`, transformer.rs:9397, keyed `(trait, type key)`) and dispatches through the table's slot. When the WHOLE PROGRAM erases exactly one concrete type `T` into `dyn Trait<Args>`, the table has one possible occupant: the pair is redundant, and every slot call is `T`'s impl. trait-objects.md §0 measured that direction once — monomorphization beat erasure by 14–18 % — so the win is known, and the owner's framing is the right one: `dyn` stays the AUTHOR'S spelling and the compiler tightens it to the variant when it can, or keeps the runtime coloring when it cannot. No cliff in meaning, only in cost, and the cost cliff is the second implementor arriving, which is exactly when a vtable is earned.

**Shape (rec).** A whole-program pass between analysis and emission, per LEG (each entry is its own program: the client may see one `Source` implementor where the server sees three): (1) the census — group `dyn_coercions` by `(trait, resolved args)` into the SET of resolved concrete type keys; (2) a key whose set has exactly one member is DEVIRTUALIZED: its coercion sites emit the bare value (no pair, no table), and every dispatch on a receiver of that `dyn` type emits the direct call to `T`'s impl (the monomorphized path the concrete receiver already takes); (3) everything else is unchanged. The analyzer keeps `Type::Dyn`, the LSP shows `dyn`, hover and completion are the trait's — nothing about the language moves, which is what makes this an optimization and not a feature.

**What has to be true (the paper's questions).** Q1 COMPLETENESS of the census: every way a `dyn` value can come to exist must be a coercion the analyzer recorded — B430's element-wise tuple erasure, B412's generic-parameter erasure, `combine`'s `(U in T: dyn Source<U>)` position, a closure returning `dyn`; any door that MINTS a dyn without a record (an extern answering a `dyn`? a Wire/Json decode into a dyn — is `dyn` Wire at all? a `dyn` crossing an rpc boundary; bindgen) makes the census wrong and the direct call a MISCOMPILE, so the pass must enumerate the doors and refuse to devirtualize a key that any un-recorded door can reach. Q2 GENERICS: coercions inside a generic body are recorded once and resolved per instantiation (`emit_vtable` resolves at emission) — the census must run over RESOLVED keys after mono, or `dyn Source<U>` for two `U`s is one bucket with two occupants that are really one each. Q3 the DROP path: §8's drop-glue for a resource behind a vtable — a devirtualized dyn drops as `T`, which is the cheaper and the correct path, but the drop plan must see the same decision the emitter took (one table, both readers). Q4 OBSERVABILITY: is a pair ever distinguishable from a bare value by a program — `__clone` over the pair, identity, a `dyn == dyn`? If no downcast and no reflection exist, none; the differential (the corpus's dyn goldens run both ways, stdout identical) is the proof, red-first on a planted second implementor. Q5 the NATIVE backend (F1 S1a): Rust's `dyn` vs the emitted enum/struct — the same census can devirtualize there, or the Rust compiler already does; measure before building. Q6 a `[dyn]`-style opt-out is NOT wanted (the author cannot want the slower shape), but a `VILAN_DEVIRT=0` build switch for the differential is.

**Beyond one.** Two-to-N occupants could become an ENUM dispatch (a tag and a `match`, the closed-world form) instead of a table — a second step, priced separately; the one-occupant collapse is the whole of this item.

**Measure.** kolt's client leg and the A124 exhibit under callgrind, `dyn Source<T>` at the model's fields before and after; the paper's §3.3 method. Sizing M (the census S; the emitter's two seams — coercion site, dispatch site — and the drop plan's agreement M; the differential and the door enumeration are the work). Perf lane, after the paper's Q1 door list is written; not before.
