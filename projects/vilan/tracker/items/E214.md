# E214 — E202 as built places the `>` but leaves the CURSOR AFTER it, and typing `>` then doubles it: the server answers `<` through `onTypeFormatting`, and an LSP text edit cannot position the caret or register the placed character as an auto-closed pair, so VS Code's native overtype (typing the closing character steps over the one it auto-placed) never engages. The owner: 'natively in VS Code the closing pair is placed after the cursor and typing that pair steps the cursor over the auto-placed one — can you hook into that?'

- status: OPEN — filed 2026-09-21 (the owner's report, mid-Order 39, on E202 as landed in editor-39)
- kind: editor
- area: LSP & tooling

YES, and only from the CLIENT. VS Code's overtype is a property of its auto-closing machinery: it remembers the closing characters it inserted itself (per position, per editor) and, when the user types one of them at that position, moves the caret instead of inserting. A server edit is not 'itself', so no overtype and no caret control. Three ways to get the native behaviour, best first:

(1) **Let VS Code place it, but only where the server says a type context is** — a `languageConfiguration.autoClosingPairs` entry for `<`/`>` cannot be conditional, BUT the extension can register a `type` command override (`vscode.commands.registerTextEditorCommand('type', …)`, the hook Vim-emulation extensions use): on `<`, ask the server (the existing `on_type_edits` / `opens_a_generic_list` answer, exposed as a cheap request), and if it says 'type context' call the built-in `default:type` with `text: '<'` AFTER temporarily enabling the pair — simplest form: insert `<>` via `editor.edit` and set the selection between, then ALSO remember that position in an extension-side map so a subsequent `>` typed at it is swallowed by the same `type` override (that map IS the overtype, reimplemented; it must clear on any other edit/selection move, which `onDidChangeTextDocument`/`onDidChangeTextEditorSelection` give). Cost: the `type` override intercepts EVERY keystroke in vilan files (Vim extensions coexist badly; the override chain is last-registered-wins — document the conflict and make it a setting, default on).
(2) **Use VS Code's own pair by making the pair itself smarter**: `autoClosingPairs` entries take a `notIn` scope list only — no positive context — so the pair would fire on `a < b`. UNLESS the TextMate grammar scopes a type-position `<` differently from an operator `<` (e.g. `punctuation.definition.generic.begin.vilan` vs `keyword.operator.comparison.vilan`) and the pair is declared with `notIn` naming the operator scope. The grammar cannot decide type-vs-operator perfectly (it is a regex), but the E202 heuristic the server uses (the token BEFORE `<` is a type name / `fun name` / `impl` / a `::` path head) is expressible as a lookbehind in the grammar for the common cases. Then VS Code places `>` natively, overtype works natively, no `type` override, no server round trip — and the server's `onTypeFormatting` becomes the fallback for the cases the grammar misses (or is removed). REC: (2) FIRST — it is the native path the owner asked for and costs one grammar rule + one config entry + grammar_sync scope pins; (1) only if the grammar cannot carry the distinction well enough (measure over std/kolt: how many `<` tokens does each rule misclassify).
(3) Leave the server edit and accept the doubled `>` — no.

Pins: `vscode_extension` — the pair fires after a type name / `fun f` / a `::` path head and NOT after an identifier in expression position (`if a <`), per the grammar's scopes (`grammar_sync` scope pins for both `<`s); the E202 server pin stays as the fallback's guard. Non-vacuity: with the operator scope removed from `notIn`, the comparison case fires.

- 2026-09-22 (Order 40 sweep): STOPPED by editor-40, PREMISE FALSE — `autoClosingPairs.notIn` takes only string/comment/regex and decides on the token LEFT of the caret (an identifier for `List<`, whitespace for `a < b` — both `Other`), so no grammar scope can separate them (the grammar ALREADY scopes them apart: `punctuation.definition.generic.begin.vilan` vs `keyword.operator.vilan`); editor-39 had pinned exactly this (`e202_the_angle_pair_surrounds_but_does_not_auto_close`). The priced alternative is E222 (a client-side `type` override behind a setting, with the server standing down for `<` when the client declares the capability) — a RULING.
