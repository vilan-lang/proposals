# F129 — Natively an argument read through a `Shared` view is copied out of the cell when it is evaluated, so a LATER argument that writes the cell is not seen by the callee — `has(cell.read().items, grow(cell))` and `cell.read().probes.contains(mark(cell))` (a user-hashed key) print `false` natively and `true` on JS, silently

- status: OPEN — filed 2026-10-10 (native-50's find, Order 50)
- kind: miscompile (native; S–M)
- area: Native targets & rendering

The JS backend evaluates the receiver/argument to a reference, then the later argument writes through the same cell, then the callee reads the written value. Natively the `read_with(|view| view.items.clone())` copy is taken in argument order, before the writing argument runs. F123 fixed the shape for std's keyed lookups over a std-hashed key (the receiver is a view of the cell borrowed AFTER the key is evaluated, as F114's intrinsics); every other call keeps the early copy. Fix: in the call emission, when an argument reads through a `Shared` view (or a boxed binding) and a later argument may run code, settle the later arguments first (they are hoisted already when `borrows_a_cell`) and take the copy last — the order spec §6.9's native note states for views. Expected on both: `true`, `true`. Sizing S–M; vilan-rust's call seam.
