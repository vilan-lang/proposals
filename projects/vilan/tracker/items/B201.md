# B201 — `[derive(…)]` on a type declared inside an inline `mod` generates its impl at file top level

- status: OPEN — cascade-25 lane's find (2026-09-01)
- kind: bug
- area: Type system & the type solver
- source: lane cascade-25 (hit building B190's fixture)

`mod shapes { [derive(PartialEq)] enum Kind { … } }` → `cannot find
type 'Kind'; import it first (import pkg::shapes::Kind;)` ×2 plus two
generated-code follow-ons; `[derive(Debug)] struct Dot` in a mod the
same. The derive's generated items land at the FILE's top level,
where the type is out of scope. Fix: generate into the declaring
module's scope (the expander knows the item's owner), or qualify the
subject by its module path in the template. Pin both derive kinds
inside a mod; B190's fixture drops its hand-written impl when this
lands.
