# B765 — JS: a writable view of a tuple element that is itself a tuple (`&mut t.1` where `t.1` is `(i32, i32)`) is a copy, so a write through it is lost; native is correct

- status: open - filed 2026-11-26 (lane `keys-s1c`'s find; pre-existing on `next` @e43933b0, no key involved)
- kind: miscompile (JS: a checked program silently loses a write)
- area: crates/vilan-core/src/transformer.rs (tuples store flat; views of a nested tuple)

Repro:

```
fun bump(p: &mut (i32, i32)) {
	p.0 += 1;
}

fun main() {
	mut t = (1, (2, 3), "x");
	bump(&mut t.1);
	print(t);
}
```

Native prints `(1, (3, 3), "x")`. JS prints `(1, (2, 3), "x")`: a tuple is stored flat, so a nested tuple has no storage of its own, and the view is emitted as `t.slice(1, 3)`, a copy the callee writes into.

The same root through a generic accessor, which the checker cannot see because the element type is a parameter:

```
import std::tuple::{ Tuple, TupleKey };

fun at<T: (2..), U>(t: &mut T, k: TupleKey<T, U>): &mut U borrows t {
	t[k]
}

fun bump(p: &mut (i32, i32)) {
	p.0 += 1;
}

fun main() {
	mut n = (1, (2, 3));
	let (n0, n1) = n.keys();
	bump(at(&mut n, n1));
	print(n);
}
```

Native `(1, (3, 3))`, JS `(1, (2, 3))`.

What B711 S1c did about its own surface: a view of, or a write into, a tuple-typed element reached through a tuple key written directly (`&mut t[k]`, `t[k].0 = v`) is refused by name; reading it and writing it whole work. The field form `&mut t.1` and the generic instance above are not refused and are wrong.

Options: (a) give a view of a nested tuple the `(base, offset)` form scalars have, so writes land in the flat storage (the complete fix; JS emits generics per instantiation, so the generic case can take it at the instance); (b) refuse a writable view of a tuple-typed tuple element on JS by name, at the instance for generics, as S1c does for keys. Rec: (a); (b) first if (a) is large, because a refusal beats a lost write. Size M for (a), S for (b).
