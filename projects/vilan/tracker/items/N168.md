# N168 — `vilan run` of the INSTALLED toolchain reads std from the nearest vilan checkout when the program sits inside one — a probe under `vilan/.claude/worktrees/lang-50/target/` ran v0.47.0 against the worktree's edited std ("found '[' expected a type" at the new `impl [type T: PartialEq; const N]`), and a debug build reads `crates/vilan-cli/../../vilan/std` at run time, so editing std mid-suite poisons a running `nextest`

- status: OPEN — filed 2026-10-10 (lang-50's find, Order 50)
- kind: tooling question (XS)
- area: Toolchain

Two effects a lane can trip over: (1) a 'base compiler' probe written inside a checkout is not a base probe; (2) std edits during a running suite change the std every subsequently spawned compile reads (the corpus and native legs all failed for one in-flight std edit). Neither is necessarily wrong — a dev build reading the tree's std is the point — but the lane mechanics should say so (probes for the base run from the scratchpad, outside any checkout; no std or docs edits while a suite runs). Sizing XS (docs: AGENTS.md / the Mechanics).
