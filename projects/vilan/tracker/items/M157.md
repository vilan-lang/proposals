# M157 — After M144 a std item's id is one id in both shapes, but a PACKAGE item's id is not: the std-only prefix world resolves std (minting 621 entities on the repro's std set) before the package's nodes mint, the canonical path mints them before its one resolve - so the native backend (names `name_<id>`) emits `two_10238` canonically and `two_10859` over `VILAN_STD_PREFIX=on` for one program, while the JS is byte-identical

- status: OPEN - filed 2026-10-15 (incr-53b's find, Order 53)
- kind: determinism (S) - the std-prefix shape's package ids
- area: Performance & footprint

Measured on the M144 repro package (`std::path::basename` beside two sibling modules): canonical `b` module node Id(10235), over the prefix Id(10856); the gap is the entity mints of std's own `resolve_world` (prelude bindings, impl namespaces, post-settle mints). M144 could not close it: exact cross-shape equality needs the canonical path to resolve std ALONE before the package mints (std-prefix.md §4.2 hardened from guard to language rule), or the native backend to name items without ids (a content suffix). Nothing a user sees moves (the four differentials and the corpus hold over the prefix; the native differential compares stdout, not bytes), and the CLI's default is the canonical shape, so no output changes today. Rec: own it under §4.2's hardening (the rule the paper already recommends after a release without refusals) - then the std-prefix world and the canonical world are one layout and the native bytes agree across shapes; until then a program built natively under `VILAN_STD_PREFIX=on` is reproducible but not byte-equal to its canonical build. The in-process pin `prefix_roundtrip_native::m144_a_package_with_siblings_names_std_the_same_over_a_loaded_prefix` compares std's names across shapes and the package's between the built and the loaded prefix only.
