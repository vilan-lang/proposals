# E106 — the language server slows down over a session

- status: OPEN — the owner's report, 2026-08-29 evening; measure first
- kind: bug
- area: LSP & tooling
- source: the owner's kolt hand-migration session

The owner observes the LSP "slowing down quite a bit" over a working
session. Prime suspect, already on the record: every analysis LEAKS its entry
text and AST deliberately (the known `leak_measurement`-bounded leak the
perf harness documents — "a 25 KB file at 2000 keystrokes is hundreds of
megabytes of deliberate garbage"), which a long editing session accumulates
without bound. Second suspect: S5's per-request raw re-parses (semantic
tokens + completion share one parse per request — per-REQUEST cost, not
growth, but additive). The item: instrument first (a session-length memory
and per-request latency trace against a scripted editing session), attribute
the growth, then design the reclaim (bounded retention of analyses, or the
fix M11's tally work implies). Cross-refs: M11 (retentions invisible to the
tally), M14 (the std cost angle). THE OWNER'S DATAPOINT (2026-08-29 late): "Vilan: Restart Language
Server" does NOT fix the slowness; restarting VS Code DOES. That moves
the prime suspect to the EDITOR SIDE: either the extension host's client
state accumulates (providers/disposables re-registered per restart, a
leaking middleware, a diagnostics collection growing), or the restart
command does not actually replace the server process (the stale-inode
pattern already on record for this extension). The per-analysis server
leak stays a suspect only if the restart command is a no-op. The
investigation now starts at editors/vscode: instrument what the restart
command really does, then attribute.
