# B161 — a trait annotation as a checked constraint: `let count: Signal<i32> = SignalCell::new(1)`

- status: OPEN — owner-proposed 2026-08-29 with the semantics stated
  exactly; design, paper-shaped with A32
- kind: design
- area: Type system & the type solver
- source: the owner's Signal-trait discussion, 2026-08-29

The proposal: a TRAIT written as a binding's annotation is not a type and
not a `dyn` — it is a CONSTRAINT on the inferred value type. `count`'s
type is still the impl's (`SignalCell<i32>`); the annotation (a) checks
that type implements the trait and (b) feeds inference (`Signal<i32>`
supplies `T = i32` to the initializer — the owner's "simple constraint
for its value's inference"). Two branches must still unify to ONE
concrete type by ordinary inference BEFORE the trait is consulted:
`if c { SignalCell::new(1) } else { SignalCell::new(2) }` is legal;
`… else { OtherSignal::new(2) }` fails at branch unification with the
ordinary mismatch, never a trait error. This is exactly the bounded-
generic rule ported to bindings — one concrete type per binding, checked
wide, kept narrow (the `satisfies` shape).

What it deliberately touches: the trait-is-not-a-type refusal (shipped
recently — `let x: Display = bag;` is an ERROR today, reported at the
annotation) is NARROWED, not repealed: the let position becomes the
checked constraint; a PARAMETER `v: Signal<i32>` plausibly becomes sugar
for an anonymous bound (`fun f<V: Signal<i32>>(v: V)` — the spelling the
language already has); RETURN and STRUCT-FIELD positions stay refused —
a field needs a real type, and storable trait values without `dyn` is
B157's recorded residual, not this feature. The paper states each
position's fate and the diagnostic's new wording at the still-refused
ones (which should now STEER to the generic spelling).
