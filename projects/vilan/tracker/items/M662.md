# M662 — `std::db` takes statement parameters as `List<any>`, so a value SQLite cannot bind (an `Option`, a struct) type-checks and then throws at run time; on a server the throw kills the RPC's task and the client never hears back

- status: OPEN — filed 2026-10-20 (kolt's board: `create_task` bound `Option<u53>` for a nullable `status_id`)
- kind: robustness / API typing (std::db; S–M)
- area: std

`db.vl` declares `Statement::run`, `all` and `first` (and the `statement_*` externs under them) over `parameters: List<any>`. Whatever goes in the list type-checks. At run time node:sqlite binds what it can and throws on the rest:

```vilan
import std::db::Database;

fun main() {
	let db = Database::open(":memory:");
	db.prepare("CREATE TABLE t (n INTEGER)").run([]);
	let maybe: Option<i32> = Some(1);
	// Type-checks: parameters are `List<any>`.
	db.prepare("INSERT INTO t (n) VALUES (?)").run([maybe]);
	print("inserted");
}
```

`vilan run` → `Error: Unknown named parameter '0'` (the `Option`'s representation is an object, read as named parameters). In kolt, with the `Option` eighth in the list, node:sqlite answered `TypeError: Provided value cannot be bound to SQLite parameter 8`.

Where it hurts most is an `[rpc]` body: the throw surfaces as `unhandled task error (spawned in accept_socket)` in the server log, and the call never answers. The client's awaited call hangs with no error to show, so the user sees a form that does nothing.

`Option` is the natural way to write a nullable column, so this is easy to reach for. The same goes for `bool`: kolt writes `done then 1 else 0` by hand.

Recommendation:
- Type the parameters. A `SqlValue` trait (or enum) implemented for `str`, the integer and float types, `bool` (as 0/1), `Bytes`, and `Option<T: SqlValue>` (`None` as NULL). Then `run([..])` takes `List<SqlValue>` (or a variadic tuple), and a struct or nested `Option` is a compile error at the call.
- Until then, the extern could convert at the boundary: `Option` to NULL or its value, `bool` to 0/1. It could also throw a message naming the parameter's index and Vilan type, not node's.
- Separately, an `[rpc]` whose body throws should answer the call with an error, not leave it pending (see the server's `accept_socket` task).
