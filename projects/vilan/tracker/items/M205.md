# M205 — `std::image` cannot decode AVIF: `sniff` answers `None` and `decode` answers `Err("not a PNG, JPEG, WebP or GIF")`, so a server cannot make avatar copies of an AVIF upload

- status: OPEN - filed 2026-11-10 (kolt)
- kind: feature gap (std::image; M)
- area: Standard library / image

M185 built `std::image` to read four formats: PNG, JPEG, WebP and GIF. The module comment, the `Format` doc ("The four formats `decode` reads"), std/image.md and `proposal/image.md` all say so. `vilan-image/Cargo.toml` turns on only `image`'s `png`, `jpeg`, `gif` and `webp` features, and `sniff` (crates/vilan-image/src/lib.rs) checks only `\x89PNG`, `\xFF\xD8`, `RIFF....WEBP` and `GIF8`. So the four-format set is documented, but AVIF is never named as left out on purpose, and no ruling or open question in proposal/image.md weighs it. This is a missing feature, not a ruled limit. Recent phones and browsers save pictures as AVIF by default in more and more places, so an avatar or attachment upload can be AVIF.

What a caller sees on 0.55.1, with the bytes of an AVIF file's first box (`ftyp`, major brand `avif`, compatible `avif mif1 miaf`; header only, since no AVIF encoder was on hand to make a whole file, and the sniff rejects the bytes before any decoding, so the rest of the file does not matter):

```
Image::sniff(header)  -> None
Image::decode(header) -> Err("not a PNG, JPEG, WebP or GIF")
```

Kolt's avatar upload passes that string on as a 400. That is honest, but the user has no way around it short of converting the picture first.

Rec: add AVIF to decode only (`Format::Avif`, seam code 4, sniffed from an ISO-BMFF `ftyp` box at offset 4 whose major or compatible brands include `avif` or `avis`; `encode(Format::Avif, ..)` refused the way `Gif` is). The cost question comes first: in `image` 0.25 the pure-Rust `avif` feature only encodes (ravif). Decoding goes through `avif-native`, which is dav1d, a C library. That breaks M185's all-pure-Rust codec set and the committed wasm32 blob's reproducible build. Doors: (1) `avif-native` natively and a wasm32 dav1d build for node (a C toolchain in the blob's build, and the blob gets larger); (2) a pure-Rust AV1 decoder (rav1d or a successor) behind the same seam, if it builds for wasm32; (3) leave it out and document AVIF as a ruled limit in std/image.md, with the error naming the format (`"AVIF is not supported"`) so a caller can tell an unsupported picture from a corrupt one. Even if (1) and (2) are out, take (3)'s error text and the doc line. Pin: a small committed AVIF fixture that decodes to the expected size on both backends, or under (3), the named refusal.
