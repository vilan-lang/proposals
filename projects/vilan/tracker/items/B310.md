# B310 — MISCOMPILE: `Map::entries()` hands out the GENERIC tuple layout for a `Map<K, (A, B)>`: `for entry in m.entries() { let (key, slot) = entry; let (class, declaration) = slot; }` reads `class = "class,decl"`, `declaration = undefined` (and `entry.1.0` / `entry.1.1` the same way) — a tuple built inside a GENERIC function from type-parameter-typed values (`self.table.insert(key.hash(), (key, value))`, map.vl:73 `self.table.values()`) is not flattened, while the caller, which knows `V = (A, B)`, reads the result flat (`$m.slice(1, 3)`); `keys()`, `values()` and `get()` are right; silent wrong values, no diagnostic

- status: OPEN — Order 33's finds (2026-09-11)
- kind: bug
- area: Type system & the type solver

The tuple-flattening decision is made at the SITE that builds the tuple, from the static types it sees there; inside a generic body the element types are parameters, so the tuple keeps its boxed layout, and the instantiated caller assumes the flat one. Either flatten by the INSTANTIATED layout at the call boundary (the return of a generic function that yields a tuple of parameters is re-laid out when `V` is known — the `freshen_list_element_slots` neighbourhood is the model for a return-type rewrite), or never flatten a tuple whose components are type parameters and teach the flat readers to recognise the boxed form. Pins: the exhibit (a `Map<str, (str, str)>` round trip through `entries()`), a user generic `fun pair<T>(a: T, b: T): (T, T)` read flat at a concrete call, the corpus differential. Family: miscompile.
