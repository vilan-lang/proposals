# E271 — a hole in element syntax that holds a non-text value — `<p>{count}</p>` over a `SignalCell<i32>`, `<p>{5}</p>` — is refused "'SignalCell<i32>' does not implement trait 'Slot', required by a generic bound of this call", spanned on the ELEMENT's `<` (not the hole) with a secondary label on std's `fun child<C: Slot>`, a call the author never wrote; no steer to the text form (`{count.derive(|n| i"{n}")}`, `i"{5}"`)

- status: OPEN — filed 2026-10-05 (docs-47's find, Order 47)
- kind: diagnostic (S)
- area: Diagnostics & error messages

Element syntax lowers `{expr}` to `.child(expr)` before analysis, so the bound failure is reported as a call-site bound failure of the desugared chain. Two improvements, either alone useful: (1) span the refusal on the hole's expression (the desugar knows it); (2) when the refused type is a number, a bool, or a `Source` of one, say that a hole takes a View, a str, a List<View> or a Source of one, and offer the i-string / `.derive(|n| i"{n}")` rewrite. The same refusal on an explicit `.child(5)` can keep today's wording. Repros: finds/hole_not_a_slot_signal.vl, finds/hole_not_a_slot_literal.vl (both 0.44.0 / next @b94cb47f).
