# A65 — module DIRECTORIES: `import pkg::lib::input_system` resolving `lib/input_system.vl` (and `pkg::lib::ui::widget` → `lib/ui/widget.vl`); today a module is `name.vl` or `name/lib.vl` at the package ROOT only (spec §4.1–4.2), so a directory holds exactly one module and `pkg::lib::util` fails with "cannot find 'lib' in the imported path" — the owner wants kolt's library files under `lib/` or `common/`

- status: OPEN — the owner's ask (2026-09-07); an Order 30 candidate
- kind: feature
- area: Type system & the type solver

Probed on a5473227: `src/lib/lib.vl` is reachable as `pkg::lib` (the directory-module form works) but `src/lib/util.vl` is not reachable by any spelling. Two resolver sites change: `resolve_module_file(root, name)` (analyzer.rs ~45778) takes ONE name and tries `name.vl` / `name/lib.vl`; the import path walk (~31350) descends only through a module's item scope and an enum's variants, so a module is not a namespace of submodules. Design, Rust's rule: `a.vl` OR `a/lib.vl` is module `a`'s body (both present stays the ambiguity error), and `a/b.vl` is `a::b` whether or not `a` has a body — a directory without `lib.vl` is a pure namespace. The walk resolves the LONGEST module prefix of an import path against the disk (`pkg::lib::ui::widget::widget` → module `lib/ui/widget.vl`, member `widget`), then the item segments; `collect_module_import_paths` (B236's collector, E142's alias tuple) records multi-segment module paths; case-exactness per component stays (`case_exact_mismatch`). Touch points to pin: file mode's `package_of_source` and B250's declared-entry rule per leg, the LSP's `module_paths` and `pkg::` completion (E129) and rename of a module segment, `vilan fmt`'s walk, the fmt gate, platform coloring across a directory, and the build hooks' generated root (which may then move under `root`). Spec §4.1/§4.2 gain the directory sentence. Kolt's `lib/` move is the exhibit.
