# B257 — ASSIGNMENT from a live aggregate place does not copy: `b = a; a.push(4)` leaves `b` at 4, `r = q; q.x = 10` leaves `r.x` at 10 (lists and structs alike), while the binding form `mut f = e` clones — spec §6.1 names assignment first and its own example fails rewritten as one

- status: OPEN — found under B255 (2026-09-06)
- kind: bug
- area: Memory model (rule 1 / rule 2)

Probe on 757d3f4b (`assign3.vl`): P1 `mut b = [0]; b = a; print(a.len()); a.push(4)` — `b` reads 4 with `a` read AFTER the assignment, so this is not rule 2's last-use elision; P2 `r = q; q.x = 10` — `r.x` reads 10; P3 with a dead source — elision legitimate; P4 `mut f = e; e.push(4)` — `f` reads 3 (`let f = __clone(e)`). Emitted for P1/P2: `b = a;` / `r = q;` with no `__clone`. The same miss covers assignment THROUGH a view: `h.write() = c; c.push(4)` grows the cell (`h.v = c;`), which is how `bind_each`'s `row_items.write() = list` came to alias (B255).

The Assignment arm calls `consider(value_id, self.type_id_of_expr(value_id))` where the `let` arm passes the variable's own type and the construction arms `place_value_type_id`; `consider` also asks `is_elidable_copy` (liveness) and `assignment_target_is_view`. Find which input declines for a plain local on the right of `=` and pin the four probes as a rule 1 pin in `inference/borrows.rs` (P1, P2, and the `h.write() = c` form, with P3 asserting the elision still fires when the source is dead).
