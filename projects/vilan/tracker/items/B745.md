# B745 — RemoteStore mirror: a patch that lands on the value held in an `Option` of a primitive (`Some("..")`) calls `__replace` on the string and throws ("Cannot assign to read only property '0' of object '[object String]'")

- status: OPEN - filed 2026-11-10 (kolt, checking reconnection after a server restart; vilan 0.55.1)
- kind: bug (std::rpc::mirror / emitted store apply; JS)
- area: Reactive stores / mirror
- renumbered: filed as B740 on the local branch `kolt-mirror` (kolt-side session); synced to main as B745 on 2026-11-16, because main's B740 is another item. Kolt's sources cited the old number until its v0.56.0 patch.

Seen in kolt's client after the server it was connected to restarted and the client reconnected. The next call whose reply carries a store patch logs:

```
unhandled task error (spawned in ask): TypeError: Cannot assign to read only property '0' of object '[object String]'
    at Object.assign (<anonymous>)
    at __replace (client.js:340)
    at store_apply_at2 (client.js:33976)
    at store_apply_at (client.js:33785)
    at store_apply_at41 (client.js:60809)
```

The emitted code: `store_apply_at41` is an `Option<T>`'s apply. With the path exhausted it replaces the whole option; otherwise, when the option is `Some`, it descends: `store_apply_at(held, path, from, deserializer)` with `held = self[1]`. For a leaf `T` that apply is `store_apply_at2`, which does `__replace(self, store_wire_rebuild_of2(deserializer))`, and `__replace` is `Object.assign(target, value)`: an in-place overwrite. When `held` is a JS primitive (here a string) there is nothing to overwrite in place, and assigning its index properties throws.

So a patch addressed INSIDE `Some(primitive)` can't be applied; it has to replace the option's slot (`self[1] = rebuilt`) instead of mutating what the slot holds.

Repro so far (kolt, not yet minimal): sign in, open an organization's tasks, create a task; stop the server and start it again on the same data; wait for the client to reconnect (about 9 s); create another task. The task is made and shows, and the error above is logged once. Without the restart it doesn't happen; it happens the same on kolt's previous commit, so it isn't from kolt's change of that day. Which field the patch addresses isn't identified; kolt's stores have several `Option<str>` fields.

Rec: in an `Option<T>` (and any container) apply, when `T` is a primitive on JS (str, numbers, bool), write the rebuilt value into the parent's slot rather than `__replace`-ing the held value; or have the leaf apply return the rebuilt value for the parent to store. Pin: a mirrored `Store` with an `Option<str>` field, patched `Some("a")` -> `Some("b")` through a path that descends into the option, on JS. Worth checking why this only shows after a reconnect (the resumed mirror may address paths one level deeper than a fresh one does).

2026-11-10 (later, from a deployed kolt's console log): it needs no restart. In ordinary use it fires each time a page asks again for a value the mirror already holds: `me.organizations().derive(..)` built per page (kolt `organization_by_slug`), 14 times in one short session of switching tabs and panels, each as `unhandled task error (spawned in ask)` through `reply_store` -> `land` -> the Option apply -> `__replace` on a string. So the trigger is a second ask's reply landing on a held `Some(text)`, not the reconnect. The reply is dropped where it throws. Raises the priority: every kolt page build logs it.

2026-11-10 (later, kolt task 128): CAUSE FOUND, and it is not the mirror: B746. The value that throws is a str-backed enum FIELD of the struct the `Option` holds (kolt's `ChannelRecord.kind`, `Notice.kind`), not a primitive held in `Some`: in the stack above, `store_apply_at` is the struct's derived apply and `store_apply_at2` its `kind` leaf. A backed enum is a bare JS string, but `&mut` to it lowers as an aggregate, so the leaf's `self = ..` is `Object.assign` on a string. Minimal repro (no mirror, no std beyond the prelude): B746. The two kolt paths, both seen with their stacks: `bind` -> `landed_over` (a re-ask over a held replica: the account's mint on a reconnect's replay) and `MirrorClient::land` -> a boundary's `apply` (a re-seed over a held `ChannelRecord`). The "ordinary use" entry above is the same thing one step later, not a separate trigger: once a reconnect's re-ask has thrown, the account's mint never binds again (`bind` throws before its batch, with `asking` already false), so every later hold asks again and logs again, once per page build, until the page reloads. Without a dropped connection it was not reproduced (reloads, tab switches, layout switches, a panel's page changed from its switcher: no error). `organization_by_slug` is one of those holders, not the cause. Closes with B746; the mirror needs no change of its own.
