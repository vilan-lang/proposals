# B691 — JS MISCOMPILE: an enum value is never copied at a value seam - `mut b = a` of an `Option<List<i32>>` aliases `a`'s payload, so a write through `b` shows in `a`; `*p` of an `&Option<List<i32>>` aliases too

- status: OPEN - filed 2026-10-31 (lane b689's find; B689's `HashMap::get` keeps the table's own `get` rather than `peek(key, |slot| *slot)` because of it)
- kind: miscompile (JS emitter; rule 1 copies skip `Type::Enum`)
- area: Compiler

Rule 1 (value semantics) wraps an aggregate in `__clone(..)` at a value seam - a `let`/`mut` from a place, a `*view` read, a return of a borrowed place - and the analyzer's `is_cloneable_aggregate` answers structs, tuples, lists and maps but NOT enums, so an enum whose payload is an aggregate (`Option<List<T>>`, `Result<Struct, E>`, any user enum with data) is handed out BY REFERENCE and two bindings share one payload. Natively every binding is its own value (`Clone`), so the backends disagree. Rec: `is_cloneable_aggregate` answers true for an enum with any aggregate payload (a payload-less or scalar-payload enum stays a scalar copy); pins in inference/borrows.rs for the three seams (`mut b = a`, `*p`, a return of `*p`) on both backends; the copy-elision census moves and is read. Note the two B689 sites that work around it (hash_map.vl `get` and `get_or_insert` comments) can take `peek`/`modify` once this is fixed.
