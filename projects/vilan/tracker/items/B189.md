# B189 — three cascade siblings B182's stand-down does not reach

- status: OPEN — b182 lane's finds (2026-09-01); each its own pin when taken
- kind: bug
- area: Type system & the type solver
- source: lane b182

B182 gave a REFUSED ANNOTATION's `Unknown` slot provenance, so its
consumers stand down. Three same-shaped piles remain, each with a
different provenance:
1. **The unresolved-name sibling.** `struct Holder { inner: Nope }`
   gives `cannot find type 'Nope'` AND `cannot call method 'length'
   on unknown` — that arm resolves to Unknown one match arm below the
   instrumented one. Extending the provenance set is a one-line
   change; left so the "an unrelated unknown still reports" pin stays
   non-vacuous. Rule it: a `cannot find type` refusal is a root like
   any other — extend, and re-shape that pin around a GENUINELY
   unrelated unknown.
2. **`[derive(Wire)]` over a refused bare-trait field** emits `cannot
   find 'from_json_value' in Greet` / `'rebuild' in Greet` — the
   derive template is built from the annotation's SPELLING, which
   survives the refusal, so the receiver is the trait, not the slot.
   Needs spelling-level provenance (the refusal marks the annotation
   node; derive generation checks it before templating).
3. **`[expose]` of a non-Wire element reports twice** — the curated
   root plus a generated-code bound failure at the struct span. A
   real type failing a bound, not an Unknown: the generated call
   should carry a "reported at the field" marker the bound check
   honors (E104's covered-set idea, keyed on the field).
