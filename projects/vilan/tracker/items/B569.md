# B569 — named tuple fields — `let p: (x: f64, y: f64) = (x = 5, y = 7); p.x` — labels for a tuple's positions, with no declaration

- status: OPEN — filed 2026-10-05 (the owner's idea; a paper in Order 48, no build before it is ruled)
- kind: language design (L) — paper first
- area: Type system

The owner's sketch:

```
let point_1: (x: f64, y: f64) = (x = 5, y = 7); // (5, 7)
let point_2: (x: f64, y: f64) = (5, 7);         // (5, 7)
let point_3: (x: f64, y: f64) = (y = 5, x = 7); // (5, 7)  [as written by the owner; by-name matching would give (7, 5) - the paper settles which]
print(i"point x={point_1.x}, y={point_1.y}");
```

The owner's rules: like a struct but undeclared; assignment in expression position is BANNED so `x = 5` inside parentheses is unambiguous (a block expression still assigns); a literal may write its fields in another order than the type; two tuple TYPES must agree in order (`(a: str, b: bool)` is not `(b: bool, a: str)`). Open in the owner's mind: whether `(a: str, b: bool)` reconciles with `(b: str, a: bool)` - he leans YES: the names are labels for a position, an explicit `(0: str, 1: bool)`, not struct fields.

Facts and questions for the paper (the integrator's first read):
1. Assignment IS an expression today (`let y = (x = 5);` checks clean on next @db2df5f1), so the ban is a breaking change; count the estate.
2. If labels are not part of a type's identity, two types reconcile by position and a `(x: f64, y: f64)` flows silently into a `(y: f64, x: f64)` with every label now wrong. Candidate rule: labelled and unlabelled convert freely; differently-NAMED labels reconcile; the SAME label set in a different order is refused (or warned), since that case is almost always a swap.
3. A labelled LITERAL against a labelled expected type matches by name; with no expected type it has the type of its written order. Say what `point_3` is.
4. `(x = 5)` with one field: a one-slot named tuple, a grouping, or a refusal (tuple families are `(2..)` today).
5. What reads the labels: `p.x` beside `p.0`; destructuring by name; hover, `dbg` and `Debug` output; `keys()` on a tuple family; mapped tuples (`(U in T: ..)`) carrying labels through.
6. What erases them: Wire and JSON (an array, as now, or an object?), the contract hash (B525), the native backend (Rust tuples).
7. The door this opens: a spread parameter over a named tuple is named arguments.
8. Why not a struct: say when the book should steer to one.

- 2026-10-05 (the owner): the third example was a typo: it is `(y = 7, x = 5)`, which is `(5, 7)` - so a labelled literal matches a labelled expected type BY NAME (settled; question 3 is answered). RULED: the same label set in a different order does not reconcile (refuse or warn - the paper picks which and says why); labelled and unlabelled convert freely and differently-named labels reconcile, as the owner leaned. The rest goes to the paper.
