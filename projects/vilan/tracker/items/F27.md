# F27 — how USERLAND writes platform-specific code: kolt's `lib/conditional_value.vl` is a user `Slot` impl over the BROWSER twin's `Region` (`region.anchor`, `cut_row`), so (1) opened before anything imported it, the editor analyzed it as `process` and errored `struct 'Region' has no field 'anchor'` — every name it imports (`Region`, `Row`, `Slot`) exists in BOTH `std::ui` twins, so import-name inference (B36) has no evidence; and (2) it has no server-side meaning at all, though 'technically a server-side implementation should exist too'. The owner's candidates: `import std::ui::Region layer browser;`, a `[layer(L)]` attribute, a layer entry in vilan.toml. Measured the same day: today's `[platform("browser")]` FUNCTION fence does not change how a body resolves — `region.anchor` still errors under it

The integrator's recommendation, to be argued in a paper:

**Not an import clause, and not the word `layer`.** `import std::ui::Region layer browser;` re-targets ONE name; every other name in the file (`Slot`, `Row`, `View`, the prelude) still resolves under the ambient platform, so the file is analyzed half-and-half. And 'layer' is a library's PACKAGING word (which file serves a module, platform-coloring §3.4); what app code has is a REQUIREMENT, and the language already spells that `[platform(..)]`.

**R1 — `[platform("browser")]` at MODULE level** (a file-leading attribute; also on `impl` blocks and nominals). It means what the function fence means — everything inside requires that platform — and additionally it is the platform the item is ANALYZED under: the editor stops guessing (it outranks every heuristic, and an unconsumed file is right from the first keystroke), and reaching it from a server entry reports the coloring chain ('`when_value` requires browser; reached from `server` through …') instead of a field error in the wrong twin. Today's function fence must gain the same resolution meaning (measured: it has none), or the two spellings would disagree. S–M.

**R2 — better evidence for the unannotated file**: extend B36's rule from imported NAMES to MEMBERS — a field or method that only one twin declares (`Region.anchor`, `cut_row`) is evidence exactly as `mount` is. Makes kolt's file right with no annotation. S. (E182: `infer_platform` is still binary browser/not — a native twin makes it three-way.)

**R3 — true twin implementations in userland: platform-fenced ITEMS in one file.** `[platform("browser")] impl ConditionalValue<..> with Slot { .. }` beside `[platform("@process")] impl ConditionalValue<..> with Slot { .. }`: two impls of one trait for one type are coherent iff their platform sets are DISJOINT; each is analyzed only under a platform it admits (so the one `import std::ui::Region` means the right twin inside each); a build selects by its entry's platform; the editor analyzes the file once per declared platform and unions the diagnostics. This is the general answer, it is what F17's 'named exceptions' needs for native window chrome, and it is strictly nicer than the fallback — R4 — of letting an APP package declare layers the way std does (`[package.layer.browser]` → `src/browser/x.vl` + `src/process/x.vl`), which already has all its machinery and is as clunky as the owner says. The cost R3 must face honestly: a fenced item is NOT type-checked in a leg that excludes it, which bends platform-coloring §2's 'unreachable code is still type-checked' — the paper states the new invariant (every item is checked under at least one platform it admits, and the editor checks all of them).

**R5 — and std's share**: `Region`'s fields are public in the browser twin and absent in the process twin, and the twin-parity gate did not object — is parity FIELD-blind? Either the gate learns fields, or those members carry E213's internal label; and A119 ships the form so userland rarely needs to write a `Slot` impl at all.

Rulings the paper asks: R1's attribute at module level (yes/no); whether the function fence gains resolution meaning; R3 vs R4 for userland twins; whether R2's heuristic is wanted once R1 exists (rec yes — zero-annotation is the common case).
