# G11 — `vilan build --explain`: every `dist/` output names its contributors

- status: OPEN — filed on the owner's word, 2026-08-29 (the 027-reopen
  discussion's side finding: traceability is a tooling gap, not a model gap)
- kind: feature
- area: Macros & const
- source: the owner's config-as-code steer, kolt.local 035/027, 2026-08-29

The complaint the item answers: the const channel's contributions are
scattered across files by construction (that scatter IS import-driven
composition), so "where did this `dist/` file come from?" is a grep today —
and for an accumulated kind, a grep over every `emit` site. The compiler
holds the provenance the whole time: every `emit`/`bundle`/`read` site has a
span, the flush knows which kind each line landed in, the manifest knows the
rows, and the hook runner knows what ran and what was `Fresh`.

`vilan build --explain` prints the build's story from that record: one block
per `dist/` output — the emitting/bundling sites (file:line) for channel
outputs, the source path for a bundled copy, the hook that wrote a declared
output, `generated shell` / `compiled bundle` for the build's own files —
and per tracked input, what it invalidates. Tier-agnostic by design: it
explains the channel, the bundles, AND the hooks in one report, which is
what makes it worth having regardless of how 027's reopened Q1 is ruled.
No new machinery, no new record: the verb reads what the build already
knows and says it out loud. (The refusal doctrine's cousin: a build that
can refuse by name should also be able to explain by name.)
