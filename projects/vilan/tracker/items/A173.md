# A173 — TERMINAL INPUT: a key-stream primitive for stdin — `let keys = process::keys(); for key in keys { .. }` (a RESOURCE in raw mode, pulled per iteration with an awaiting `next`, restored on Drop, carrying the nursery's ambient cancel signal as `fs::Watcher` does) with a `Key` enum (`Char`, `Enter`, `Backspace`, `Tab`, `Escape`, the arrows, Home/End/PageUp/PageDown, `Delete`, function keys, a modifier set) decoded identically on both backends and degrading to `Char`/`Enter` from the bytes when stdin is not a TTY — after `scan()` itself becomes incremental and awaiting

- status: OPEN — filed 2026-10-16 (the owner, after Order 53: 'how can we improve stdin scanning?'); paper in Order 54
- kind: design discussion (paper) — the owner's; std::process (M)
- area: Language

Ground truth (v0.51.0): std's one stdin door is `process::scan(): str` (an `external fun`, synchronous); on JS its helper `__scan` reads ALL of stdin to EOF with one `readFileSync(0)` and hands out lines, so an interactive prompt blocks until the stream closes; no native implementation of `scan` was found in vilan-rust/vilan-rt; nothing touches raw mode anywhere; there is no `scan_char`. The owner's ask: a per-key primitive (`scan_key` awaited per iteration, or a callback) that `scan_char`/`scan_line` could be built on, with backspace handling. Recommendation (the paper `proposal/terminal.md`, Order 54): (1) PULL, not a callback — the language already solved values-arriving-over-time as an awaiting `next()` (`fs::Watcher::next`, `fetch::BodyReader::read_chunk`), which gives the `for` loop, `break`, error flow and nursery cancellation for free; a reactive `Source<Key>` for a terminal UI can be DERIVED from the stream by a task, never the reverse; (2) a RESOURCE, not a free function — raw mode is terminal state that must be restored on `break`, exit and panic: the handle owns it and `Drop` restores it (destruction.md's rule; `Watcher`'s stop is the model); `next` yields `Option<Key>`, `None` when stdin closes; verify first whether a `for` over an `Iterator` whose `next` awaits already works through the async adaptation, or why the watcher avoided the trait; (3) the DECODER is the cost — VT escape sequences with the lone-Escape timeout, UTF-8 multibyte, bracketed paste, the Windows console API natively; node gives most of it via `setRawMode` + `emitKeypressEvents`; native needs crossterm in vilan-rt or a hand-rolled termios reader; both must decode identically (the native differential) and degrade to `Char`/`Enter` on a pipe so the corpus, the differential and `vilan run < input` keep working; (4) `scan()`/`scan_line` stay on COOKED mode (the terminal does echo, backspace and history) — building line editing on keys means a line editor in std; the key stream is for key-driven programs (menus, pagers, games); `scan_char` falls out as a filter. Slices: S1 `scan()` incremental + awaiting on both backends (JS reads to the newline, native implements it; pipe pins; the interactive prompt works), S2 the `Keys` resource + `Key` + both decoders + the pipe fallback (+ `keys()` inside a nursery cancels), S3 line editing on top only on a shown need. Owner questions for the paper: the names (`process::keys()` / `Key`), whether `scan()` gains a `prompt(text)` twin, the native decoder's dependency policy (crossterm vs hand-rolled), and the pipe-degradation rule's exact shape.
