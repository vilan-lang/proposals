# M35 — a multi-entry `check`/`build` compiles its entries one after another; the compiler uses one of sixteen threads

- status: OPEN — kolt-benchmark's find (2026-09-04); the first parallelism item in the tree
- kind: performance
- area: CLI & build

Nothing in `vilan-core` or `vilan-cli` uses a thread pool: the three
kolt entries (client, probe, server — a `BTreeMap`, alphabetical)
are compiled sequentially by `compile_unit` in one process, sharing
only the parse cache and the base cache. Each entry is a complete,
independent analysis, so a package's `check` wall is the SUM of its
entries where it could be the MAX. Honest expectation on kolt
itself: small — the client is ~80% of the total (1.85 s of 2.26 s
CPU), so the gain is ≤ 18%; on a package with balanced entries it
is up to N×. The shared state is the hazard, not the loop: the
process-global caches (`parse_clean_cached`, `BASE_CACHE`, the macro
worlds, `leak_tally`) are `Mutex`ed and content-keyed, so
concurrent entries would serialize on them correctly but the base
cache's M23 claims and M24 eviction were designed for one analysis
at a time — audit those two before spawning. Do NOT extend this to
inside an analysis (the analyzer is one `&mut self` struct; that is
M19's frozen-module direction, not a thread). Pin: `vilan check` of
a generated package with four equal entries runs in ~1.1× one
entry's wall on a quiet 16-thread machine; the corpus goldens are
byte-identical (emission order must not depend on scheduling).
