# A44 — `Source::selector()`: O(2) per-key selection notification (Solid's `createSelector`); the owner's `sub_condition` is O(n) and lands inside the notify loop

- status: OPEN — the owner's idea while migrating kolt (2026-09-04); triage lane's design note at 289e2a2b
- kind: feature
- area: Reactive core & UI

The owner proposes `Source.sub_condition(cond, cb)` — subscribe but only
update when a condition holds — to build Solid's `createSelector`.
Nothing exists (zero hits for selector/sub_condition in std/kolt/website).

Mechanism: `createSelector` takes ONE subscription on the source and
keeps a per-key map of boolean signals; on change it writes the
outgoing key's cell and the incoming key's — O(2) regardless of row
count. `sub_condition` cannot give that: N subscribers on the source,
`cond` evaluated N times per emission, and that linear cost lands
inside `notify`'s loop (reactive.vl ~583) next to `enqueue`'s linear
dedup scan (~99–110, whose own comment says "a keyed set can replace
this later") — O(n²) at N rows.

Shape: `fun selector<T: Hashable + PartialEq, S: Source<T>>(source: S):
sync |T| SignalCell<bool>` — one `on_change` (A43) on the source; a
`NativeMap<SignalCell<bool>>` keyed by `key.hash()`; on change
`map.get(old)?.set(false); map.get(new)?.set(true)`; the closure
creates-or-returns the per-key cell seeded `key == source.get()` and
`defer_to_owner`s the entry's removal — which fits `bind_each`'s
per-row owner (ui.vl ~346/351). Returning `SignalCell<bool>` drops into
`.show`/`.when`/`bind_class`/`bind_styled`. Offer `sub_condition` only
as sugar over `on_change`; it buys no complexity class. Internals
available: `subscribers` (~514), `Subscription::dispose` (~284),
`Owner` (~329), `Hashable`/`NativeMap` shipped. First customers: kolt's
theme picker (views.vl ~514–522) and command palette (~690), which
re-derive and re-render whole rows today. Size M (~50 lines) + S–M to
key `enqueue`'s scan so the win holds at scale. Related: A43, A14, I1.
