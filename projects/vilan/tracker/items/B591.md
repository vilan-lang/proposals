# B591 — the subscript's `usize` check passes an index whose type is not yet known when the subscript resolves and nothing checks it again: `xs[one()]` and `xs[n.max(0)]` (both `i32`) check clean while `let i: i32 = 1; xs[i]` is refused; a negative call index panics "the index is -1" on JS and "the index is 18446744073709551615" natively

- status: OPEN — filed 2026-10-09 (papers-49's find, Order 49)
- kind: solver: a check that runs once (S)
- area: Type system & the type solver

Repro (`finds/subscript_index_unchecked_call.vl`, vilan 0.46.0): `fun minus_one(): i32 { 0 - 1 }` and `print(xs[n.max(0)]); print(xs[minus_one()]);` over a `List<i32>` -> `vilan check`: no errors. JS: `2`, then "index out of bounds: the length is 3 but the index is -1"; natively the emitted `(minus_one()) as usize` wraps and the panic reads "... the index is 18446744073709551615" (a differential the corpus does not carry). Cause: `subscript_index_is_an_index` (analyzer.rs ~60016) is lenient about an index that is `Unknown`/`Unresolved` ("reported by the fixpoint's own leftover sweep"), but a call's type is often still Unknown when the subscript resolves and then resolves to `i32`, which the leftover sweep does not report (it reports holes, not wrong types). B386's rule ("`xs[i]` takes a `usize` and nothing else") is therefore enforced only on indexes typed at resolution time. Fix: defer the subscript while its index is Unknown (the B290 pattern), or re-run the index check after the fixpoint over the subscripts that passed leniently. Expect estate fallout: every `xs[f()]` with an `i32` answer becomes a refusal with `.as_usize()` (count kolt, the website, std, the corpus before landing). Sizing S.
