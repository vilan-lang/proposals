# M33 — four macro-world compiles per CLI process: ~18% of a small entry's instructions, paid by every `vilan check`/`build`, cached only in-process

- status: OPEN — kolt-benchmark's find (2026-09-04; callgrind at 289e2a2b, lucide-stubbed client)
- kind: performance
- area: Macros & const

A cold `vilan check` of kolt's client compiles four macro worlds
(`analyze_source` ×4 inside `macros::expand_source`, **18.2% of the
stubbed client's 3.21e9 Ir**, ~0.58e9 — comparable to the entry's
own `checks`). Each is macro-engine.md §3's hermetic world: the
blanked copy of one macro-defining file (the std modules hosting the
derive vocabulary and the service/rpc attributes) analyzed against
`macro_std`. §6 caches them by blanked-file content hash — but the
cache is process-global and leaked, so the LSP and an HMR loop pay
once while every `check`, every `build`, and every `perf_baseline`
cold row pays all four again, for inputs (std files + the toolchain)
that do not change between runs. The phase line hides it: a world
prints only its post-passes line, its `load+walk`/`base`/`checks`
fold into the outer entry's. Direction: (1) put the four on the
phase line as their own row so the cost is visible; (2) a
cross-process cache keyed by (blanked-file hash, toolchain version)
— the world's leaked text/program/AST is what `Box::leak` holds, so
the natural unit is the serialized `Source` expansions rather than
the world itself, i.e. cache §6's expansion table on disk under the
package's build dir; (3) or precompile std's macro worlds at install
time beside `macro_std`. Pin: the second `vilan check` of an
unchanged package compiles zero macro worlds; a std edit invalidates
by content.
