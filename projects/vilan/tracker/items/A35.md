# A35 — the element desugar's `view` is capturable, and the shadowed case has no diagnostic

- status: OPEN — lucide lane's find (Order 23); one 55s build to hit, any generator will
- kind: design
- area: Reactive core & UI (`std::reactive`, `std::ui`)
- source: lane lucide, 2026-08-31

lucide ships an icon named `view`. The generated `fun view(): View`
silently shadowed `std::ui::view`, and every `<tag />` in the file then
failed with `` `view` expects 0 arguments, but got 1 instead ``
pointing at the ELEMENT, the shadowing item shown only as "declared
here". The ABSENT case is excellently diagnosed ("element syntax
lowers to std::ui::view; add import std::ui::{ view, View };"); the
SHADOWED case gets nothing.

Two doors, the ruling picks one: (1) the diagnostic names shadowing —
"element syntax lowers to std::ui::view, and `view` here is your
`fun view` at <site>" — or (2) the desugar's `view` becomes HYGIENIC:
it is compiler scaffolding, so arguably a user item should not be able
to capture it at all (note the prelude pin
`an_explicit_import_shadows_a_prelude_name_silently` — shadowing
prelude NAMES is a ruled feature; the question here is narrower, the
desugar's own callee). Any generator over an external name set hits
this; lucide worked around by prefixing (`lucide_*` module-owned
names, per-icon fns unprefixed but the set has no `view` collision at
fn level — the collision was the module-level helper).

## RULED 2026-09-01 — name it in the diagnostic

The owner: "Name it in the diagnostic. This could happen again, and
improving the diagnostic would help." The absent-case steer gains a
shadowed-case twin: "element syntax lowers to `std::ui::view`, and
`view` here is your `fun view` at <site> — rename it or qualify the
element's callee". The desugar stays capturable (no hygiene change).
The companion question — the process-layer `View.element` message —
is E119.
