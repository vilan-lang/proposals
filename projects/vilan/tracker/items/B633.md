# B633 — `[derive(Wire)]` over a GENERIC struct refuses a field whose type reaches a type parameter (`struct Page<T> { items: List<T> }`) - C7's guard refuses parameter-typed Wire fields on purpose, and B622's Hashable fix withdrew its Wire half on that pin; relax the guard so a reached parameter is admitted under the derive's own binders, and judge a generic derived type by its ARGUMENTS in `resolved_type_is_wire` the same day

- status: OPEN — filed 2026-10-13 (std-52's Q3, Order 52; integrator)
- kind: derive surface (Wire; S)
- area: Language

The same shape as B622's landed half: the Wire boundary reads each field under the derived impl's own type parameters (a `T: Wire` bound on the derive), and a generic derived type used as a field is judged through the impl table by its arguments, not by name. C7's pin becomes the positive case (a parameter-typed field IS Wire when the parameter is bound Wire) plus its negative twin (an unbounded parameter still refused, naming the bound to add). Estate: count the derives over generic structs in kolt, the website, the examples and std's corpus (expected a handful, all currently refused or written by hand). The Wire generator's three `{type}::rebuild` sites need B623's path-head treatment for an array field (A171). Sizing S (analyzer.rs's Wire boundary + the generator; pins in borrows.rs and generics.rs).
