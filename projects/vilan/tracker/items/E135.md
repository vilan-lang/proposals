# E135 — an incomplete `a::` path rolls the `::` back: the failure surfaces as a missing `;`, or the path re-binds to the NEXT line's identifier and swallows that statement

- status: OPEN — the owner's find while migrating kolt (2026-09-04); reproduced at 289e2a2b by the triage lane
- kind: bug
- area: Language server & tooling

The owner: an incomplete `style::` breaks element parsing, giving `found
'<' expected a statement or '}'` instead of an expected-something-after-
`::` message. Reproduced (the defect, not that exact wording): `let x =
style::` + `<div class("panel")></div>` → `expected ';' to end this
statement` anchored on the `::`, plus a bogus `Expected View, but got
void`. Worse face: `let x = style::` followed by `print(render(<div>
</div>));` parses as `style::print(..)` — the incomplete path silently
swallows the next statement's head; the only error is `cannot find
type 'style'`. The owner's literal wording comes from `emit_statement_
failure` (parsing.rs ~1401) once E136's element recovery has consumed
the failure — their file hit both at once.

Cause: `parse_static_accessor` (parsing.rs ~2497): the `None` arm of
`eat_ident()` at ~2538 does `self.position = save; break;` — rolls the
`::` back instead of reporting. The `Length::css` arm right above
(~2523–2536) is the model.

Fix (S, low risk): in that arm `note_expected("a name after `::`")` +
`emit_failure`, consume nothing further, stop the path with a
`Node::Error` stand-in so the enclosing statement still parses.
`parse_expr_regression` pins `"a::"` as a decliner — re-pin its
message. Scratch: `triage27/parse-fmt-diag/issue1*.vl`. Related: E136,
E129 (the completion side of the same `::` position).
