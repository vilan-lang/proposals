# E161 — the TextMate grammar mis-scopes a nested generic head: in `impl Source<Option<type _: Source<type U>>>` the `type` binder keyword is `storage.type.vilan` (the declaration-keyword scope — `fun`/`struct`/`impl` — which most themes colour like a type name), `<type` matches the ELEMENT rule (vilan.tmLanguage.json:388: a lowercase name glued to `<` is a tag, so that bracket is `punctuation.definition.tag.vilan`), the other angle brackets fall to the bare-operator fallback (`keyword.operator.vilan`, :380), and a line-leading `>` is E115's multi-line element terminator (`punctuation.definition.tag.vilan`) — three scopes for one bracket kind and a keyword coloured as a type

- status: OPEN — the owner's report (2026-09-11); Order 32 (smalls-32)
- kind: editor
- area: LSP & tooling

**Mechanism, read from the grammar at 65af4be0.** (1) `type` sits in the declaration-keyword list (`storage.type.vilan`: `fun|struct|enum|impl|trait|type|mod|macro`, :303) — right for `type Alias = ..`, wrong for the BINDER inside a head, where it introduces a parameter. (2) The element rule (:388, `(</?)([a-z][a-zA-Z0-9_]*(?:-[a-zA-Z0-9_]+)*)\\s*(/?>)?`) fires on `<type`, `<sync`, `<str` — any lowercase word glued to `<` — so `Option<type _` opens a 'tag' named `type`. (3) Every other `<`/`>` in a type is the operator fallback's single-character class (:380, `[-+*/=<>!&|^?%]`). (4) A wrapped head whose continuation line starts with `>` (or `>>>`) hits the E115 terminator rule (`^\\s*(/?>)`), scoped as a tag delimiter.

**Fix (TextMate, line-based and regex-only, so structure by begin/end).** (a) A generic-argument-list rule: `begin` = `<` immediately after a type-name character (`(?<=[A-Za-z0-9_])<`), `end` = `>`, `name` = `meta.generic.vilan`, delimiters `punctuation.definition.generic.begin/end.vilan`, patterns = itself + types + the binder rule — nesting gives `>>>` three ends. (b) The binder rule inside it: `\\b(type)\\b(?=\\s+(?:[A-Za-z_]|_))` → `keyword.other.type-binder.vilan` (or `storage.modifier.vilan` — pick the one the shipped themes colour as a keyword, and say which themes you checked); `_` there is `variable.language.wildcard.vilan` if the theme has a colour for it. (c) The element rule requires the `<` NOT to follow an identifier character (`(?<![A-Za-z0-9_])`) — element syntax's own atom-position rule (S2) already says a tag `<` starts an atom, so this is the grammar catching up with the spec, not a new rule; `<type` can never be a tag. (d) The terminator rule: scope only inside an element head — an element-head begin/end (from `<tag` to `>`/`/>`) is the honest form of E115's stopgap; if that is too large, the terminator rule at least excludes a `>` that closes a generic (the generic rule from (a) consumes it first when the list began on an earlier line — a begin/end spans lines, which is the whole point).

**Third place.** The book's highlight.js theme (`vilan/docs/theme/vilan.js`) is the grammar's twin for word lists (grammar_sync's GENERATION covers keywords/primitives/operators only); check whether it mis-colours the same head and fix the structural rule there too if so.

**Semantic layer.** If vilan-lsp classifies `type` binders or brackets, its class wins in VS Code — fix the classification there (E2's span classes) or leave those spans unclassified so TextMate paints them; report which layer owned each of the owner's three observations.
