# B172 — a module-qualified TYPE path is a parse error in every type position

- status: OPEN — templates lane's find (Order 23); the prelude makes it load-bearing
- kind: bug
- area: Type system & the type solver
- source: lane templates, 2026-08-31

`style::Style` fails to PARSE as a return type, a `let` annotation, a
parameter type, and a struct field type — even with an explicit
`import std::style;` in the file, so this is a grammar gap, not a
prelude bug. Expression paths through the same module are fine
(`style::style()`, `style::Display::Flex` resolve and run). Repro:

    import std::style;
    fun f(): style::Style { style::style() }

→ `found 'fun' expected an expression` pointing at line 1 column 1 of
the NEXT item. Parameter/field positions give `found '::' expected ','
or ')'`; the `let` case cascades into a bogus `cannot find 's'`.

The `std::web` prelude carries `style` and `ui` as MODULE names (the
ruled spelling), so a web-set user can reach every VALUE in
`std::style` but cannot name any of its TYPES without a member import
— both web templates now carry a forced `import std::style::Style;`
with a comment saying why, which comes out when this closes. Two
facets: (1) admit qualified paths in type positions; (2) the
return-type diagnostic misattributes to the following item — fix its
anchoring even if (1) lands first.
