# B156 — a manifest-configurable prelude: std ambient names by default, overridable

- status: OPEN — RULED 2026-08-29: **write the paper** (Order 21). The
  census draws the default set; the questions below are the paper's to
  settle and the owner's to rule after.
- kind: design
- area: Modules & resolution
- source: the owner's ask, 2026-08-29

Every vilan file today imports its basics by hand — `import std::print;`,
`import std::option::Option::{ None, Some, self };`,
`import std::result::Result::{ Err, Ok, self };` head nearly every module in
the estate (kolt's nine files carry them all). The ask: a PRELUDE — a set of
names in scope with no import — set to a std one by default (`print`,
`Option` and its variants, `Result` and its variants, and whatever the
census says belongs beside them), overridable with a custom one.

The spelling is the manifest's, and this is one of the few things that
GENUINELY qualifies under the owner's own charter (the 035/027 ruling:
manifests carry pre-compiler facts only): the ambient scope must be known
before any file resolves, so it cannot be declared in the code it governs
without a bootstrapping hole. Something like `[package] prelude = ...`
(default the std prelude; a module path for a custom one; `false` for none),
exact spelling the paper's.

Design questions the paper must settle:

- **The default's contents, by census.** Count the most-imported std names
  across the estate (std itself, the corpus, the examples, kolt, the
  website) and let the data draw the line — `print`/`Option`/`Result` are
  certain; the question is what else (List/Map are inherent-ish already;
  `Range`? `Signal`? platform-colored names presumably never).
- **Per-package, never inherited.** A dependency's files resolve under the
  dependency's OWN declared prelude, not the consumer's — anything else
  breaks composability the day two packages disagree.
- **Override replaces, does not extend** (lean): a custom prelude is a
  module whose exports ARE the ambient names, and extending std's is
  spelled by re-exporting std's names from it — one mechanism, no merge
  rules. Whether `export` as shipped suffices is the paper's to check.
- **Shadowing.** An explicit import or local declaration of a prelude name
  must win silently (the prelude is the WEAKEST scope, like the UA sheet
  under preflight); a prelude that could collide with user code any other
  way is a migration hazard.
- **Tooling is half the feature.** Organize Imports must stop minting
  imports for prelude names (and should REMOVE ones the prelude covers —
  or must it leave them? the paper decides and the formatter follows);
  completion offers prelude names undecorated; go-to-definition resolves
  them; the unresolved-name diagnostic says "in the prelude of" vs
  "import"; docs teach the default set in one place.
- **std itself** likely compiles with NO prelude (explicit imports keep
  the base library's own resolution boring and greppable) — or with it,
  uniformly; either way, decided and stated.
- **Breaking posture:** additive for the default set only if every name
  chosen is one no estate file declares locally — the census answers this
  too; alpha makes a small breakage cheap if not.
