# A123 — `and_then` on `Source<Option<T>>` (Kleisli composition for a source of options: `|T| I: Source<Option<U>>` → `SignalCell<Option<U>>`) and `switch` on `Source<T>` (`|T| I: Source<U>` → `SignalCell<U>`, = `map(f).flatten()`) — the two DYNAMIC-DEPENDENCY combinators every kolt chain hand-rolls: channel.vl:41 is `message.map(|x| x.map(|x| x.author.user())).flatten().map(|x| x.flatten())` and model.vl:130's `map_safe` is `and_then` specialised to the client. PROBED: the generic `and_then` blanket impl compiles and runs correctly TODAY on 4f990aa2c; the generic `switch` hits B371

- status: OPEN — filed 2026-09-21 (the owner's question, mid-Order 39); Order 40 candidate, S
- kind: feature (std, two blanket methods)
- area: Reactive core & UI

**The finding.** Every 'ugly' signal chain in kolt is a DYNAMIC dependency (which inner source to follow depends on the current value) spelled through STATIC combinators plus the join. `Source` has one dynamic primitive, `flatten`, in two shapes (A86), and the `Option` shape is `sequence`-then-join — `Source<Option<Source<U>>>` → `Source<Option<U>>` — not the join of the composite `Source∘Option` (that would take `Source<Option<Source<Option<U>>>>` straight to `Source<Option<U>>`). Which is why kolt needs the trailing `.map(|x| x.flatten())` every time: the inner source is itself a source of options. The owner is right that it is 'not really a flatten'; it is a legitimate op with an overpromising name, and a third `flatten` for the composite shape cannot be added — its subject `Source<Option<I: Source<Option<U>>>>` overlaps the existing `Source<Option<I: Source<U>>>` and there is no overloading to pick between them.

**The two methods** (probed in the scratchpad on 0.40.0 @4f990aa2c):

```vl
/// Follow the source `f` answers for the current `Some`; `None` while the outer is `None`.
export impl type S: Source<Option<type T>> {
	fun and_then<U, I: Source<Option<U>>>(self, f: sync |T| I): SignalCell<Option<U>> {
		self.map(|x| x.map(f)).flatten().map(|x| x.flatten())
	}
}
/// A dynamic dependency with no option in it — Rx's `switchMap`.
export impl type S: Source<type T> {
	fun switch<U, I: Source<U>>(self, f: sync |T| I): SignalCell<U> {
		self.map(f).flatten()
	}
}
```

`and_then` RUNS correctly today as a userland blanket (alice → `?` on a switch to an empty inner → `bob` when that inner fills → `?` on outer `None` → `alicia` on re-follow, five prints as expected). `switch` compiles to the internal error B371 in the generic body (`self.map(f).flatten()` at an abstract `I: Source<U>`), while the same expression at a concrete type with the result annotated runs — the std lane either lands B371 first or writes `switch` directly over `on_change` (which is what the total `flatten` does anyway, so the direct form is also the cheaper one: ONE derived cell, not two).

**Why `and_then` is the right primitive and not a special case.** Signals are TOTAL — `get()` always answers — so the partial operations (filter, `.some()`) are the ones that cannot exist on a `Source<T>`: there is no value to hold while the predicate is false. `Option`/`Result` solve partiality by making absence a value, and `Source<Option<T>>` is exactly the total encoding of a partial signal — which is why kolt's model layer is `SignalCell<Option<X>>` throughout. `and_then` is the Kleisli composition of that encoding, the same reason `Option::and_then` exists; the owner's `.some().and_then(fetch)` is `and_then(fetch)` on the total encoding with nothing lost.

**Kolt after.** channel.vl:41 → `let author = message.and_then(|m| m.author.user());`. model.vl:130's `map_safe` → `get_client().and_then(|client| client.get_message(id))` (the impl block on `SignalCell<Option<KoltClient<…>>>` keeps `get_safe` only). model.vl:110 `get_channels` likewise.

**Doc work.** The `Option` `flatten`'s doc comment says what it is (`sequence` of `Option` over `Source`, then join) and points at `and_then` as the everyday spelling; the guide's derivations section gets 'static dependency: `map`/`combine`; dynamic: `switch`/`and_then`; `flatten` is what they are built on'.

**Pins.** `and_then` over a source of options: switch of inner, inner update, outer `None` detaches (a later write to the abandoned inner does NOT reach the result), re-follow; `switch` the same without the option; both DERIVATIONS under A110 door 2 (an effect downstream sees the settled value in one wave — pin it with a diamond); the rolling inner subscription released at the ambient owner's disposal (A28's story, inherited from `flatten`); one derived cell per call in the direct form (count via `cell_identity`/`fresh_id` deltas, or the shared census if std's own use grows).
