# F28 — once `[platform(..)]` fences items (F27), should std's LAYERS collapse? Measured on c3f7d1a3: std has exactly ONE twin pair — `std::ui` (browser/ui.vl 1,756 lines, process/ui.vl 757) — and thirteen single-platform layered modules with no twin at all (`dom`, `storage`, `router`, `dev`; `fs`, `http`, `db`, `document`, `rpc_server`, `build`, `watch`, `process`); std uses NO `[platform]` fence anywhere today. The ui twins declare 60 names in common: 19 byte-identical (11 % of the browser twin's code, 21 % of the process twin's — the forms `each`/`each_by`/`each_values`/`when`, `Conditional`, `Each*`, the traits `Slot`/`AttrValue`/`AttrBinding`, `View::attr`/`bind_attr`/`child`), 41 with the same name and a different body, 4 nominals that differ (`View`, `Region`, `Row`, `Swap`), 18 browser-only and 8 process-only

- status: OPEN — filed 2026-09-21 (the owner's question, mid-Order 39); waits on F27 R1 + R3
- kind: design
- area: Native targets & rendering

The integrator's recommendation:

**`std::ui` — YES, and the prize is parity, not lines.** Collapsing saves 11–21 % of the text; what it buys is that the shared surface is WRITTEN ONCE. Today 60 names are kept in step across two files by a gate (`std_twin_parity`) that compares them after the fact, is blind to fields (`Region.anchor` exists in one twin only and nothing objected), and must become N-way the day a native twin arrives (F15). With fenced items the 19 identical declarations simply stop existing twice, and the 41 same-name-different-body items become one name with per-platform bodies.

That needs ONE rule F27 R3 does not yet state: **same-named fenced items must agree on their public signature** — two `[platform]`-disjoint declarations of `View::on` are coherent only if a caller cannot tell them apart by type. That rule IS the parity gate, moved into the compiler, N-way for free, and it covers fields the day a fenced nominal's public fields are part of the comparison (or carry E213's `[internal]`). Without it, collapsing the files would make drift EASIER to write, not harder.

**Shape: one MODULE, not one file.** The browser half is a DOM reconciler and the process half a string renderer; interleaving 2,500 lines of them with a native third would be unreadable. Module directories (A65) already allow `std/src/ui/lib.vl` (the shared surface: traits, forms, the signatures) + `ui/browser.vl`, `ui/process.vl`, later `ui/native.vl`, each with a file-level `[platform(..)]`. Import paths do not move (`std::ui`); nothing is breaking; the corpus, split and SSR-differential goldens byte-identical is the gate.

**The thirteen single-platform modules — ELIGIBLE, low value, do not churn.** `std::dom` could live at `src/dom.vl` under a module-level `[platform("browser")]` and the `browser/` / `process/` directories would disappear — layers-as-directories replaced by fences-as-attributes, one mechanism instead of two. What would have to move with it: `check_library_contract` reads a layer's promise per directory (it would read the fence per module — equivalent), and the editor's `infer_platform` reads 'a module served ONLY by a browser layer is browser evidence' off the directory (it would read the fence — simpler). What it buys a USER: better errors — today a node build does not find `std::dom` at all; fenced, it finds it and reports the coloring chain (F27 R6's 'why'). Rec: only after the fenced `std::ui` has proven the mechanism for an order; and THIRD-PARTY `[library]` packages keep layers as a supported spelling either way (a published library's boundary contract is not ours to delete).

**Timing:** after F27 R1 + R3 build, and BEFORE a native `std::ui` twin is written (F17's conversation) — a third twin is the moment the two-file model triples its cost, and the moment this pays for itself.

Rulings asked: the signature-agreement rule for same-named fenced items (rec yes — it is the point); module-directory shape vs one file (rec the directory); the single-platform modules (rec later, not now).
