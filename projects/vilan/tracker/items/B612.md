# B612 — The `[derive(Wire)]` / `[derive(Hashable)]` field check renders a `dyn` field's type as `_` — "field `source` of `[derive(Wire)]` type `Holder` is `_`, which is not Wire" — and since G25 it follows the derive's own refusal as a second diagnostic about the same field

- status: OPEN — filed 2026-10-12 (fix-51's find, Order 51)
- kind: diagnostics (checker; S)
- area: Diagnostics

The analyzer's derive field check (ledger rows 2 and 3) prints the field's resolved type, and a `Dyn` type renders as `_` there. G25 (fix-51) refuses `[derive(Wire)]`/`[derive(Json)]` over a `dyn` member above the generators, naming the member and its written type; the check still runs afterwards and reports the same field again. Fix: render `dyn Trait<..>` in the check (the type printer's `Dyn` arm), and skip the field check for a derive the expansion already refused (or let the refusal stand alone, B161's one-report rule). Sizing S; analyzer.rs.
