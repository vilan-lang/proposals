# E242 — error spans DRIFT while typing: a diagnostic should stay pinned to the code it applies to until the next paint — typing lines above an error makes it slide up a line

- status: OPEN — filed 2026-10-01 (the owner's item)
- kind: bug (LSP diagnostics; S–M)
- area: LSP & tooling

Observed: with an error showing, inserting or deleting lines ABOVE it leaves the squiggle at its old line/column until the next analysis publishes, so it sits on the wrong code (one line up per inserted line). Expected: between a `didChange` and the next published analysis, every outstanding diagnostic's range is carried through the edit — shifted by the edit's line/column delta when the edit is before it, dropped or clamped when the edit overlaps it — and republished at once (cheap; no analysis), then replaced by the fresh set when analysis lands. Reproduce first: establish whether the stale ranges are the server's (it publishes nothing until analysis finishes, and the client does not track) or a republish of old ranges against the new text; check what E232 built for inlay hints and reuse its edit-mapping. Cover: an insert above, a delete above, an edit on the same line before the span, an edit inside the span, a multi-file diagnostic (an edit in file A must not move file B's), and a slow analysis (the harness from E236 can hold analysis back). Sizing S–M; editor lane.
