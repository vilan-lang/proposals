# B711 — Struct keys: `S.x` as a typed `Key<S, F>`, `~` for the expected type, erased `AnyKey<S>`

- status: PROPOSED - filed 2026-11-05 (kolt)
- kind: language feature
- area: Type system
- paper: `proposal/struct-keys.md`

A value that names a struct field, checked by the compiler, generalizing `TupleKey` from tuples to structs.
- `S.x` (and paths, `S.a.b`) is a `Key<S, F>` that carries the field's type.
- `s[k]` reads in place, and `s[k] = v` writes.
- `~.x` and `~::Variant` take the expected type.
- `AnyKey<S>` is the erased form, for keys known only at run time: `parse`, `all`, `name`, `index`, `typed<F>`, `starts_with`.
- On the wire a key is its index, which needs the contract hash to cover struct layouts (see the paper, §4). Stored data uses names.

Motivation: kolt's reactive-list prototype names changed fields with strings (`slot.edit("status", ..)`), so a typo compiles and leaves a binding silently stale. With keys, those strings become `~.status`. Later stages would let the `PartialEq`, `Json` and `Wire` derives and store projections become library code.

- 2026-11-05 (the integrator, at the sync to main): Synced from kolt-053 with its paper (proposal/struct-keys.md). Notes from the integrator's review of kolt's `planning/proposal/live` (2026-11-05): (a) the paper's §4 claim that A144's contract hash fills each slot with the type NAME and not the struct layout deserves a check on its own - if true, reordering a field of a service struct keeps the hash while the binary codec pairs values with the wrong fields, today, with or without keys; (b) for the reactive list, a key only closes the stale-binding risk if `edit` hands the closure the FIELD (`edit<F>(key: Key<T, F>, change: |&mut F| void)`), not the whole item - with the item, a body can still change a field it did not name; (c) `~` is a new sigil with two meanings (`~.x`, `~::Variant`) - weigh it against inferring the root from the expected type with no sigil.
