# N199 — `dial_cancel`'s hung-dial pins assert that the client's upgrade arrived before the cancel, which a loaded Windows runner does not guarantee

- status: open
- kind: harness (flake)
- area: crates/vilan-cli/tests/dial_cancel.rs

The 300 ms deadline is the program's own clock and the listener's backlog completes the connection before the client writes, so the cancel can beat the first write. Cause not proven from the log (an abortive close discarding unread data would look the same). The `within` pin on node is relaxed; the `service` (explicit cancel) pins and the native legs still assert the upgrade and have the same shape. If one of them flakes, relax it the same way or have the program print a line once the socket has written, and wait on that. Low priority; close at the sweep if no further flake.
