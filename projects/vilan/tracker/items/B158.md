# B158 — a blanket impl (`impl type T with Trait<T>`) is accepted, then ICEs at the first dispatch

- status: OPEN — RULED 2026-08-29: **SUPPORT the blanket impl**, resolved by
  the SPECIFICITY rule (a blanket is the least-specific tier; any
  constructor-headed impl wins where both match; genuinely-overlapping
  blankets with no specificity order are refused at the second declaration,
  named — negation stays out of the grammar). The lane that builds it writes
  the resolution semantics into the traits/generics spec section in the same
  change. Order 22 material; found probing B157, accept-then-ICE until built
- kind: bug
- area: Type system & the type solver
- source: the B157 probes, 2026-08-29

`impl type T with MaybeSignal<T> { fun bind(self, react: |T| void) { react(self); } }`
parses and analyzes CLEANLY when declared and never used (a program carrying
it compiles, exit 0). The first call through the bound —
`fun badge<V: MaybeSignal<str>>(label: V)` called with a `str` — dies with
the internal error: "a call resolved to `MaybeSignal`'s requirement `bind`,
which has no body — … The receiver's type could not be resolved to a
concrete implementation at this call; please report this program" (exit 1).
Reported as the message asks.

Two acceptable fixes, and the choice is a design call B157 carries the case
for: (a) REFUSE the blanket form at the declaration, named ("a blanket impl
over a bare type parameter is not supported; implement the trait per type"),
which ends the ICE today; or (b) SUPPORT it — and the coherence analysis is
already done in B157's terms: the blanket (`V = T`) and a constructor impl
(`V = Signal<T>`) can never overlap at any finite `T` (`T = Signal<T>` has
no solution), so the pair vilan would most want is sound. (b) is what makes
B157's `MaybeSignal<T>` whole — one trait, one blanket static impl, one
generic signal impl — instead of per-type static impls. Whichever way,
accept-then-ICE goes.

**The owner's follow-up (2026-08-29): would a negative bound help —
`impl type T: (not Signal) with MaybeSignal<T>`?** Analysis: it is not
NEEDED for soundness here — the blanket (`V = T`) and the constructor impl
(`V = Signal<T>`) are already disjoint by the occurs-check (`T = Signal<T>`
has no finite solution), so resolution is deterministic at every bound
without any exclusion. The cheaper rule that makes (b) implementable is
SPECIFICITY, not negation: a blanket impl is the least-specific tier, and
any constructor-headed impl wins where both match — which also keeps the
one case negation would DELETE (under a `MaybeSignal<Signal<str>>` bound, a
bare `Signal<str>` is a legitimate STATIC value via the blanket; with
`not Signal` it has no impl at all). And negative bounds carry a standing
ecosystem hazard worth refusing on its own: they invert the "adding an impl
is additive" rule — implementing `Signal`-likeness for a type would newly
EXCLUDE it from every `not`-bound, making impl addition a breaking change
(the reason Rust has refused negative trait bounds for years), which lands
squarely on D5's future compatibility contract. Recommendation: (b) with
the specificity rule; genuinely-overlapping blankets with no specificity
order are REFUSED at the second declaration, named — negation stays out of
the grammar until a case arrives that specificity cannot order.
