# B158 — a blanket impl (`impl type T with Trait<T>`) is accepted, then ICEs at the first dispatch

- status: OPEN — found probing B157's `MaybeSignal` design, 2026-08-29;
  accept-then-ICE, the refuse-or-work doctrine's exact target
- kind: bug
- area: Type system & the type solver
- source: the B157 probes, 2026-08-29

`impl type T with MaybeSignal<T> { fun bind(self, react: |T| void) { react(self); } }`
parses and analyzes CLEANLY when declared and never used (a program carrying
it compiles, exit 0). The first call through the bound —
`fun badge<V: MaybeSignal<str>>(label: V)` called with a `str` — dies with
the internal error: "a call resolved to `MaybeSignal`'s requirement `bind`,
which has no body — … The receiver's type could not be resolved to a
concrete implementation at this call; please report this program" (exit 1).
Reported as the message asks.

Two acceptable fixes, and the choice is a design call B157 carries the case
for: (a) REFUSE the blanket form at the declaration, named ("a blanket impl
over a bare type parameter is not supported; implement the trait per type"),
which ends the ICE today; or (b) SUPPORT it — and the coherence analysis is
already done in B157's terms: the blanket (`V = T`) and a constructor impl
(`V = Signal<T>`) can never overlap at any finite `T` (`T = Signal<T>` has
no solution), so the pair vilan would most want is sound. (b) is what makes
B157's `MaybeSignal<T>` whole — one trait, one blanket static impl, one
generic signal impl — instead of per-type static impls. Whichever way,
accept-then-ICE goes.
