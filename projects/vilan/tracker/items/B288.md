# B288 — a closure's declared return type that reaches a callee generic THROUGH A USER GENERIC STRUCT (`g: |T| Remote<U>`, `|T| Option<Remote<U>>`) neither binds `U` nor is checked against it: `wrap([], |x| Remote { seed = [x] })` leaves the list's element "never determined" (the `[]` seed wins, the closure never refines it), and `let f: List<str> = wrap([], |x| Remote { seed = [x] })` COMPILES — while `|T| Option<U>`, `|T| Option<Option<U>>` and `|T| List<U>` all bind and all refuse the wrong annotation. Kolt hits both faces through its `Task::remote_signal<U>(fallback, |T| Option<RemoteSource<U>>)` hack: `channel.vl:13` annotates `SignalCell<List<Message>>` over a `List<i53>` handle and is accepted; `views.vl:134` cannot drop the annotation at all

- status: OPEN — kolt marker sweep (2026-09-10)
- kind: bug
- area: Type system & the type solver

The closure's expected return type is reconciled against the closure body's type only through std applications (`Option`, `List`); a user struct application (`Remote<U>`) is skipped, so a `U` reached only that way is left to whatever the OTHER arguments bound (an empty `[]` seed: `List<?>`) and a pre-bound `U` (the annotation) is never compared. Descend user struct applications in the closure-return reconciliation exactly as `Option`/`List` are descended (the same walk `reconcile_type` does for arguments); pins: the infer face (`wrap([], |x| Remote { seed = [x] })` then `f[0] + 1` compiles), the refuse face (the `List<str>` annotation is refused naming `Remote<List<i32>>`), and the kolt shape on a generated client (`remote_signal` over a handle with a wrong annotation refused). Probes: scratchpad `kolt-markers/pa2` (free fn + generic-impl method) and `pa4` (real `[service]` client).
