# B652 — String-literal escapes beyond the single-character set reach the JS output with their backslash escaped: `"\x41"` and `"\u{1F600}"` are always emitted `"\\x41"` / `"\\u{1F600}"` (lengths 4 and 9, not 1 and 2), and `"́"` is emitted `"\\u0301"` (length 6) in some files and correctly as `"\u{301}"` in others

- status: OPEN — filed 2026-10-19 (kolt's rich text editor, met writing a grapheme-cluster test)
- kind: miscompile (JS emitter; S)
- area: Language

Spec §2 (lexical.md) says plain-string escapes are "interpreted at code generation with JavaScript string-escape semantics (`\n`, `\"`, `\\`, …)". `\n`, `\r`, `\t` and `\"` are; the hex and Unicode forms are not, consistently.

**Always wrong** (vilan 0.52.0, `vilan build` and `vilan run` alike, standalone or in a package):

```vilan
fun main() {
	print("\x41".len());       // 4, expected 1 — emitted "\\x41"
	print("\u{1F600}".len());  // 9, expected 2 — emitted "\\u{1F600}"
}
```

**Context-dependent.** `"́"` usually compiles to `"\u{301}"` (right), but this standalone file emits `const u = "\\u0301"` (length 6, first code unit 92), and deleting any ONE of the other four `let`s does not fix it, while every reduction of it to `u` alone (with `panic`, with an i-string, with `.code_at`) emits the right literal:

```vilan
import std::io::panic;

fun main() {
	let t = "\t";
	let x = "\x41";
	let u = "́";
	let b = "\u{1F600}";
	let q = "\"";
	panic(i"t {t.len()} x {x.len()} u {u.len()} b {b.len()} q {q.len()} u0 {u.code_at(0)}");
}
```

The second reliable trigger is a package import. In kolt, a `*_test.vl` holding only

```vilan
import std::io::panic;
import pkg::lib::rich_text::style::StyleId;

fun main() {
	let direct = "q́b";
	panic(i"direct {direct.len()}");
}
```

panics `direct 8`; delete the `pkg::` import (any `pkg::` module does it, including one with no string escapes) and it panics `direct 3`. The reading: two emission paths for a string constant, one that decodes the token and one that re-escapes the raw token text — and `\x`/`\u{…}` are missing from the decoder on both.

Workaround in kolt (src/lib/rich_text/document_test.vl): the combining mark is written as the literal character. Doors: decode every JS escape form at lexing (one decoded value, the token's raw text only for diagnostics), or refuse the forms the decoder does not know with a steer. Rec: decode — the spec already promises JS semantics, and a refusal would break the form a JS author reaches for first. Pin both repros above on the JS backend and the native one.
