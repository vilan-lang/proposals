# B432 — the v0.41.0 playground compiler (`vilan-playground-wasm.tar.gz`) ABORTS on every compile — `RuntimeError: unreachable` on `compile("fun main() {}")` — because M44's `base_cache_admit` reads `std::time::Instant::now()` for its build-wait deadline, unguarded on `wasm32-unknown-unknown` where `Instant::now()` panics (no clock without WASI); the v0.23.0 playground crash, again, one function over from the `PhaseClock` that already knows

- status: OPEN — filed 2026-09-27 (the integrator, preparing the v0.41.0 fold); FIX FIRST, then v0.41.1 per releases.md §7.3
- kind: bug (playground wasm; SHIPPED in v0.41.0)
- area: Compiler pipeline & caching

**Repro.** `scripts/fetch-wasm.sh` in the website repo, then under node: `await glue.default({module_or_path: bytes}); glue.compile("fun main() {}")` → `RuntimeError: unreachable`. The symbolized debug build (`cargo build -p vilan-wasm --target wasm32-unknown-unknown` + `wasm-bindgen --keep-debug`) names the chain: `bindings::compile` → `analyze_source` → `analyze_inner` → `analyzer::base_cache_admit` → `<std::time::Instant>::now` → `panic_fmt` → `__rust_abort`. `format`, `format_checked`, `complete` and `version` are fine; the trap is the analysis path only, and every compile takes it.

**Cause.** `crates/vilan-core/src/analyzer.rs:59658` — `let deadline = std::time::Instant::now() + BASE_CACHE_BUILD_WAIT;` and `:59699`'s `saturating_duration_since(Instant::now())`, added by M44 (a cold sibling waits on the thread that claimed the base build). On wasm32 there is ONE thread and no sibling can ever hold a claim, so the wait can never happen — the deadline exists for nothing there and aborts the instance. `lib.rs:1421`'s `PhaseClock` was built for exactly this (dec16c7f: 'the phase marks learn wasm has no clock (v0.23.0 playground crash)'); M44 did not use it.

**Fix (S).** Take the deadline only where a wait is possible: `#[cfg(not(target_arch = "wasm32"))]` around the deadline and the wait arm (on wasm32 an `Absent`-with-a-foreign-claim falls to the build-unclaimed `return (None, None)`), or route the two reads through `PhaseClock`-shaped helpers. Pin: the wasm crate's host test cannot see this (the host has a clock) — the pin is the smoke N134 asks for.

**Why it shipped.** `release.yml`'s `wasm` job and `ci-local.sh wasm` BUILD the artifact and generate the bindings; nothing runs a compile through it. The one gate that does is the WEBSITE's deploy (`smoke-playground.mjs`), which runs at the fold — after publication. It caught v0.23.0's crash pre-publish only because the fold then ran before the publish was announced. → N134.

**Consequence for the v0.41.0 fold.** Steps 6–7 (main, next) are unaffected; step 8 (the book) is unaffected; step 9 (the site deploy) would be REFUSED by its own smoke, so the playground cannot move to v0.41.0. Recommendation: fix on next, cut **v0.41.1** from `release/0.41` (releases.md §7.3: branch from the tag, cherry-pick the fix, tag; merge the branch back into next `--no-ff`), and run ONE fold at v0.41.1. The v0.41.0 release stays published (the native toolchains, the vsix and the npm packages are fine); its wasm asset is the only broken one.
