Reproduced on a scratch copy of kolt with the one-line change: 1 correct arity error, then `channel_component` reads context `app_context`/`owner_scope`/`turn_scope`, so it can't be used as a value (×3 at views.vl:107 — the failed call is read as a VALUE use of the function name) and `context X is read here, but this code can be reached without an enclosing run` ×5 (app_context.vl:44, and FOUR at std reactive.vl:402 for `owner_scope` — the callee's transitive reads, fenced because the callee now has no resolved caller). In isolation (`settings.run(10, || f())` with `f(x)` missing its argument) the arity error stands alone, so the kolt ingredient is the call inside a closure handed to a method (`.swap(get_route(), |route| match route { .. })`) under a component `run` calls. Two fixes, B229's shape: (a) an arity-invalid call is still a CALL of its named callee for the context pass — record it as a call-shaped site (as B229 records run-shaped ones) and never as a value use; (b) a context-reading function whose only callers are invalid calls stands down (no fence for it or for what it reaches) while the program carries the arity error — the invariant for CLEAN programs unchanged; the std-located fences are the same stand-down. Pins: the kolt shape (closure argument under a component under run), the isolated control (arity alone), a genuinely uncovered read still fencing, the value-use refusal still firing for a real value use of a context-reading function.
