# M164 — `std::http` reads every request body whole into memory before the handler runs, with no size limit and no streaming: one large POST (or many) can exhaust the server's memory, and a handler cannot refuse an oversized upload until it has already been received

- status: OPEN — filed 2026-10-20 (kolt's file uploads, `POST /api/upload`, capped at 25 MB by the app)
- kind: robustness / security (std::http; M), feature
- area: std

`http.vl`'s request path (`read_request_bytes`, around :586) buffers the whole body before `on_request`'s handler is called. `Request::bytes()` and `Request::body()` then hand over that buffer. So:

1. **No limit.** Nothing caps a body's size. A client can send gigabytes and the server allocates them. Kolt checks `Content-Length` and then `bytes.len()` against its 25 MB cap, but only after the bytes have arrived, and a chunked body declares no length at all. The RPC POST leg has the same exposure.
2. **No streaming read.** A handler cannot read a body incrementally (hash it, write it to disk or an object store as it arrives), so an upload costs its full size in memory, per request.
3. **No early refusal.** A handler cannot see the headers, decide (auth, `Content-Length`, quota) and answer 401/413 before the body is read. Every rejected upload is fully received first.

Asks, roughly in order of value:
- A server-wide `max_body_bytes` on `ServerBuilder` (a sane default, e.g. 1 MiB), overridable per route or per mount. Exceeding it answers `413` and closes, without buffering the rest. It should apply to chunked bodies as they arrive.
- A way to decide before the body is read: either a pre-body hook (`on_request_head(|RequestHead| Option<Response>)`) or a lazily-read body, so `request.bytes()` reads on first call and a handler that answers without reading never buffers.
- A streaming body reader (`request.body_stream(): Reader` with `next(size): Bytes`, like `std::fs::Reader`), with the limit enforced as it reads.
- Optionally, multipart parsing on top of the stream (the docs only mention multipart as refused on the RPC POST leg).

The response side has the mirror gap: `ResponseStream::send` takes `str` chunks only, so a large file is served from a whole `Bytes` buffer too (`body_bytes`). A bytes chunk on the stream would let file serving stream from storage.
