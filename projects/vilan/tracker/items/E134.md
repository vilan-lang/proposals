# E134 — a struct-init shorthand's two references share one span; the index dedup drops the variable's use (unused-local fade + find-references), and rename at that span serves only one name

- status: OPEN — the owner's find while migrating kolt (2026-09-04); reproduced at 289e2a2b by the triage lane; the one-line widen reds INVARIANT 2 on a std span
- kind: bug
- area: Language server & tooling

`struct A { x: i32 }` / `let x = 1; let a = A { x }; a.x`: references at
the `let x` declaration → only the declaration; references at the
shorthand `x` → answers about the FIELD (three rows); `unused_local_
spans` = ["x"] — the owner's two reports (unused fade; find references
doesn't work) are one defect.

Cause: the AST has no value node for a shorthand field (node.rs
~1099), so the analyzer synthesizes a local READ whose span is the
entry span (analyzer.rs ~23124–23137) and separately records the
field-key reference at the NAME span (~23119, pushed ~33904) — for a
shorthand the identical span. The index builds two rows
(`Definition::Field` and `Definition::Entity(local)`) at one (source,
span) and `rows.dedup_by(source, span)` (references.rs ~528) drops one;
Field sorts first, so the local's only surviving row is its
declaration: find-references returns just that, and
`unused_local_spans` (document.rs ~3583, `occurrences_of(..).all(is_
declaration)`) fades it.

Widening the dedup key to include the definition fixes both halves in
the lane's repro — but it is NOT shippable: it reds
`no_two_indexed_occurrences_share_a_span` (INVARIANT 2, references.rs
~861), and reds it on a STD source (549..551 at SourceId(11)) — there
is already another span claimed by two definitions that today's dedup
silently discards; find that one too. Recommended (M): keep invariant
2; make the shorthand's field-key row carry the local it also reads
(an `Occurrence` co-reference or a shorthand table) so `occurrences_of
(local)` and the unused check see the use while `at` returns one row;
and make RENAME REFUSE at a shorthand span from either side — rewriting
the shared span serves one of the two names; a correct rename must
expand to `A { x = value }` (renaming the field today already silently
breaks such a site). Order-dependent (the parse-fmt-diag lane): with the struct declared
AFTER the function nothing fades but references on the shorthand
return the local's rows instead of the field's — the tie falls to
`Definition::sort_key()` (references.rs ~79), entity-id order, i.e.
whichever of the struct or the local was walked first; one row is
always destroyed. The dedup's stated reason ("a struct rename emits
each constructor site twice and the client rejects the whole edit as
overlapping") belongs at the rename emitter, not the index.

third reads this index), the kolt.local 002/003/034 lineage.
