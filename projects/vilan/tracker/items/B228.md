# B228 — a ZERO-argument method call anchors its arity diagnostic on the DECLARATION, so a std callee's error renders against std's file at the caller's offsets (`<div .styled() />` looks undiagnosed)

- status: OPEN — the owner's find while migrating kolt (2026-09-04); reproduced at 289e2a2b by the triage lane
- kind: bug
- area: Type system & the type solver

The owner: no diagnostic for `<div .styled() />` though `styled` takes
an argument. The arity IS checked: "`styled` expects 1 argument, but
got 0 instead: `style: Style` is missing" — rendered with its caret on
an unrelated line of std's browser/ui.vl (~120, `"feFlood" => true`) and
the owner's file never named, so it reads as absent. Same for a
hand-written `view("div").styled()`; not element-specific. Too-many
arguments on the same std method and any arity error on a same-package
callee render correctly (they take the `CallSubject` path).

Cause: `Constraint::MethodArgCheck { argument_ids, member_id, .. } =>
argument_ids.first().copied().unwrap_or(*member_id)` (analyzer.rs
~2279) — with ZERO arguments the anchor degrades to the declaration;
`attribute_diagnostics_to_anchor` (~28893) then stamps the diagnostic's
source as std's file while `error.span` still holds the caller's byte
offsets (`Span` carries no file, span.rs ~17); the "declared here" note
is std-sourced too, so the CLI folds both labels into one block
(vilan-cli/src/main.rs ~5896).

Fix (S, low risk): `MethodArgCheck` already carries `call_id` (~2197) —
anchor on it: always caller-side, identical for the non-empty case, and
`redirect_derived_diagnostics` already handles a `DERIVED_SOURCE`
`call_id` from the element desugar. Pin: the primary label's FILE for a
zero-argument std method call (element and plain forms).
