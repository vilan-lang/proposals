# M208 — The editor feels spongy on Kolt: a plan for the language server's latency, in order (measure today's Kolt; M194; the solve per keystroke; the unbuilt speed half of `auto` annotations; caches)

- status: open
- kind: performance (LSP latency; the owner's priority 2026-11-17; an arc with its own measurements)
- area: crates/vilan-lsp, crates/vilan-core/src/analyzer.rs (the checks phase, resolve_world), analyzer/auto_annotations.rs, incremental.rs, scripts/lsp-latency.py; M110, M194, M79, M140, M19, E297, E121, N208; proposal/auto-annotations.md §9 and §13 (S5)

WHAT IS MEASURED: a leaf keystroke on the perf exhibit costs 1,090 ms of CPU to diagnostics (mandate 500), css 1,220 ms, a parse break 1,930 ms, flat since v0.54. WHAT IS NOT: the exhibit is a frozen Kolt from BEFORE its reorganisation (N208); today's Kolt is 161 files and 85,048 lines and has never been through the latency harness, so the figure the owner feels is unknown. Hover, completion and colouring do not type-check and should be instant; if those feel slow too, that is a separate defect to look for (the keystroke path's <10 ms figures are printed by the harness and not carried into any report). THE PLAN, in order: (1) MEASURE TODAY'S KOLT: migrate the harness to the new layout (N208), record the six E121 rows plus the keystroke-path latencies, and take one instruction profile of a leaf keystroke split by phase and pass, so the order below is decided by numbers. (2) M194: derived bodies are never filed, so every checking pass sweeps about 126,000 always-live entities per keystroke; the named next lever, and the same item unparks the lens (A185 S3b). (3) THE SOLVE: `resolve_world` runs per keystroke and its constraint fixpoint is 79 to 96% of that pass (M73, M79); a paper first. (4) `auto` ANNOTATIONS, THE SPEED HALF. B570 shipped S0 to S4 in Order 49: the syntax, stale refused with `--fix`, the editor's on-save rewrite, the `[check] auto = "exported"` opt-in. Its S5, 'M110 S6 reads syntactic interfaces for annotated items', has no record of landing and no trace in `incremental.rs`, `item_records.rs` or `id_windows.rs` (grep 2026-11-17; not read closely enough to be certain). That slice is what turns an annotation into speed: an exported item's interface becomes a function of the PARSE, so 'interface unchanged' is known before the edited module is walked, importers are reused without waiting, and a half-typed body no longer moves the interface (paper §9.2: 10% of a recorded Kolt session's keystrokes re-walked 12 modules for that reason; 57% of the owner's body edits were in functions with an inferred return). And Kolt has not opted in: 4 `: auto` sites, no `[check] auto` in its manifest; the paper counted 54 exported annotations the opt-in would write. So: build S5, then opt Kolt in and measure both steps. (5) CACHES: the base-cache budget of 192 MiB no longer holds two Kolt worlds at about 74 MB each (M140); an unchanged package module is re-analysed per round (M19). (6) WHAT TO PROMISE while an analysis runs: publish the edited item's diagnostics first (E297, an owner question). Each step lands with its row re-measured on the SAME exhibit; the mandate row stays the arc's test.

2026-11-18 (the integrator; lane incr-58 stage 1, the owner's 'Yes, start it'): THE DESIGN IS IN AND IT SAYS NO TO THE OBVIOUS MECHANISM. Paper: `proposal/importer-reuse.md` (DRAFT, three decisions for the owner). Measured on a quiet machine: a body keystroke in theme, model or styles with the entry open is 20.9 to 22.6 G and 2,074 to 2,327 ms of analysis CPU; a leaf 10.9 to 12.0 G and 1,165 ms. WHY 'fingerprint equal, reuse the importers' CANNOT WORK AS IS: (1) the stored world is the world MINUS the hot set and nothing can remove a module from a world, so no stored world holds an importer; (2) ids are not stable across a re-walk (a window's start is a running sum; 28% of anchored type mints spill to a shared tail); (3) today's fingerprint is NOT a complete interface: a 24-edit probe found body-changeable facts an importer reads that it misses (which hidden contexts, the retaining summary behind the view-escape check, a generic body's move-cleanliness, const evaluability) and attributes it misses (`[deprecated]`, `[must_use]`, `export`). THE MECHANISM THAT CAN BE SOUND, the STUB SPLIT: walk the edited module's declarations with the prefix, resolve importers against that stub, store, walk its bodies after the store; nothing is removed and no id reused. It is sound only when every item another module can reach has its type written or `auto`-annotated, so it IS `auto`'s slice S5 and it needs kolt's opt-in to help kolt. Prerequisites: a split walk (P1), positions under body edits (P2, the least certain part), and for cold importers an effects audit (P3). Estimated: slice A about 16 to 17.5 G, slice B about 11 to 12.5 G, for eligible modules only; the file-switch miss is NOT helped and memory goes up. A SMALLER WIN NEEDS NO PREREQUISITE (section 9): three costs paid for hot importers (the bound audit at module grain +177 ms, `compute_clone_sites` +94 undiagnosed, the item-record decision +63), about 335 of the 909 ms gap, perhaps 3.5 G, for every module annotated or not: the lane is sent on to build THAT now (no semantic change, under the existing differentials). The stub-split spike waits on the owner's ruling.
