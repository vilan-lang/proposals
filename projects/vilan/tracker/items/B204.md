# B204 — should `panic(…)` count as divergence for the CHECKER (return-position checking, R4/R7), as it now does for paint?

- status: RULED 2026-09-03 — BUILD: `panic(…)` evaluates to a NEVER type that reconciles with any type through erasure (`never + i32 = i32`); the checker agrees with paint (the owner: "I can't think of a situation where it wouldn't"). Ready to queue.
- kind: bug
- area: Type system & the type solver

E114's paint treats a `panic(…)` call (lowers to `throw`) and an
endless `for { … }` as diverging leaves; the checker's
`Divergence` deliberately does not, so `fun f() -> i32 { panic("x") }`
still wants a value after the panic (rpc.vl:308's `0 - 1` exists
for this). Counting `panic` in the checker is a language change:
R4/R7's exemption list and return-position checking. Decide: (a)
panic diverges everywhere (drop the `0 - 1` idiom, pin the
return-position case), or (b) it stays paint-only, documented.

## Ruling 2026-09-03 (the owner)

`panic(...)` should evaluate to a never type that reconciles with any
type through erasure (`never + i32 = i32`) — that is the semantics,
and the checker should agree. Build: a `Never` type in the solver
(or the existing bottom, if one exists) as `panic`'s result; return-
position checking accepts a diverging tail (R4/R7's exemption list
gains it); the erasure rule for `never` in every join (if/else arms,
match arms, operators, `?`-chains). Paint and checker share
`Divergence` already (E114) — the checker's leaf set gains `panic`
and the endless `for {}`. Delete the `0 - 1 // unreachable` idiom
(rpc.vl:308, N48) once it lands, and pin: `fun f() -> i32 {
panic("x") }` compiles; `let v: i32 = if c { 1 } else { panic("no") }`
compiles; `never` never reaches emission as a value.
