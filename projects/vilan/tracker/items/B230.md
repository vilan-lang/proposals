# B230 — `?` inside a `let` initializer double-wraps: `let v = probe()? > 0; Ok(v)` returns `Ok(Ok(true))` and an `Err` becomes `Ok(Err(..))`, never propagated (RELEASED MISCOMPILE)

- status: OPEN — found by lane b224 (2026-09-04) at 289e2a2b; reproduced with no `&&` present
- kind: bug
- area: Type system & the type solver

`fun check(): Result<bool, str> { let v = probe()? > 0; Ok(v) }` emits
`$a = [0, $b[1] > 0]` in the good branch and `$a = $b` in the bad, then
`const v = $a; return [0, v]` — success is `Ok(Ok(true))`, and an `Err`
from `probe()` becomes `Ok(Err("boom"))` and is never propagated. The
`?`-lift wraps the WHOLE initializer expression's value as if the
initializer were the function's return, instead of assigning the
unwrapped payload to `v` and returning early on `Err`. Sibling: `flag &&
probe()? > 0` also runs `probe` unconditionally — the same lift
restructures ABOVE the `&&`, so B224's short-circuit fix cannot reach
it; both belong here. Repros: scratch `b224out/p_try2.vl`, `p_try3.vl`
(lane b224). Fix: the `?` lowering inside a `let` (and any non-return
expression position: an argument, a field, a condition) must emit the
early `return` of the `Err` and bind the payload — find how `?` is
lowered in return position (transformer.rs, grep `Try`) and the
statement-position slot it needs; with B224's `Sequence` node landed,
the conditional operand case has a statement slot to use. Pins must RUN
under node (`assert_compiles_and_runs`): the `let` form on Ok and on Err
(the Err propagates), an argument position, a condition position, the
`&&` sibling with a side-effecting probe, and the return-position
control. Corpus goldens: any `?` in a non-return position in the estate
is affected — census the corpus and std for the shape and expect those
goldens to move (each byte explained). Family: miscompile.
