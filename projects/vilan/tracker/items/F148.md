# F148 — On Windows, a `Keys` whose task a nursery CANCELLED does not free the next `keys()`: the native run of `process::a173_s2_a_dropped_or_cancelled_keys_frees_the_next_one` prints `opened after an explicit drop` and `held`, then never `opened after a cancelled task's keys` (CI's windows leg; every unix leg and the JS side pass)

- status: OPEN - filed 2026-10-27 (the integrator, Order 55: CI's windows leg on next @6e9f5d57 after std-55b's merge)
- kind: native (Windows; vilan-rt-term / the executor's cancel path)
- area: Native targets & rendering

A173 S2 (std-55b, Order 55) built `vilan-rt-term` with a `#[cfg(windows)]` module that was compiled and lint-checked here (`scripts/ci-local.sh windows`) and first RUN by CI's windows leg, which found this. Over a pipe (CI has no console) the one-at-a-time rule is the observable: a `Keys` that did not drop makes the next `keys()` panic or park. The explicit drop frees the next one on Windows too; the cancelled task's `Drop` does not - the cancellation's unwind on the Windows native build, or `vilan-rt-term::leave` under the Windows console branch when stdin is a pipe, is the suspect. The pin is `#[cfg_attr(windows, ignore = "F148: …")]` until a Windows box runs it (CLAUDE.md: a Windows-only verdict is CI's). Rec: a native lane with a Windows box or CI-driven probing; size S-M.
