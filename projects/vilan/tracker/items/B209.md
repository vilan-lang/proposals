# B209 — `for x in tuple` exists undocumented and binds `x` as `any`: a write through `&mut` is silently discarded, `let s: str = x` is accepted

- status: OPEN — paper lane b183-paper-2's find (2026-09-03); MISCOMPILE family; Order 26 lane b209-b210 (added 2026-09-03) builds the CONSERVATIVE fix now — the loop is REFUSED with a steer — shaped so an unroll can replace it if the owner's answer to tuple-comprehension.md §R8 Q2 is 'unroll'
- kind: bug
- area: Type system & the type solver
- source: `analyzer.rs:23891` `iterable_element_type` has no `Type::Tuple` arm, so a tuple takes the `Any` give-up default written for empty lists — while the spec says `any` is produced at host boundaries only

Probed on 0.40.0 (635e3728): `for x in (1, "two", true) { print(x + 1) }`
prints `2` / `two1` / `2`; `let s: str = x` inside the loop is accepted
and prints `undefined`; `for e in &mut xs { e = e + 1 }` compiles,
emits `__replace(e, e + 1)` on a JS number, runs, and DISCARDS the
write. Not a B174 hit (B174 bounds generics; `any` is absorbing by
spec). Fix, per the owner's Q2: UNROLL the loop (per-element typing —
the same per-element elaboration the comprehension's concrete arm
needs; gives fold/reduce/any/all/for_each free) or REFUSE `for` over
a tuple outright with a steer to the comprehension. Either way: pin
the three probes; spec the form or its refusal.
