# A114 — a FIRST-PARTY scoped effect: an effect whose every run gets its own `Owner`, so whatever the body registers — `get_owner().defer(..)`, `take`, a nested `effect`/`map`, a timer it cancels in a cleanup — is torn down BEFORE the next run and when the enclosing owner goes. The owner's ask (2026-09-21), after A113's 'there is no per-run cleanup' row; the pattern is PROVEN in user code on 0fa109eb7 and is what `place_swap` already does privately for a `swap` instantiation

- status: OPEN — filed 2026-09-21 (the owner's ask, mid-Order 38)
- kind: feature
- area: Reactive core & UI

The probe (scratch `effect-cleanup/main.vl`, run on the installed 0fa109eb7) — a free function today, a `Source` member when it lands:

```
fun scoped_effect<T>(source: SignalCell<T>, body: (sync |T| void) context owner_scope) {
	let current: Shared<Option<Owner>> = Shared::new(None);
	source.effect(|value: T| {
		match current.read() { Some(let previous) => previous.dispose(), None => {}, }
		let fresh = Owner::new();
		current.write() = Some(fresh);
		run_with_owner(fresh, || body(value));
	});
	get_owner().defer(|| { match current.read() { Some(let last) => last.dispose(), None => {}, } });
}
```

Measured output — `run 1 / inner 1 sees a / cleanup 1 / run 2 / inner 2 sees a / inner 2 sees b / cleanup 2 / run 3 / inner 3 sees b / dispose boundary / cleanup 3`, and nothing after the boundary goes: run N's cleanup and its nested subscription are gone before run N+1's body, the last run dies with the enclosing owner. It is only crash-safe with Order 38's A110 door 1 (a disposed observer never fires).

Design points: (1) SURFACE — a `Source<T>` trait default beside `effect` (`scoped_effect` / `effect_scoped` — name to rule; A99's naming argument applies) and its `_on_change` twin (no immediate call); both twins of `std::ui` get it for free (it is `std::reactive`). (2) A fresh `Owner` per run is forced by B291 (an owner is single-use); the cost is two `Shared` boxes per run — MEASURE against `shared_census` and the per-wave Ir, and consider an owner that can `reset()` (A87 `Owner::release` declined this; A111's suspend/resume wants the same verb — design the three together). (3) `on_cleanup(|| ..)` as SUGAR for `get_owner().defer(..)` — inside a scoped effect it is per-run, inside a plain boundary it is per-boundary: one name, the ambient owner decides; is that clarity or a trap? (4) ORDERING under A110 door 2 (ruled: nested forms parent-before-child): the per-run owner's children are created by the run, so they sort after it — state it and pin it. (5) A throwing body: the fresh owner is already installed in `current`, so the next run (or the boundary) still disposes what the failed run registered — pin it (B292's drain exception safety is the neighbour). (6) `RemoteSource` leases taken inside a run release at the run's end — the demand-decides rule (R3, Order 31) composes; pin one. (7) What `swap`/`when`/`each` should be REBASED on it (they hand-roll the same dance in `place_swap`) — one mechanism, not two.

Pins owed: the probe's exact sequence as a `reactive_lifetimes` case (inline and in a turn); disposal count equals creation count after N runs + boundary disposal; the throwing-body case; the lease case; a docs section in guide/reactivity.md beside A113's 'who cleans up what' table. Answers A113's second ruling question (a per-run cleanup hook): this item is the proposed YES.
