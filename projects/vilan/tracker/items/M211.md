# M211 — `std::key` in the prelude costs every program about 4.7 M instructions of `vilan check` (+1.86 % on a tiny program, +0.46 % on the website): load it only when a program writes a key or names `Key`

- status: option 2 LANDED on `next` locally 2026-11-27 (lane `m211-key-on-demand` @e8a8b3c7, eleven commits, merged @84ba1621; NOT pushed, not released); the `std::tuple` share (about 1.2 M) stays - filed 2026-11-26 (measured by lane `keys-s1a`, B711 S1a); the cost was accepted for now by the owner 2026-11-26, and option 2 started on his word 2026-11-27
- kind: performance (compile cost of an ambient std module)
- area: std loading (the prelude), crates/vilan-core/src/analyzer.rs

`Key` is ambient (the struct-keys paper: "nothing to import"), so `std::key` loads for every program. Measured with `perf_count.py`, medians of 5 warm `vilan check` runs:

| Subject | Before | After | Change |
|---|---|---|---|
| A tiny program | 253.01 M | 257.71 M | +1.86 % |
| The website | 8,043.5 M | 8,080.5 M | +0.46 % (inside run-to-run noise) |

Where it goes, each std variant swapped in under one binary:

| Variant | Cost over a std without the module |
|---|---|
| The analyzer change itself (no module) | +0.43 M (+0.17 %) |
| The file on disk, not in the prelude | 0: a module nothing imports is never loaded |
| The three structs only, in the prelude | +0.28 M |
| The full module (7 impl blocks, 15 functions) | +4.0 M |
| The full module with its three loop bodies stubbed | +2.4 M |

So the cost is the impls and functions, not reading or registering the module, and it does not depend on which module they live in. The floor with free bodies is about +1.3 %.

It does not turn a gate red today: the CI budget rows sit 4 to 5 % under their ceilings (`example:math` x0.959 against a limit of x1.005), and the absolute cost is about 1 ms.

Options:

1. Accept it. About 1 ms per check; it is the price of an ambient name with methods.
2. Load `std::key` on demand: when a program writes a key literal or names `Key`. Programs without keys then pay only the 0.17 % analyzer change. Needs on-demand std loading and finding `Key` before name resolution has seen the module. The same mechanism would serve any later ambient std type (`MaybeKey` in S3 will add to this cost).
3. Make the `KeyPath` / `KeyStep` methods compiler intrinsics: saves at most about 1.6 M plus part of the per-function cost, and both backends carry more emitter code.

Rec (the integrator): 1 now, and 2 before S3 adds `MaybeKey` to the same module, since S3 will raise the figure and every program pays it.

What it is. The preludes still list `Key` (`export import pkg::key::Key;`), but that re-export no longer loads the module. The loader seeds `std::key` off the program's syntax, through the collector that already seeds `std::task` for `async` and `std::web::style` for a `css` block, so the world key, the std prefix and the hot sets all see one answer. A file seeds it when it writes:

- `Key`, `KeyPath` or `KeyStep` as a bare name, unless that body declares or imports the name itself;
- a field read whose subject is a name or path that does not start with a lower-case ASCII letter (`Task.title`, `model::Task.title`, the half-typed `Task.`);
- a lower-case struct with fields, or an import that binds a lower-case alias to a name that is not lower-case;
- a `[field_syntax]` method.

It is asked of the entry, every package and dependency module, a dependency's `lib.vl` surface and macro or derive output. Std files are not walked: a std module that needs keys imports `std::key` by path (the store does), and the unit test `std_modules_import_the_key_they_seed` holds every std file to that. Loading on first need during analysis was rejected: the analysis runs over a world already loaded and often cached whole. If a key literal is ever built with the module absent, the analyzer reports an internal error; it does not compile a different program. Completion still offers `Key` before any use (`Program::prelude_deferred_names`).

Over-approximation: a field read off an upper-case value (`LIMITS.max`), a half-typed `Task.`, a lower-case struct or alias. Across `vilan/test` (165 programs) no program without keys or the store loads the module.

Left open:

- The `std::tuple` share (`TupleKey`'s impls, about 1.2 M per program): its trigger is the `.keys()` call, which syntax cannot identify, so it needs its own module and a different mechanism. Not built.
- **For B711 S3:** the seed's spelling rule covers STRUCT roots. When enum variants become key roots, a lower-case enum must seed the module the way a lower-case struct does.
- The std import index cache now keys on the build id as well as std's content (it could serve another build's index before); old cache files are invalidated once.
- `KeyPath` is not offered by auto-import completion in a program that has not loaded `std::key`, like any unloaded std module.
- A future std file that reads a field off an upper-case name fails the invariant test and is told to import `std::key`; the import is the cost of the spelling rule there.
- Observed, the same before this change: `self[Self.title]` is refused with "cannot index Task": `Self` is not a key root.
- Noted by the lane, not reproduced: a dependency's `lib.vl` surface and macro output are not walked for the older `css`, element and `async` seeds.
- Doc drift, older than this: the prelude table in `docs/spec/names.md` §4.7 omits `Key`, `dbg` and `dbg_stack`.
