# B293 — should `std::router::link` (and the guide's `<a href on:click>` idiom) set `draggable="false"` on in-app nav anchors? A quick click with a little motion starts a link drag and flashes a ghost image; an in-app route link has nothing to drag, and the href stays for middle-click / ctrl-click / copy-link. Filed as a BUG on 2026-09-11 from kolt's Chrome pointer freeze — MISDIAGNOSED the same day (see the status line); what remains is this small UX question

- status: OPEN — re-scoped 2026-09-11: the freeze it was filed from was a WEDGED CHROME INSTANCE, not the arming — the owner's trace showed every drag start in that instance (a text-selection drag from the composer input included) getting `dragstart` then `pointercancel` and never `dragend`; a plain page in the same Chrome was fine, an incognito window was unaffected, and a browser restart cleared it. Nothing in std or the app reacts to a drag. `draggable="false"` only stopped the most common way of starting one. Downgraded from bug to a UX question
- kind: design
- area: Reactive core & UI

`link` sets `draggable="false"` on the anchor it builds (the href stays: middle-click, ctrl-click and copy-link keep native behaviour, only the drag arming goes); the guide's hand-written `<a href on:click>` idiom in `guide/routing` (and wherever the sidebar pattern is shown) gains the attribute with one sentence on why; consider a `View::link_to(route)` chain so an app styling its own anchor gets the attribute without knowing the story. Pin: the built anchor carries `draggable="false"`. The Chrome mechanism is not ours to fix, but a note in the tour's browser-quirks list is owed.
