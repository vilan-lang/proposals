# B293 — `std::router::link` (and the guide's `<a href on:click>` idiom) builds a DRAGGABLE anchor, and a link drag that starts while a quick click's in-app navigation is still settling WEDGES THE TAB in Chrome (Windows, 153.0.8010.37): from then on every drag in that tab gets `dragstart` then `pointercancel` and never `dragend`, and pointer input stays dead (hover, `:active`, clicks, native scrollbars) while compositor wheel scrolling lives; a HARD REFRESH keeps the breakage, only a new tab escapes it. Reproducible by the owner: anchors draggable + clicking back and forth between two channels. `draggable="false"` removes the trigger and costs nothing (middle-click / ctrl-click / copy-link keep native behaviour)

- status: OPEN — kolt investigation (2026-09-11). RECORD: filed as a bug from the freeze; re-scoped to a UX question the same day when a plain page and an incognito window were fine and a restart cleared it (a wedged instance); RESTORED to a bug hours later when the owner reproduced the trigger at will and showed the wedge is PER TAB (survives a hard refresh, a new tab is clean) — a link drag during settling navigation churn is what wedges it. Chrome's bug to fix; std's to stop triggering
- kind: bug
- area: Reactive core & UI

`link` sets `draggable="false"` on the anchor it builds (the href stays: middle-click, ctrl-click and copy-link keep native behaviour, only the drag arming goes); the guide's hand-written `<a href on:click>` idiom in `guide/routing` (and wherever the sidebar pattern is shown) gains the attribute with one sentence on why; consider a `View::link_to(route)` chain so an app styling its own anchor gets the attribute without knowing the story. Pin: the built anchor carries `draggable="false"`. The Chrome mechanism is not ours to fix, but a note in the tour's browser-quirks list is owed.
