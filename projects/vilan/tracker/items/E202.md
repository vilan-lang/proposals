# E202 — typing `<` does not place its `>`: `editors/vscode/language-configuration.json` declares auto-closing pairs for `{}`, `[]`, `()` and `""` only, so `List<`, `Map<`, `fun f<` and an element head `<div` are each closed by hand. The owner's ask (2026-09-21): pair `<` with `>` AT LEAST in type context. The hazard is the comparison operator — `a < b` must not grow a `>` — and a static `autoClosingPairs` entry cannot tell the two apart (its only filter is `notIn: [string, comment]`)

- status: OPEN — filed 2026-09-21 (the owner's ask, mid-Order 38)
- kind: editor
- area: LSP & tooling

Doors: (1) a plain `{ "open": "<", "close": ">", "notIn": ["string", "comment"] }` plus `autoCloseBefore` — cheap, but fires on every comparison; VS Code's type-over (typing `>` over the placed one) and its delete-the-pair-on-backspace soften it, they do not remove it; (2) the pair placed by the SERVER where the position is provably a type or generic-parameter context — `textDocument/onTypeFormatting` on `<` (the syntax-only window E121 §2.1 already parses per keystroke knows whether the token before `<` is a type name, `fun name`, `impl`, `struct`/`enum`/`trait` head, or a `::` path head) returning the `>` as an edit with the cursor left between; element heads (`<div`) are a separate question — the closing TAG is the useful completion there, not `>`; (3) both: (1) for `surroundingPairs` only (select text, type `<`, get `<text>` — no comparison hazard), (2) for typing. Rec: (3). The playground (Monaco/CodeMirror, whichever K-section item owns it) and the Zed/other-client story follow the server half for free.

Pins owed: `let x: List<|` places `>`; `fun f<|` places `>`; `Option<i32>::Some` path head places it; `if a <|` does NOT; inside a string and a comment does NOT; typing `>` over the placed one does not double it (client behaviour — pinned in `vscode_extension` by configuration, as E194 pinned `wordPattern`); `surroundingPairs` carries `<`/`>`.
