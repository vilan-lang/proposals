# A61 — `str::parse_bool` is missing beside `parse_i32`/`parse_f64` (four call sites in kolt's preference decoders) — while the OTHER two conversions kolt hand-wrote, `bool.to_string` and `f64.to_string`, already ship as `Display` impls and can be deleted: the gap is the parse direction plus a discoverability trap on a trait method

- status: OPEN — the owner's kolt TODO/FIXME sweep (2026-09-07)
- kind: feature
- area: Reactive core & UI

kolt/src/prefs.vl:69-93 hand-writes three conversions, each marked `// FIXME: Implement with std.`:

    impl str {
        fun parse_bool(self): Option<bool> {
            match self { "true" => Some(true), "false" => Some(false), _ => None }
        }
    }
    impl bool { fun to_string(self): str { if self { "true" } else { "false" } } }
    impl f64  { fun to_string(self): str { i"{self}" } }

ALREADY COVERED — two of the three, deletable from kolt today. vilan/std/src/display.vl:5-7 declares
`trait Display { fun to_string(self): str }`, with `impl f64 with Display` (:54-58) and
`impl bool with Display` (:60-64), both bodied `i"{self}"` — the f64 one is byte-identical to kolt's, and
`i"{true}"` renders "true". The only real cost is DISCOVERABILITY: `to_string` is a TRAIT method, so a
module that has not imported `std::display::Display` gets "no method to_string" and reasonably concludes std
lacks it — which is precisely the visibility trap display.vl:16-21 already documents for `List::join`, with
an analyzer steer built for that one shape. The same steer should fire for `to_string`; if it does not, that
is the small build hiding in this item.

THE REAL GAP is the parse direction. `parse_i32` and `parse_f64` are `external` methods on `str` that live
in `std::option` (option.vl:292-305, sited there because their return type puts them on the `Option` chain,
per the note at :292-298). There is no `parse_bool`. kolt needs it in four of its six preference decoders
(prefs.vl:28, :40, :46, :52), each of the form `x.parse_bool().unwrap_or(false)`.

PROPOSED: `str::parse_bool(self): Option<bool>` beside `parse_i32`/`parse_f64` in option.vl, accepting
"true"/"false" only — the exact round trip of `Display::to_string`, and what `std::json`'s bool `FromJson`
(json.vl:248-260) accepts. State the three-way idiom in the doc so the next app does not hand-write any of
it: `Display::to_string` going out, `str::parse_*` coming back, `std::json`'s `Json`/`FromJson` for anything
structured.
