# B359 — a trait DEFAULT body's `self.member(..)` is HIJACKED by the implementing type's INHERENT member of the same name: `trait Pusher<T> { fun push(&mut self, v: T) {..}; fun push_twice(&mut self, v: T) { self.push(v); self.push(v); } }` + `impl Bag with Pusher<str> {}` where `Bag` has its own `push` → `push_twice` calls the INHERENT one; and when that inherent is `external` (`impl List<type T> with Pusher<T> {}`) the emit calls a function that was never emitted — MISCOMPILE, `ReferenceError: $b is not defined` at runtime, clean at check

- status: OPEN — filed 2026-09-21 (A112's receiver probe B)
- kind: bug (miscompile) + a ruling
- area: Type system & the type solver

## Measured (vilan 0.40.0, 0fa109eb7)

**Face 1 — the hijack (vilan-bodied inherent).**

```
struct Bag { count: i32 }
impl Bag { fun push(&mut self, value: str) { print("inherent push"); self.count += 1; } }
trait Pusher<T> {
	fun push(&mut self, value: T) { print("trait push"); }
	fun push_twice(&mut self, value: T) { self.push(value); self.push(value); }
}
impl Bag with Pusher<str> {}
fun main() { mut bag = Bag { count = 0 }; bag.push_twice("x"); print(i"count {bag.count}"); }
```

prints `inherent push` ×2, `count 2`. The default body was written against the TRAIT's `push`; which function it calls now depends on names the implementor happens to have. A trait author cannot know them, and an implementor adding an inherent method later silently changes every default that calls the same name.

**Face 2 — the miscompile (`external` inherent).** Same trait, `impl List<type T> with Pusher<T> {}`, `plain.push_twice("x")`: checks clean, emits

```
function $a(self, value) { $b(self, value); $b(self, value); }   // $b is never defined
```

The specialized default resolved `self.push` to `List`'s `external fun push` and then emitted it as a vilan function call by mangled name rather than the external's method form (`self.push(value)`), and nothing emitted `$b`.

**Not affected:** the same call reached through a generic bound — `fun fill<S: Pusher<str>>(target: &mut S) { target.push("g") }` with `fill(&mut plain)` — dispatches to the TRAIT's `push` (probe B's `$d`). So the two routes to one default disagree about what `push` means.

## Ruling asked

Inside a trait default body, what does `self.name(..)` mean when the implementing type has an inherent `name`?

- (a) **the trait's member, always** — `Self` is opaque in a default body; inherent members of an implementor are not in scope there (Rust's rule; what the generic-bound route already does). Rec.
- (b) inherent wins, as at an ordinary call site — then Face 1 is as designed and only Face 2 is a bug; but defaults become implementor-dependent and the two routes must be made to agree the other way.

Under (a) both faces close in one fix (the default-body receiver resolves against the trait's member set before specialization looks at the concrete type). Under (b) Face 2 still needs the emit fix: a specialized default that lands on an `external` member must emit the external's call form.

## Pins owed

- Face 1's program prints `trait push` ×2 (under (a));
- Face 2's program runs, and `List`'s own `push` is NOT what `push_twice` reaches (under (a));
- the generic-bound route and the direct route print the same thing;
- an ordinary call site `plain.push(..)` still reaches the inherent member (inherent-wins is unchanged OUTSIDE default bodies).

Relatives: B205/B216/B243 (default-body `Self` specialization), B254 (dispatch candidates by name across same-named members).

- 2026-09-21 (Order 38 GO): R1 RULED (a) — inside a default body `self.name(..)` is the TRAIT's member, always; inherent-wins is unchanged outside default bodies. Lane solver-38 (TOP).
