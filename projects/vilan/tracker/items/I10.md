# I10 — consider whether the hash maps and sets should accept an INJECTED ORDERING STRATEGY (to order items within the collection arbitrarily): today iteration order is whatever the backend's structure gives — JS `Map`/`Set` iterate in INSERTION order, a native `HashMap` in none — which is a parity hazard the differential should pin before any strategy is added; the ask is a per-collection order (insertion, sorted by key with a comparator, or a caller-supplied rank) chosen at construction rather than by sorting on every read

- status: OPEN — filed 2026-09-28 (the owner's item, at Order 43's GO)
- kind: design (S–M)
- area: Collections

Doors: (a) one type, a strategy parameter with a default — `HashMap<K, V, O = Insertion>` where `O: Ordering<K, V>` supplies `place(key, value) → rank` and the collection keeps a rank index beside the hash index (every insert pays the index; reads are ordered for free); (b) separate types — `HashMap` (unordered, but insertion order PINNED on both backends via an index map natively, so programs port), `BTreeMap`/`SortedMap<K: Ord>` (ordered by key), and an `OrderedMap` with a comparator; (c) no strategy in the collection — `entries().sorted_by(..)` views, cached with `.cell()` where hot. Rec: FIRST pin insertion order as the contract of the hash types on both backends (the native side moves to an insertion-ordered map — a differential fix, S); THEN (a) as the paper, since a strategy at construction is what the owner asked for and (b) multiplies types; (c) is what exists and stays the answer for one-off sorts.
