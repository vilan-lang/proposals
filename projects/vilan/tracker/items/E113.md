# E113 — file-mode and the LSP color a module by `default-entry`, not by the entry that reaches it

- status: OPEN — the owner's persistent kolt report (2026-09-01); FIX-NOW lane
- kind: bug
- area: LSP & tooling
- source: the owner: `self.element` in interact.vl's `impl View` drew "struct 'View' has no field 'element'"; persistent in the editor, absent from `vilan build`

The diagnosis, reproduced: kolt is fullstack with `default-entry =
"server"`. interact.vl is reached ONLY from the client entry
(browser), and `vilan build` colors it browser — the per-leg compiles
are clean. But `vilan check <FILE>` (G20's new manifest adoption) and
the LSP adopt THE MANIFEST'S DEFAULT platform, so the module analyzes
under the PROCESS overlay, where `View` is `{tag, attributes,
children, text}` — no `element` — and every browser-only module in a
fullstack app cries wolf in the editor.

The fix: color the module by REACHABILITY, the way the build already
does — reuse platform_color's per-entry reachability over the
package; a module reached by exactly one leg gets that leg's color; a
shared module gets whatever the build's shared-by-construction rule
gives it; an unreached module falls back to default-entry (say so in
a note if cheap). File-mode and the LSP take the same answer from the
same machinery — G20 unified them, which is the right shape; it just
unified them on the wrong input.
