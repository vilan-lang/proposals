# B229 — an unresolved value argument silently deletes the `run` site: every context read then fences, burying the real initializer error; and the 'flows through this call' note spans the whole receiver chain

- status: OPEN — the owner's find while migrating kolt (2026-09-04); both faces reproduced at 289e2a2b by the triage lane
- kind: bug
- area: Type system & the type solver

The owner: "context threads through this call" underlines the entire
component body; and when the context IS supplied but incomplete (a
field added to the struct, not the initializer) it complains EVERYWHERE
that the context doesn't exist.

(b) exact: add `density: i32` to `AppCtx`, initializer untouched → FOUR
errors: three `context 'app_ctx' is read here, but this code can be
reached without an enclosing 'run'` (one per read) and, LAST, the real
`AppCtx expects 2 fields, but got 1: 'density' is missing`. Bisect: a
wrong field TYPE cascades nothing; an unrelated type error cascades
nothing; a field ARITY mismatch (missing or extra) cascades, as does any
unresolved value (`run(missing_fn(), ..)` → the same three). Cause:
context.rs ~352–419 collects `run` sites via `call_target` (~187), which
needs the call's subject resolved to `Expr::Local(run_fn)`; an
unresolved argument leaves the method unselected, the site is never
recorded, `bound` stays empty, every strict `get` fences (~1287);
`post_analysis_passes` runs `thread_contexts` unconditionally (lib.rs
~766) with no gate on `program.diagnostics`, so a program that never
type-checked still gets a full coverage verdict. Fix (M, medium): record
`run`-SHAPED call sites whose target failed to resolve and suppress
fencing for the contexts they name (preferred; the initializer's error
stands alone), or gate the `errors` push on a clean program — the pass
must still run its rewrite, and "an uncovered read is a compile error,
not a silent miscompile" must not weaken for clean programs.

(a) weaker than reported: plain hops are tight (`label()`, `print(
component())`), but a METHOD-call hop takes the whole receiver chain's
span — `root = root.child(row` / `.render_body())` underlines both
lines; in kolt the receiver chain is the component's body. Cause:
context.rs ~1249–1259 builds the note from `span_of(program, hop.call)`
(~297), the call's full span; the analyzer keeps the precise callee
span in `member_name_spans` (analyzer.rs ~2857) and this does not
consult it. Fix (S): anchor on `member_name_spans`, fall back to
`span_of`. Scratch: `triage27/parse-fmt-diag/issue5d.vl`, `issue5f.vl`.
Related: B146 (same check, its dispatch refinement), E78/E74 (closed;
the trace/anchor work this modifies).
