# E356 — Calling an `own self` builder as a statement drops what it built, without a word

- status: OPEN - filed 2026-11-02 (kolt)
- kind: diagnostic
- area: Checker / diagnostics

A builder method that takes `own self`, changes a field and returns `self` can be called as a statement, its result thrown away. The variable it was called on is still usable afterwards and still holds the value from before the call, so the change is lost and nothing says so.

Kolt hit this three times. Its `Overlay::on_close(own self, fn): Overlay` was called as `modal.on_close(|| controller.refocus());` in two editor dialogs and once more in new code, and none of those hooks ever ran. The new one, where closing a dialog had to cancel work in progress, is how it came to light. The fix was `let modal = Overlay::modal(...).on_close(...)`.

Repro (standalone): kolt session scratchpad `ownself/main.vl`, the whole file:

```
struct Dialog {
	title: str,
	on_close: Option<|| void>,
}

impl Dialog {
	fun on_close(own self, fn: || void): Dialog {
		self.on_close = Some(fn);
		self
	}

	fun close(self) {
		if self.on_close is Some(let fn) {
			fn();
		}
	}
}

fun main() {
	let dialog = Dialog { title = "Link", on_close = None };
	dialog.on_close(|| print("closed"));
	dialog.close();
	print("hook kept: " + (dialog.on_close.is_some() then "yes" else "no"));
}
```

Prints `hook kept: no` and never `closed`, with no warning on 0.53.1 or `next` (f9fcc6ce).

Recommendation: warn when the result of a method taking `own self` is discarded and the result's type is the receiver's own type. That is the builder shape, where the caller nearly always meant to keep the result. Something like "`on_close` takes `dialog` and returns the changed value; this result is discarded, so the change is lost. Assign it: `let dialog = dialog.on_close(...)`". A general opt-in marker (`[must_use]`) would cover other cases, but this shape is common enough to be worth catching without one. A related question: whether `dialog` should still be usable after `own self` took it. If calling an `own self` method moved the value out, using it afterwards would be the error that catches this.
