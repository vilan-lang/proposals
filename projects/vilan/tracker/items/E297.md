# E297 — 'The edited item's diagnostics published first' has no honest reading inside one analysis: the language server publishes a document's diagnostics once, when the world lands (`land_world`), and lsp-latency.py's 'to diagnostics' is the LAST publishDiagnostics — the only earlier publish possible is a PRELIMINARY one after the Class A window, which would drop and re-add the item's Class B/C/post-pass diagnostics (a flicker) unless diagnostics carried their class

- status: OPEN — filed 2026-10-12 (incr-51b, Order 51)
- kind: design question (editor latency; S) — the owner's hope (2) of M110
- area: LSP & tooling

With S7 the edited item's Class A diagnostics are known ~150–200 ms before the analysis ends (the Class B/C whole-program passes and the post passes follow the window). A mid-analysis hook could publish the previous (sticky, E279) set with the edited item's range replaced by its fresh Class A output, then the final set. The harness would not show it (it times the last publish). The flicker: a post-pass diagnostic inside the edited item (an async or platform refusal, a bound refusal) vanishes at the preliminary publish and returns at the final one, unless the analyzer tags each diagnostic with the pass class that produced it and the preliminary publish replaces only Class A rows in the item's range. Recommendation: do not build the preliminary publish; read 'published first' as 'the fixed error clears when the (now shorter) analysis lands', and rule it closed with M110 S7, or queue the class-tagged form after S7b when the analysis is short enough that the two publishes are ~100 ms apart.
