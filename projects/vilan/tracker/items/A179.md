# A179 — A client's `connect_with` can't be timed out: the dial has no deadline and ignores cancellation

- status: OPEN - filed 2026-10-31 (kolt)
- kind: feature (std::rpc client; S)
- area: Reactive core & UI — rpc

`KoltClient::connect_with(url, codec, protocols)` (the generated client's dial, over `dial_for_service_with` → `dial_socket`) returns only when the WebSocket opens or fails. When it does neither — a TCP connect the OS keeps retrying, a proxy that holds the upgrade, a half-open network after sleep — the call hangs for as long as the browser lets it (tens of seconds, sometimes minutes).

An app can't bound it:

- There is no timeout parameter or option on the client or the transport.
- `dial_socket` doesn't take the ambient `CancelSignal`, so cancelling a nursery doesn't abort the dial.
- Racing the dial against `sleep(..)` with `Task::race` inside a `nursery` doesn't help either: the nursery joins every spawned task before it returns, so it waits for the hung dial anyway. Racing outside a nursery leaves the dial running, and if it later succeeds, a second connection is opened that nothing owns.

Kolt meets it in its connect loop (`src/client.vl`, `connect`/`try_connect`): it retries an unreachable server with backoff and shows "Can't reach Kolt" after 4 s, but a hung first attempt holds every retry back until the browser gives up on it. Found by failing the socket in a headless browser (2026-10-31).

Recommendation: either (a) honor the ambient `CancelSignal` in `dial_socket` (close the half-open WebSocket on abort), so the race idiom from `std::task` works as documented; or (b) a `connect_timeout(ms)` on the dial (a `with_timeout` option beside `connect_with`) that fails with a distinct `RpcError::Timeout`. (a) is the general fix and makes every awaited rpc call cancellable the same way; (b) is the convenience most apps want.
