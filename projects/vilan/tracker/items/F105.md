# F105 — A generic enum's variant constructed inside a list inside another variant is refused natively as "a generic type instantiated at `any`" even under an annotation: `let t: Tree<i32> = Tree::Node([Tree::Leaf(1), Tree::Node([Tree::Leaf(2)])]);`

- status: OPEN
- kind: gap (native backend refuses a program the JS backend runs)
- area: Native backend

Repro (vilan 0.44.0 e5e15ca7, `vilan run --backend rust`):

```vilan
enum Tree<T> { Leaf(T), Node(List<Tree<T>>) }
struct Wrapper<T> { inner: T, tags: List<str> }
fun main() {
	let w = Wrapper { inner = Tree::Node([Tree::Leaf(1), Tree::Leaf(2)]), tags = ["a"] };
	print(w.tags.len());
	let t: Tree<i32> = Tree::Node([Tree::Leaf(1), Tree::Node([Tree::Leaf(2)])]);
	print(1);
}
```

native: `the rust backend does not emit a generic type instantiated at any (the site's argument is still open) yet` at `Tree::Leaf(1)` (4:40), and the annotated `let` on line 6 is refused the same way. The JS backend runs it. The inner variant's `T` is grounded only through the outer constructor's list payload, which the native emitter's instance arguments do not follow. Found by debug-47 writing the `dbg` printer's differential fixture (`native/dbg_printer.vl` avoids the nested generic for that reason).
