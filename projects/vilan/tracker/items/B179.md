# B179 — a bounded generic in the NUMERIC position of `+` still miscompiles

- status: OPEN — b176 lane's find (Order 23); pinned #[ignore]d; RULING WANTED
- kind: bug
- area: Type system & the type solver
- source: lane b176, 2026-08-31; pin `a_bounded_generic_added_to_a_number_is_rejected`

`fun bump<T: Add>(total: i32, value: T): i32 { total + value }`
compiles and `bump(1, Point{x=1,y=2})` PRINTS `11,2` — a string typed
`i32`, verified by running it. The square neither B169 (unbounded)
nor B176 (bounded, concatenating) covers: the gate still skips a
bounded parameter in the numeric position.

Not mechanical — B176's concatenation could be ROUTED because a bound
can promise a string form; nothing can promise the right operand IS
`i32` (`Add`'s `B` defaults to Self, the parameter itself). So the
question is a ruling: what may a bound mean on the right of a native
operator? The likely answer is REFUSE (the operand must be converted
explicitly, or the left operand's `Add` must admit the parameter as
its `B`), with wording that names the working spellings. Rule it,
then flip the pin.
