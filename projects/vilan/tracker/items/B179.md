# B179 — a bounded generic in the NUMERIC position of `+` still miscompiles

- status: OPEN — b176 lane's find (Order 23); pinned #[ignore]d; RULING WANTED
- kind: bug
- area: Type system & the type solver
- source: lane b176, 2026-08-31; pin `a_bounded_generic_added_to_a_number_is_rejected`

`fun bump<T: Add>(total: i32, value: T): i32 { total + value }`
compiles and `bump(1, Point{x=1,y=2})` PRINTS `11,2` — a string typed
`i32`, verified by running it. The square neither B169 (unbounded)
nor B176 (bounded, concatenating) covers: the gate still skips a
bounded parameter in the numeric position.

Not mechanical — B176's concatenation could be ROUTED because a bound
can promise a string form; nothing can promise the right operand IS
`i32` (`Add`'s `B` defaults to Self, the parameter itself). So the
question is a ruling: what may a bound mean on the right of a native
operator? The likely answer is REFUSE (the operand must be converted
explicitly, or the left operand's `Add` must admit the parameter as
its `B`), with wording that names the working spellings. Rule it,
then flip the pin.

## RULED 2026-09-01 — REFUSE, by the owner's operand-role semantics

The owner: the `+` belongs to `total: i32` — the right operand must
conform to what `i32.add` accepts, "which should only be numeric
types". Neither `i32 + str` nor `str + i32` works because neither's
`add` accepts the other; `i32 + (T: Add)` doesn't either because `T`
is WIDER than what `i32.add` accepts. This is the principle that
unifies the family: membership in the LEFT operand's admitted set,
provable by bound only where that set is trait-characterizable —
str's renderable set is (B176's render bound proves membership),
i32's numeric set is not (b148's admitted numerics are T+T same-type;
no trait names the set), so EVERY generic right operand of a
numeric-left `+` refuses, with the message naming the working
spellings (convert explicitly, or an `Add` impl whose `B` admits the
parameter). Same frame applied to the generic LEFT operand is B174 —
deferred breaking, because trait defaults write `self.once() +
self.once()` over the trait's own parameter.
