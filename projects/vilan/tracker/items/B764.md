# B764 — Native: an `async fun` called without `await`, bound, and awaited later (`let b = work(); print(await b);`) is refused by rustc (E0277: `i32` is not a future); JS is correct

- status: open - filed 2026-11-26 (the integrator, probing struct keys across `await`; no key involved; reproduced on local `next` @e43933b0, which does not touch this path)
- kind: backend defect (native: a checked program is refused by rustc)
- area: crates/vilan-rust (async calls; bindings of an un-awaited call)

Repro:

```
import std::time::{ Duration, sleep_for };

async fun through(n: i32): i32 {
	await sleep_for(Duration::millis(1));
	n + 1
}

async fun main() {
	let b = through(1);
	print(await b);
}
```

JS prints `2`. Natively the call is emitted already awaited, so `b` is an `i32`, and the later `await b` becomes `(b).await` on an `i32`: `error[E0277]: i32 is not a future`. `let b = await through(1); print(b);` builds and prints `2`.

Not investigated: which side is wrong by the language's rules. If a bare call of an `async fun` is meant to yield the pending value (what JS does, and what `Task<T>`-returning functions spell out), the native emitter must not await at the call when the result is bound; if it is meant to be awaited implicitly, the checker should refuse the later `await b` on both backends. Either way the two backends must agree and rustc must not be the one to say so. Size S once the rule is read out of `docs/spec`.
