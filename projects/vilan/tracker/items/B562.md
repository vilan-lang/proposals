# B562 — a method called on a SCALAR view is refused — `n.abs()` with `n: &i32`, `s.len()` with `s: &str` (a parameter or a closure's) say "a view can't be read as a value here; write `*`" — while the same call on an aggregate view (`p.get()`, `xs.len()`) projects the place, as transparent-references R4 says every `e.method(args)` does

- status: OPEN — filed 2026-10-05 (editor-47's find, Order 47)
- kind: semantics question / false refusal (S)
- area: Type system & the type solver

Repro: `fun f(p: &P, n: &i32, xs: &List<i32>): i32 { p.get() + xs.len().as_i32() + n.abs() }` refuses `n.abs()` only; `fun f(s: &str): usize { s.len() }` and `|s: &str| s.len()` are refused the same way. R4 reads `e.method(args)` for any `e: &[mut] U` as auto-deref to the referent place; R6's uniform `*` is about a view used as a plain VALUE. A by-value `self` receiver on a scalar view is in between: the scalar view is a `(base, key)` pair at runtime (view-invalidation.md §5's 'scalar views don't auto-deref in argument position'), so treating the receiver as an argument is consistent with that representation and not with R4's wording. Either the paper's R4 says 'aggregate' and the refusal is the rule (then the message could name `(*n).abs()`, and the editor's E263 parameter fix could say a body may need it), or the receiver auto-derefs. An owner question first; the fix is small either way. Sizing S.

- 2026-10-05 (the owner, all recommendations accepted): RULED a bug: a method call on a scalar view (`n.abs()` with `n: &i32`) must auto-deref, as transparent-references R4 says.
