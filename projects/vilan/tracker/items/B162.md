# B162 — trait-associated functions: `Signal::new` on the trait, with a default body

- status: OPEN — RULED 2026-08-29 ("should definitely be supported");
  design, paper-shaped with A32
- kind: design
- area: Type system & the type solver
- source: the owner's Signal-trait discussion, 2026-08-29

The ruled ask: a trait may carry associated functions with no `self` —
`Signal::new(value)` called ON THE TRAIT NAME — so the canonical-cell
constructor keeps its spelling while `Signal` becomes a trait. The shape
that serves the exhibit: an associated function WITH A DEFAULT BODY
written in the trait (`fun new(value: T): SignalCell<T> { SignalCell::new(value) }`
— returning the canonical impl), which is a namespaced static, no
dispatch, no receiver — `Trait::func(args)` resolves to the default body
unless design decides impls may override (the paper's call; the exhibit
needs no override). Questions the paper settles: whether an impl can
shadow it; whether a body-less associated function (a per-impl
requirement invoked as `<Impl>::func`) is also admitted or deferred; and
the diagnostic when `Trait::func` is called for a requirement with no
body (today's accept-then-ICE on requirement calls, B158's cousin, must
be a refusal here from day one). Adjacent, NOT covered: associated
CONSTANTS on types (`i32::MAX`'s stopgap) — a sibling in the eventual
static-member design, but consts-on-types and fns-on-traits are separate
features and this item promises only the second.
