# F186 — A development runtime for native programs: run them without the Rust toolchain in the loop, swap changed modules while state survives, so change-to-seen is near instant (the owner's idea: a 1:1 interpreter)

- status: open
- kind: design (native development loop; the owner's proposal; paper + spike before any build)
- area: crates/vilan-core (transformer.rs, interpreter.rs), crates/vilan-cli (hmr.rs, the run command), crates/vilan-rt-gfx/src/host, vilan/std/src/gfx.vl + ui.vl (the `__gfx_*` / `__ui_*` externs)

The idea separates the two jobs the Rust backend does today: release builds (slow is fine, rustc and LLVM stay) and the development loop (speed of change matters, run-time speed does not). THREE DOORS, the integrator's reading, none measured: (A) THE JS BACKEND IS ALREADY THAT INTERPRETER. Vilan has a second backend whose semantics the native differential holds equal to the native one on ~95% of the corpus, with an engine (V8) far faster than a tree walker, and a hot-module path that already preserves state for web programs (`vilan run --watch`, hmr.rs, std::web::dev). A server or CLI program can be developed on node today and built natively only for release. What is missing is the same for a GPU UI program, which is native-only because its host is: `std::gfx` and `std::ui` reach `vilan-rt-gfx` through a narrow set of about 85 host functions. Give the JS emission that host, either as a node native addon over `vilan-rt-gfx`'s host API, or by embedding a JS engine in a `vilan dev` host binary that owns the window, and a UI edit becomes a module swap in a running window. The hard parts: one event loop (winit wants the main thread and the loop; node has its own), handles and callbacks across the boundary, and what state survives a swap (the reactive graph and owners: hmr.md's rules for the DOM twin are the precedent). (B) GROW THE CONST INTERPRETER (`interpreter.rs`, 4,471 lines, runs const evaluation today) into a whole-program one: async, every host binding, the reactive runtime. It is a THIRD execution of the language to hold in parity, and a tree walker is slow where debug rendering is already 5 to 10 times slower than release. (C) A bytecode VM of our own: (B)'s cost plus a compiler to bytecode, for speed V8 already gives. Recommendation: a short paper and a spike of (A): the `ui-counter` example drawn by `vilan-rt-gfx` and driven by its JS emission, one module swapped while the counter keeps its value, with the time from save to pixels measured. That answers whether the loop and the boundary work before anything is designed around them. It also bears on F167's open ruling about optimising the GPU stack in the debug profile, and on MAP.md 13.2: a dev runtime removes the per-project cold build from the loop entirely, so the compile-time levers then matter for release and CI only.
