# B683 — A literal accumulator decides `fold`'s `B` as `i32` before the unannotated closure's body says otherwise - `[1usize, 2].fold(0, |sum, value| sum + value)` is refused "`+` adds two values of the same type, but the operands are `i32` and `usize`"

- status: OPEN - filed 2026-10-26 (solver-55's find, Order 55)
- kind: type inference (checker; S)
- area: Language

B659's neighbour, left out of B659 on purpose: there the generic sat only in the closure's RESULT, so the literal could wait for the closure. Here `B` is also the closure's first PARAMETER, so the closure cannot type without it, and the literal is the only binder (B589 covers the case where the closure's parameters are WRITTEN). The answer would need the body's arithmetic as evidence (`sum + value` with `value: usize` says `B = usize`) - a deferral of the literal's default until the closure's body has typed with `B` open, then a retry. Same on v0.52.0. Workarounds: `0usize`, or `|sum: usize, value|`. Sizing S-M; rec: defer only an unsuffixed literal whose generic the closure's body constrains by an operator against a known width, else keep `i32`.
