# A64 — a style-paper ruling A36 did not cover: should conditional component state COMPUTE a class list per state (`.when` today), or ride CSS variables, or data attributes via the `within`/`child_relation` machinery std already has — the owner's own first use of `when` hit the compound condition and asked, and views.vl runs `when` chains inside a signal `.map` where nobody has priced the per-notify rebuild

- status: OPEN — the owner's kolt TODO/FIXME sweep (2026-09-07)
- kind: design
- area: Reactive core & UI

kolt/src/styles.vl:62-68, on the combinator A36 shipped:

    fun button_style(selected: bool, disabled: bool) {
        button_style_base
            // TODO: Investigate whether these should be computed or css vars or data attributes
            //       (performance? tidiness?).
            .when(selected, button_style_selected)
            .when(!disabled, button_style_interactive)
            .when(!selected && !disabled, button_style_interactive_events)
    }

A36 is CLOSED (tracker archive.md, 2026-09-04, Order 27, lane std-27, vilan bb80ec4f): `Style::when(condition,
delta)` landed as "exactly the ruling's five lines" — vilan/std/src/style.vl:1455-1461,
`if condition { self + delta } else { self }` — with doc guidance that own-flag chains are the intended use,
that "a compound condition is the tell for `match`", and that a later delta wins. The owner's FIRST real use
immediately produced a compound condition (`!selected && !disabled`) and a question the ruling did not reach:
whether a stateful component's style should be COMPUTED per state at all.

THE THREE CANDIDATES, AND WHAT EACH COSTS:

- COMPUTED (today's `when`): each distinct (selected, disabled) pair yields its own class-list string. The
  delta styles are emitted to the sheet once, which is the cheap part; the cost is that the app re-derives
  the string on every reactive read. That is not theoretical in kolt — views.vl:513 and :711 run `.when`
  chains INSIDE a `.map` on a signal, so the rebuild is per-notify, and `class_list` (style.vl:1465) walks
  every slot to join it.
- CSS VARIABLES: one stable class, the varying declarations written as `var(--x)` set per element. Sheet size
  flat, class attribute never changes, cost is one custom-property write per change — but a variable cannot
  vary a SELECTOR-shaped thing, and two of kolt's three deltas are exactly that (`hover`, `active` in
  `button_style_interactive_events`).
- DATA ATTRIBUTES: one class whose rules are conditioned on `[data-selected="true"]`. std ALREADY has this
  machinery — `within(name, value, inner)` (style.vl:1244) and `child_relation` (:1296), both of which check
  the attribute name and value and refuse a media-conditioned inner — and kolt already uses `within` in its
  own `select_off` (styles.vl:18-22) and `child_relation` in views.vl:138. The element's class never changes
  and toggling is one `set_attribute`. The cost is sheet size (both branches always emitted) and giving up
  the "a style is a value you can merge and pass around" property that makes `when` composable at all.

WHAT IS WANTED IS A RULING, NOT A BUILD: which of the three is the IDIOM for boolean component state; whether
`when` stays the answer for it; and whether the compound-condition steer should point at `within` rather than
at `match`. MEASURE FIRST — the per-notify class-list rebuild at views.vl:513 is the exhibit and it has never
been priced. Belongs in the style paper beside A36's record.
