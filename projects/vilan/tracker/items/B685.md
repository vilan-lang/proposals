# B685 — `opt.unwrap_or(&0) + 1` over an `Option<&i32>` that is `None` prints `0,01` on JS and `1` natively - the fallback view's `[cell, key]` pair is handed on as the value

- status: OPEN - filed 2026-10-26 (solver-55's find, Order 55)
- kind: miscompile (JS) - a view fallback at a generic `T` that is a view
- area: Language

Met pinning B649's exemption. `Shelf::count(&self, i): Option<&i32>` answers a wrapped view; B577 made the JS emitter read a SOME payload out where the option is consumed (`unwrap_or`, `map`, `+ 1`), but when the option is `None` the result is the FALLBACK argument, which is itself a view (`&0`, `&zero`) and is not read out, so `+ 1` concatenates the pair. Same on v0.52.0; natively F99 reads both. B649 deliberately leaves the `&` there alone (the parameter's `T` IS a view: a by-value fallback would not type). Rec: the JS emitter reads the fallback out at the same consuming positions B577 reads the payload (transformer, B577's seam); a pin per consumer (`unwrap_or`, `unwrap_or_else`'s result, `+`).
