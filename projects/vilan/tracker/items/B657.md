# B657 — STRUCT UPDATE (`Point { x = 1, ..origin() }`) is not in the language, and the parser never says so: the minimal form reports "unclosed `{` in struct initializer" on a brace that is closed; in a larger literal the errors become "`Hooks` expects 6 fields, but got 0" (five were written) plus "expected `;` to end this statement" at an unrelated line

- status: OPEN — filed 2026-10-19 (kolt's rich text editor: `Hooks { on_key = .., link_decoration = .., ..Hooks::none() }`, a hook record where a host overrides a few of six closures)
- kind: diagnostics (parser; S) + a feature question (the owner's)
- area: Language

```vilan
struct Point { x: i32, y: i32, z: i32 }

fun origin(): Point { Point { x = 0, y = 0, z = 0 } }

fun main() {
	let moved = Point {
		x = 1,
		..origin()
	};
}
```

vilan 0.52.0: one error, "unclosed `{` in struct initializer: expected a matching `}`", spanning the literal. In kolt the same `..base` tail inside a six-field literal of closures produced "expects 6 fields, but got 0 instead: `on_key` is missing" and "expected `;`" at the last field's closure body — neither names `..`. Tuples DO spread (`(0, ..pair, 9)`, spec §5), which makes the struct form look plausible to a reader of the spec.

Two parts. (1) Diagnostics, regardless of (2): on `..` inside a struct initializer, refuse at the `..` with "a struct literal names every field; there is no `..base` update form" (and, until (2) is ruled, a steer: bind the base and assign the fields that change). (2) The feature: `..expr` as the LAST item of a struct initializer, filling the unnamed fields from `expr` (moved/copied per the memory model). The motivating shape is a record of defaults — a hook set, an options struct — where callers override a few fields; today every caller writes every field, or the type grows a builder. Rec: (1) now (S); (2) is a language design call — note that tuple spread already exists, so the syntax has a precedent.

- 2026-10-19 (the owner, on the feature half: open to it): kolt's use case is fully served by `mut hooks = Hooks::none(); hooks.on_key = ..;` (the pattern `TextStyle::rebased` uses), so the feature is ergonomic, not a capability gap: what `..base` adds is expression position (a record built inline as an argument, in a `match` arm or a `then`/`else` branch, without a temporary `mut` binding) and stating "these defaults, except…" as one value. The diagnostics half stands on its own and is the part to do first.

- 2026-10-27 (Order 55 seal sweep): Order 55 (R-e): the struct-update FEATURE (part 2, `..base`) is NOT this order - it waits for a shown need beyond `mut hooks = Hooks::none(); hooks.on_key = ..;` (a paper for Order 56). Part 1 (the diagnostic: refuse `..` in a struct initializer at the `..` with 'a struct literal names every field; there is no ..base update form') was named for parser-55 in the brief's R-e but is NOT in its lane's item list and was NOT built - no B657 commit exists this order (parser-55's B653 notes only that the update form does not exist); it stays an S Order 56 candidate.
