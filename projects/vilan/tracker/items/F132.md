# F132 — Natively an array literal is emitted as `vec![..]` (a List) where its expected type is a fixed array `[T; n]` in two nested positions - a tuple slot of a struct-literal field or of a let used by a call, and a variant payload inside a list literal passed to `print` - so rustc refuses "expected `[i32; 3]`, found `Vec<i32>`"; JS is fine

- status: OPEN — filed 2026-10-11 (debug-50's find, Order 50)
- kind: miscompile (native; S)
- area: Native targets & rendering

Repros: `H { pair = ([5, 6, 7], true) }` with `pair: ([i32; 3], bool)`; `let t: ([i32; 2], bool) = ([1, 2], false); count(t)`; `print([Frame::Empty, Frame::Bytes([0, 0, 0, 1])])` with `Bytes([u8; 4])`. The same literals directly in a call argument or a lone variant constructor emit arrays correctly, so the expected type is lost one level inside a tuple or an element position (array-lengths S1's Type::Array(TypeId, TypeId) may have moved a path). Fix in vilan-rust's literal emission: thread the expected element/slot type through tuple, struct-field and list-element literals. Sizing S; vilan-rust.
