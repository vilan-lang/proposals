# B210 — a tuple receiver resolves no methods at any arity: inherent impls, trait impls and B170's own `Add` impl are all "cannot call method X on (i32, i32)"

- status: OPEN — paper lane b183-paper-2's find (2026-09-03)
- kind: bug
- area: Type system & the type solver

`impl (i32, i32) with Add { … }` (B170) is reached through the
OPERATOR path only; `(1, 2).add((3, 4))` and any inherent or trait
method on a tuple receiver fail method resolution. So "the tuple
suite as methods" is blocked one level BELOW variadic generics (B3),
and tuple-comprehension.md revision 1 under-priced the zip form by
pricing it against a spelling that does not exist. Fix in method
resolution's receiver-type matching for `Type::Tuple` (arity and
element types); pin inherent, trait and operator-trait methods at
two arities, plus a mismatched-arity refusal.
