# E287 — a non-literal array length is answered four poor ways: in TYPE position the parser says "found '[' expected a type" (and the binding cascades "cannot find 'a'"); in a repeat literal the analyzer's refusal is followed by cascades off the substituted length 0 ("index 0 is out of range for an array of length 0 (valid indices are 0 to 0)", "its type is `[_; 0]`"); any suffix makes a length (`[i32; 3f64]`, `[0; 2i8]`); and an empty array's out-of-range message says "valid indices are 0 to 0"

- status: OPEN — filed 2026-10-09 (papers-49's find, Order 49)
- kind: diagnostics (S) — parser + analyzer
- area: Type system & the type solver

(a) `const let SIZE = 4; let a: [u8; SIZE] = ..;` -> "found '[' expected a type in type annotation" plus "cannot find 'a' in this scope" at its use: `parse_array_length` (parsing.rs ~7768) takes only a number token inside `parse_array_type`'s `attempt`, so a name fails the whole `[..]` type and the analyzer's sentence "an array length must be a non-negative integer literal (a `const` length is not supported yet)" (`array_length_literal`, analyzer.rs ~36910) is reachable only from the repeat literal and a fractional length. (b) `[0u8; SIZE]` -> that sentence, then "index 0 is out of range for an array of length 0 (valid indices are 0 to 0)" at `a[0]`; `[i32; 3.0]` -> the sentence, then "this array literal has 3 elements, but its type is `[_; 0]`": the refusal substitutes 0 and every later check believes it (use an error length that suppresses the length checks). (c) `array_length_literal` matches `Node::Number(whole, None, _)` and ignores the suffix, so `[i32; 3f64]` and `[0; 2i8]` are lengths 3 and 2 (admit unsuffixed and `usize` only). (d) `let e: [i32; 0] = []; e[0]` -> "valid indices are 0 to 0" (say the array is empty). Fix: parse a name in the length position and refuse it in the analyzer with one sentence that names what a length may be (array-lengths.md §6 widens that set in S4); no cascade; the suffix rule; the empty wording. Ledger rows. Sizing S.
