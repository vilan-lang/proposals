# B183 — a tuple comprehension: `(item in tuple => EXP)`, and the multi-tuple zip form

- status: OPEN — owner-proposed 2026-09-01; design discussion
- kind: design
- area: Type system & the type solver
- source: the owner, off the B179 operand-role ruling

The owner's sketch: `(item in tuple => EXP)` maps a tuple
element-wise; the multi-tuple form zips — `(a in aa, b in bb =>
a + b)` — which is enough to implement a generic `(a, b) + (c, d)`.
Compile-time expansion (tuples have known arity), so each element's
EXP type-checks at its own element type — heterogeneous tuples work
where the elements do, and the result tuple's shape falls out
per-element. Questions for the discussion: arity mismatch between
zipped tuples (refuse, surely); nesting; whether the binder is a
pattern (`(a, b) in pairs`); interaction with B170's now-reachable
tuple impls (`impl (i32, i32) with Add` could be WRITTEN via the
comprehension — the two features compose into element-wise operator
impls without variadic generics, a slice of B3's territory); and
spelling collision risk with the element-syntax/`in` uses elsewhere
in the grammar (the EBNF gate now exists to keep that honest).

## Paper 2026-09-01 — proposal/tuple-comprehension.md: BUILD, in four pieces

The form turns out to already exist in the language's variadic
machinery; the paper's recommendation is to add the CONCRETE arm as a
second arm beside the mapped one (never one generalized arm — it
cannot preserve `combine`'s emission), with the zip form held behind
B180 (now shipped). Four pieces, each its own lane; awaiting the
owner's go.
