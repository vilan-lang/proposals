# M175 — `SqlValue`: type `std::db`'s bind lists - `List<any>` lets a struct, a list or a tuple through to a run-time refusal (JS) or a rustc error (native) - with what the boundary half taught

- status: OPEN - filed 2026-10-26 (std-55's M165 follow-up, Order 55; R-c)
- kind: API (std::db typing)
- area: Standard library

R-c's typed form. What M165's boundary half taught: (1) the conversion an `Option` and a `bool` need already existed natively in `vilan_rt::Any` and its binder; JS needed the analyzer to record WHERE an `Option` lands at `any`, because the JS value carries no type - so a run-time refusal can name the index but never the vilan type; (2) a bind list is built three ways in the estate (a literal - kolt's 295 sites, `push` onto a `List<any>`, a generic helper - B679), and a trait-typed list catches all three at the checker; (3) `any`'s holdable set (number, str, bool, Option of those) IS the `SqlValue` impl set. Rec: `trait SqlValue` implemented for the integer and float types, `str`, `bool`, `Bytes` (BLOB, new), `Option<T: SqlValue>`; `run`/`all`/`first` take `List<dyn SqlValue>` (or a variadic tuple), a literal's elements erased at the element; the JS binder stays as the host seam; `any` then has no std bind-list user, which lets F150's refusal be stated for `any` everywhere. M. `breaking` only for a program that passes a `List<any>` it built itself (estate: 0 in kolt).
