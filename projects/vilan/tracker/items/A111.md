# A111 — KEEP-ALIVE for `swap` (`swap_cached`): park a swapped-out subtree (its row AND its owner) per key and re-insert it on return instead of rebuilding — the mechanics exist (`cut_row`/`insert_row`, what `each` moves rows with); what does not exist is `Owner` SUSPEND/RESUME, without which a parked subtree stays subscribed: effects run against detached DOM, remote leases never release, and a parked nested `swap` keeps rebuilding. ## What was asked

"Can `Memo` or something else cache the swaps, and how would ownership disposal work?" The example that prompted it did not need a cache — its outer `swap` was keyed too finely; the fix is a projected key (A110 records the ordering hazard that fix exposes). This item is the real keep-alive question, kept separate so it is not built by accident.

## Why `std::memo` cannot do it from app code

`memo.get_or(key, || <div>..</div>)` inside a `swap` render closure builds the view under the PER-INSTANTIATION owner `place_swap` mints — and disposes on swap-out. The memo then answers a view whose bindings are dead. A cache has to be the form's own, because the form is what decides which owner the subtree is born under.

## Shape

`swap_cached(source, render)` (+ a cap): `Map<K, Parked>` where `Parked = { row, content: Option<Element>, owner }`, `K: Hashable + PartialEq`.

- **birth:** the entry's owner is minted per KEY, not per instantiation, and belongs to the ENCLOSING boundary.
- **swap-out:** `cut_row` → keep the extracted content and the owner. Nothing is disposed.
- **swap-in:** hit → `insert_row`; miss → `render` under a fresh entry owner.
- **disposal, exactly two places:** the enclosing boundary's `defer` disposes EVERY entry, live and parked; EVICTION (LRU cap, or an explicit `forget(key)`) disposes one. No cap + a parameterised key (`/user/:id`) is one leaked subtree per id — the cap is not optional.

## The hard part: suspension

A parked subtree's subscriptions are live. Three costs, in rising order:

1. effects repaint detached DOM — wasted, invisible work;
2. a `RemoteSource` lease is DEMAND (A92/A97): parked demand never drops, so every page ever visited holds its channels open until eviction;
3. a parked subtree containing a form on the same source (the nested-`swap` shape) REBUILDS while parked.

So keep-alive wants `Owner::suspend()` / `resume()`: detach every subscription the owner holds (releasing leases through the existing release hook — B283's turn rule applies), and on resume re-attach and re-run each effect ONCE against the current value (the `sub` contract's immediate call is exactly this). That needs a subscription to be re-attachable — today `dispose` is one-way, and C14 S3's `Weak` subscriber list is the handle a re-attach would go through. It also meets A87 (`Owner::release`, declined until a caller appears): this would be the caller, and the two verbs should be designed together.

Open questions for the paper: is a suspended owner's `take` deferred or refused; does `resume` run effects in creation order (A110 door 2's rule); what a suspended `Draft`/`Optimistic` in flight does; whether the process twin (process/ui.vl) gets it at all.

## Rec

Do not build until something measures a need. The honest motivations for keep-alive are STATE the rebuild loses — scroll offset, a half-typed form, a media element — not rebuild cost, and which of those it is decides eviction and suspend semantics. kolt does not ask for it today.
