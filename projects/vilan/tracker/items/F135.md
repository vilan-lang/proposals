# F135 — F129's residue: a LATER argument that REPLACES the copied place whole — `sized(cell.read().items, replace(cell))` with `replace` assigning `cell.write().items = [7, 7, 7]`, `words.measured(swap())` with `swap` re-binding a captured `words` — prints the replaced value natively (copy taken last, F129) and the old one on JS (the argument is the object the place held when it was evaluated)

- status: OPEN — filed 2026-10-12 (native-51's find, Order 51)
- kind: miscompile (native; design question)
- area: Native targets & rendering

F129 (R-h) takes a copy out of a cell AFTER the later arguments, which is JS's answer for an in-place write (push, insert) and the opposite of it for a replacement: JS's argument is a reference to the object the field held at evaluation, so a later assignment of the field detaches it, while the native copy taken last reads the new field. The base (early copy) answered the replacement right and the in-place write wrong; no order of a single copy answers both. The same holds for spec §6.9's views of a captured binding (`w.measured(w.add(..))` with `add` re-binding `w`): the view is taken after, JS reads the old object. Spec §6.7 says `read()` copies, which is the base's answer for both shapes — so the alternative fix is on the JS side (the analyzer copies a `Shared::read()` spine argument when a later sibling argument reaches an in-place write of the cell, as B457 does for a callee).
