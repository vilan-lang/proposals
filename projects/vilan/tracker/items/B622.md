# B622 — `[derive(Hashable)]` over a generic struct refuses its generic fields — `struct Holder<T> { item: T }` is "field `item` ... is `T`, which is not `Hashable`" and `struct Bag<T> { items: List<T> }` likewise — although the derive binds every reached parameter `type T: Hashable` in the impl it writes

- status: OPEN — filed 2026-10-12 (solver-51's find, Order 51)
- kind: analyzer: false refusal (S)
- area: Macros & derives

`check_hashable_boundary` asks `resolved_type_is_hashable` of the field's declared type, and a declaration's own parameter answers false (the oracle reads nominal names, `List`/`Option` and impls). The generated impl's binder bound makes every reached parameter Hashable, so a parameter (and a `List`/`Option`/array of one) the derive reaches is Hashable under the impl — the check should read the field under the derive's binder bounds (the Wire boundary has the same shape to compare against). B611 made the array arm of the oracle read its element, so `Key<const N> { parts: [i32; N] }` works and `Buf<T, const N> { items: [T; N] }` meets this. Sizing S; solver (the checks).
