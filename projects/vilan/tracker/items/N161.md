# N161 — `perf_gate.py ratchet --release` RESETS every `[[bump]]` row, including the `ci`-class bumps the seal's verdict never measures, without absorbing them — so the release commit's own CI perf job goes red on the rows those bumps covered (v0.46.0: math x1.019, watch x1.019, todo x1.005 against ci ceilings whose 1.025/1.01 bumps had just been dropped)

- status: OPEN — filed 2026-10-09 (found at the v0.46.0 cut; Order 49)
- kind: release tooling (S)
- area: Release engineering & beta

The cut runs `ratchet --from <verdict> --release` (N146): a bumped row whose class the verdict measured (reference) gets its ceiling set to the measured count (the bump ABSORBED), then ALL bump rows are reset. The verdict measures the reference class only; the ci class is measured by CI's own job, so its bumps are reset with nothing absorbed, and the first CI run on the release commit refuses. Fix: `--release` resets only the bumps of classes the verdict measured, and leaves the others (or absorbs a ci bump by re-adopting the ci row from the latest green CI measured.json, which the cut could fetch when `gh` is present). At v0.46.0 the integrator re-adopted every ci row from the release commit's own run (the way M126 did) in a follow-up commit and tagged that. A pin: a budgets file with a ci bump and a reference-only verdict keeps the ci bump through `--release`.
