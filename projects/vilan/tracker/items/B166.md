- kind: bug
- area: Type system & the type solver
- source: the owner's DragHandler exhibit + probes, 2026-08-29

The owner found `self.on_drag_move = handler` accepted where the field is
`Option<|DragEvent| void>` and `handler` a bare closure. Probing generalized
it catastrophically: `b.value = "text"` into a PLAIN `i32` FIELD compiles,
and `b.value + 1` prints `text1`; `"text"` into `Option<i32>` compiles; the
bare-closure-into-Option case runs with the `is Some` test silently never
matching. Struct LITERALS check (the same value at construction refuses);
the ASSIGNMENT statement path checks nothing. Every mutation-through-field
in the estate is unverified today. The fix: the assignment path checks the
value against the declared field type like the literal path does — ONE rule,
both doors. Estate census with the fix on (kolt's DragHandler site becomes
the refusal the owner expected to write `Some(handler)` at). Family at fix:
miscompile-shaped per B163's §7.2 reasoning (accepted programs computed with
wrong types); the lane argues it. Pins per shape: scalar, str-into-numeric,
Option field bare value, closure field, nested struct field, index-path
assignment if distinct (`a.b.c = …`, `list[i].f = …`), and the literal-path
control staying green.
