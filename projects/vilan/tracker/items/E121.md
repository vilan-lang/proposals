# E121 — the editor-latency mandate: <10 ms per keystroke for tokens, hints, completion; errors <500 ms, on a large codebase

- status: OPEN — owner-set target 2026-09-01; an ARC (paper first)
- kind: design
- area: LSP & tooling
- source: the owner: "compiler performance at <10ms per keystroke … through whatever combination of caching, debouncing expensive operations, and code rewrites are needed. Semantic highlighting, inlay hints, and auto-complete shouldn't lag even on a large codebase. Errors can lag behind somewhat, but ideally would stay under 500ms for a large codebase/file."

Today (editor-perf, Order 24): a views.vl keystroke costs ~1.8 s to
diagnostics on next (3.7 s on 0.40.0), and every request rides the
SAME whole-program analysis — tokens, hints, completion, and errors
all wait for it. The mandate splits that into two paths:
1. THE KEYSTROKE PATH (<10 ms): parse the edited buffer (the parse
   cache exists), serve semantic tokens and inlay hints from the
   LAST COMPLETED analysis's resolved names re-mapped onto the new
   tree (or from syntax alone where names are unchanged), serve
   completion from a cached symbol index (per module, invalidated by
   the module's own edits) — nothing on this path may type-check.
2. THE DIAGNOSTICS PATH (<500 ms): debounced, cancellable (E117's
   version stamps), and INCREMENTAL — re-analyze the edited module
   and its dependents only, over cached analyses of unchanged modules
   (M19), a base-cache that pkg:: imports do not bypass (M21), and
   whole-program passes (dispatch_refine, const, call-graph — the
   1.2 s "post-passes") either made incremental or memoized on
   content.
The paper (`proposal/editor-latency.md`) measures the per-request
budget with editor-perf's instruments, names the rewrites, and
sequences them; M19/M21/M22 are its first three lanes. Success is
measured on kolt WITH lucide (1,791 functions) as the "large
codebase" exhibit.
