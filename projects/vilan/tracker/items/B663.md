# B663 — A struct literal as a `match` subject (`match Point { x = 2 }.doubled() { … }`) is a parse error with no hint to parenthesize it; inside element syntax the error lands at the element's closing tag, far from the cause

- status: OPEN — filed 2026-10-20 (kolt's rename-channel dialog: `match Channel { id = row.id }.set_name(…) {` inside an `on:submit` handler)
- kind: diagnostic (parser; S)
- area: language / parser

The parser reads the struct literal's `{` as the start of the match arms, which is the usual rule (Rust has it too). The problem is how the error reads.

Plain code (`vilan run`):

```vilan
let label = match Point { x = 2 }.doubled() {
	4 => "four",
	_ => "other",
};
```
→ `found '=' expected '=>'` at `x = 2`. The location is right, but nothing says that a struct literal cannot head a `match` subject, or to wrap it in parentheses or bind it with a `let` first.

Inside element syntax (a `browser` entry with `prelude = "std::web::prelude"`), the same `match` in an event handler gives a worse error:

```vilan
fun view(): View {
	<form
		on:submit(|event| {
			event.prevent_default();
			match Point { x = 2 }.doubled() {
				4 => print("four"),
				_ => print("other"),
			}
		})
	>
		<input name("a") />
		<p>"text"</p>
	</form>
}
```
→ `expected ';' to end this statement` at `</form>` (line 23 of the repro, eight lines below the cause). In kolt the gap was sixteen lines, and the reported span pointed at markup that was fine.

Recommendation: when the parser sees `match <path> {` followed by `ident =` (a field initializer, which an arm cannot start with), report at the struct literal: "a struct literal can't be a `match` subject here; wrap it in parentheses or bind it with `let`". Element syntax's recovery should not swallow the inner error and report an outer one at the closing tag.
