# B242 — `context` clauses on `fun` declarations (`fun f(x: f64) context settings`): an explicit requirement that anchors coverage diagnostics at the declaration and stops cascades like B241 at the boundary

- status: OPEN — the owner's proposal (2026-09-05)
- kind: design
- area: Type system & the type solver

Today a function's context requirement is INFERRED from its body and flows to every caller ("threads through this call"), so a diagnostic about a deep read surfaces wherever inference breaks (B229, B241) and the reader hunts for the boundary. A declared clause `fun f(x: f64) context settings` (the spelling closure types already use: `(|| T) context flavor`, contexts.md ~184) makes the requirement explicit: the body's reads must be a subset of the declared set (else an error AT the declaration), callers are checked against the DECLARATION only (an undeclared caller must be under run or declare the clause itself — the diagnostic names the clause, one hop), and a cascade from an unresolved call cannot cross the boundary because the requirement no longer depends on the body. Optional: an undeclared function keeps inference. Cheaper for the editor too (a declared boundary is a frozen fact M19's replay can key on). Decide: (1) the spelling and position (after the return type?), (2) whether a declared clause may be WIDER than the body's reads (a forward-compatible API surface — recommend yes, with a warning for an unused declared context), (3) trait methods and closures' clauses, (4) the LSP: hover shows the clause; a quickfix adds the inferred set. Paper section in contexts.md, then build; B241 lands first as the bug fix regardless.
