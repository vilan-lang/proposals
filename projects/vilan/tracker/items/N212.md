# N212 — The const-scaling pin divides by zero ticks on Windows: `GetThreadTimes` advances in 15.6 ms steps and the 20-site window is about 20 ms

- status: FIXED on `next` locally 2026-11-27 @6744ee9d (not pushed) - filed 2026-11-27 (the integrator, from CI run 46058469269 on `next` @84ba1621, the `test (windows-latest, 3, 4)` shard)
- kind: test harness (a flaky pin; Windows clock resolution)
- area: crates/vilan-cli/tests/perf_baseline.rs (`the_const_pass_scales_with_its_const_sites_and_not_with_their_square`, `const_pass_costs`)

The pin costs the post-analysis passes of a 20-site and an 80-site program on thread CPU time and bounds the ratio at 6x. On Windows the thread CPU clock counts whole scheduler ticks. The red run printed:

`PERF-SCALE const_pass clock=thread-cpu load=? 20 sites = 0.00 ms, 80 sites = 15.62 ms, ratio inf× (wall 20.25 ms → 26.09 ms, ratio 1.29×)`

and failed on "the 20-site measurement read zero, so the ratio means nothing". The large reading is one tick, so on Windows the CPU ratio has only ever been a ratio of one or two ticks. It turned red the day M211 landed, which made the small program a little cheaper (inferred: the same shard was green on the commit before; the failing shard was re-run and its result is recorded below).

The fix: the wall pair is measured in the same rounds, so when the small CPU reading spans fewer than sixteen ticks of the clock (always, on Windows; never on unix) the gate uses the wall pair and prints `clock=wall (thread-cpu too coarse)`. The bound is unchanged. On Linux the pin reads as before (`clock=thread-cpu`, 1.33x locally).

Not verified: the Windows branch is one constant and was not compiled for Windows locally; CI's Windows legs are its first run.

Left open: on Windows the pin is now a wall-clock pin, which is what M15 moved away from on Linux (a loaded machine read 8.83x there). If a Windows runner ever reads over the bound under load, the honest choices are a longer window on Windows (more sites) or leaving the asymptote to the Linux legs.

2026-11-27 (the integrator): the failed shard of run 46058469269 was re-run and passed, so the run now reads green on `next` @84ba1621. The zero reading is intermittent: it depends on where the 20-site window falls against the tick. The fix still stands, unpushed.
