# E371 — Dot-completion lists a universal trait's methods on every value: `.bind`, `.same_element`, `.start_element`, `.start_element_value`, `.store_diff` and `.store_leaf_diff` after any `.` under `std::web::prelude`

- status: IN PROGRESS - filed 2026-11-25 (the owner: "I don't like how every single value has `.bind`, `.same_element`, `.start_element`, `.start_element_value`, `.store_diff`, and `.store_leaf_diff` in the auto-complete always for the `std::web::prelude`"); lane `e371-completion` off `next` @30247c7e
- kind: tooling (member completion; blanket impls)
- area: crates/vilan-ide/src/completion.rs (`member_completions`, `push_blanket_methods`, E249), crates/vilan-core/src/impl_select.rs

The cause. Each of the six is a member of a std trait that every type implements through a blanket impl, the bottom tier of std's specialization pattern: `MaybeSignal` (`bind`), `IntoFlow` (`start_element`), `IntoElement` (`start_element_value`), `SameElement` (`same_element`), `StoreLeaf` (`store_leaf_diff`) and `Storable` (`store_diff`, universal through its one bound `T: StoreLeaf`). E249 made member completion offer what the applying blanket impls give a receiver, and an impl over a bare `type T` applies to everything. The web prelude imports `Signal` and `CollPipe`, which loads `std::reactive` and those impls with it, so the six appear after every `.` in a web app. Only `bind` is written by users (component authors, through a bound); the other five are std's own plumbing.

A second defect in the same function: for a name several applying impls declare, completion keeps the FIRST impl in declaration order and not the one a call dispatches to, so `.bind` on a `SignalCell` shows the unbounded fallback's member.

The fix (ruled by the owner 2026-11-25: "Completion fix first"), in the editor alone:

1. A trait is UNIVERSAL when it has an impl over a bare type-parameter binder whose every bound is itself a universal trait (no bound at all included). A method a receiver has from a universal trait, through any tier or through a nominal impl (a derive's `impl User with Storable`), is offered the way an `[internal]` name is (E213): only to a typed prefix of three characters it extends, sorted last, with the reason as its detail. It uses the candidate's existing `admission` field (B620), so no use is dimmed and no lint fires. An inherent blanket (`impl type F: Flow<type T> { fun derive .. }`) is not a trait's and is untouched. A receiver that is a type parameter naming the trait in a bound keeps the method.
2. Per name, the candidate is the most specific applying impl's member, by the solver's own order.

No std change and no new attribute. A third-party tier trait gets the same treatment with no annotation.

Not in this item:

- Completion does not apply the analyzer's trait-in-reach rule (B515/B535), so it can offer a method the analyzer would refuse at that file. With (1) the six are out of the browse list either way; the general rule is its own item if it is wanted.
- A37 (`[gone]` on a trait member) is the language-side answer to the same complaint and stays open, not queued.
