# M666 — a derived `FromJson` refuses an object that leaves out an `Option` field, so a stored JSON value can never gain a field

- status: OPEN — filed 2026-10-21 (kolt's panel layout: adding `locked` to `LayoutNode` would have dropped every layout already saved)
- kind: API / schema evolution (std::json derive; S)
- area: std

```vilan
import std::json::{ FromJson, Json };

[derive(Json)]
struct Node {
	id: u32,
	note: Option<str>,
}

fun main() {
	print(i"{Node::from_json("\{\"id\": 1}").is_ok()}");   // false: "missing field note"
	print(Node { id = 1, note = None }.to_json());          // {"id":1,"note":null}
}
```

The derive (`json.vl`, the `from_json_value` builder) emits `if !value.has_field("…") { ret Err("missing field …") }` for every field, including `Option` ones. `json.vl` itself says "An absent `Option` is JSON `null`", but absent is refused before the field's own decoder (which maps `null` to `None`) ever runs.

This matters for any JSON kept between versions: a preference in localStorage, a layout saved on the server, a `body` column. Adding a field to such a struct makes every stored value fail to decode. The app then has to keep a copy of the old struct and try both, or hand-write `FromJson`. Kolt hit this with its saved panel layouts, which live in both the account's row and localStorage.

Recommendation: in the derived `from_json_value`, decode a missing `Option<T>` field as `None` (skip the `has_field` check for `Option` fields). Optionally, add a field attribute for a default on non-`Option` fields (`[default(false)] locked: bool`) for the same purpose.
