# E279 — spans stick to their text across edits — on every `didChange`, the LSP shifts its cached diagnostics, inlay hints, semantic tokens, references and quick-fix spans by the edit's delta BEFORE the re-analysis lands, so nothing drifts while the developer types

- status: OPEN — filed 2026-10-05 (the owner's hope 3 for the incremental work; independent of M110, can run before S2)
- kind: editor (M)
- area: Editor & tooling

Today a span published before an edit stays at its old offset until the next analysis publishes new ones; between the keystroke and that publish (870 ms on a kolt leaf, 1.6 s with importers open; E121) every underline, hint and token sits one edit behind the text. The owner's hope 3: spans update position instantly on insert, sticking to their text, for diagnostics, inlay hints, rename, go-to-definition, Find References, quick fixes, semantic highlighting and the rest.

This is LSP-side bookkeeping, independent of compiler incrementality (every mature server does it): keep the last published results per document with the document version they were computed for; on `didChange`, map each span through the content changes (an edit before a span shifts it, an edit inside a span grows or truncates it, an edit after leaves it); republish the shifted set at once (diagnostics) or answer requests from it (hints, tokens, references) until the new analysis replaces it; semantic tokens use the delta protocol so the client does not repaint. Pin: a scripted edit above a diagnostic, the published range moves by the edit's length before any analysis runs (the counters prove none ran). Sizing M; vilan-lsp `document.rs`/`main.rs` (incr-47's `edited` plumbing is the hook).
