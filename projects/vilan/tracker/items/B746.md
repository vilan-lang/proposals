# B746 — JS: a backed enum written through `&mut` takes the aggregate `__replace` path: a str-backed one throws ("Cannot assign to read only property '0' of object '[object String]'"), an int-backed one is silently not written

- status: OPEN - filed 2026-11-10 (kolt, task 128; vilan 0.55.1)
- kind: bug (JS backend; analyzer)
- area: borrows / backed enums
- renumbered: filed as B741 on the local branch `kolt-mirror` (kolt-side session); synced to main as B746 on 2026-11-16, because main's B741 is another item. Kolt's sources cited the old number until its v0.56.0 patch.

A backed enum (`A = "a"`, `One = 1`) lowers to a bare JS string or number. A `&mut` to one is still lowered as a reference to an aggregate: the callee's `slot = ..` becomes `__replace(slot, value)` (`Object.assign`), and the caller passes the value itself, not a `(base, key)` place. On a string `Object.assign` throws; on a number it does nothing, so the write is lost with no error.

Minimal repro (`vilan run main.vl`, no std beyond the prelude):

```vilan
[derive(PartialEq)]
enum Named {
	A = "a",
	B = "b",
}

[derive(PartialEq)]
enum Numbered {
	One = 1,
	Two = 2,
}

fun set_numbered(slot: &mut Numbered) {
	slot = Numbered::Two;
}

fun set_named(slot: &mut Named) {
	slot = Named::B;
}

fun main() {
	mut numbered = Numbered::One;
	set_numbered(&mut numbered);
	print(i"numbered written: {numbered == Numbered::Two}");
	mut named = Named::A;
	set_named(&mut named);
	print(i"named written: {named == Named::B}");
}
```

prints `numbered written: false`, then throws `TypeError: Cannot assign to read only property '0' of object '[object String]'` at `__replace` in `set_named`. Expected: `true`, `true`. The same holds for a field (`set_named(&mut holder.kind)` passes `holder[0]`, where a `str` field passes `[holder, 0]`) and for a generic `&mut self` write monomorphized at a backed enum. A plain (unbacked) enum, `str` and `bool` are fine.

Cause: `is_scalar_view_pointee` (crates/vilan-core/src/analyzer.rs) admits the scalar primitives and `bool` (the C5.3 fix, which was this same bug for `bool`: "a silent no-op write"), but not a backed enum, whose lowering is just as scalar. So every `&mut` site falls to the aggregate `Object.assign` path for it.

Where it bites: std's mirrored stores. The derived `store_apply_at` passes each field by `&mut`, and the leaf apply is `self = T::store_wire_rebuild(..)`. Any frame applied over a HELD struct that has a backed-enum field throws at that field: `landed_over` (a mint's reply over what its replica holds: every re-ask) and a boundary's `apply` (a re-seed or a whole-value `Set`). That is B745's whole story; B745's "primitive held in `Some`" reading was a misreading of the stack (the `Option` holds a struct; the string is the struct's backed-enum field). In kolt, after one dropped connection the account's mint never binds again: its reply throws in `bind` before the batch that binds it, `asking` is already false, and every new hold asks again, so each page build logs the error once until the page reloads (the "ordinary use" log in B745 was this). The failing reply's seed is dropped and the mint reads `Waiting`; frames for the base still land, because `adopt_base` ran before the throw. A `Seed` that throws in `MirrorClient::land` also drops the rest of that `Patch` frame's ops, and its boundary is never marked heard.

Rec: make `is_scalar_view_pointee` (and anything else that decides place-vs-aggregate for `&mut`) true for a backed enum, as it is for `bool`. Pin: the repro above on JS, both lines `true`; and a mirrored `Store` of a struct with a str-backed enum field, re-seeded over a held value. Size S. Native not checked.

2026-11-12 (kolt): SEVERITY RAISED - it needs no dropped connection. It fires in ordinary use every time the server sets a WHOLE record that the client's mirror already holds and that has a str-backed enum field: the set lands as a whole-value apply over the held struct, and the field's leaf write is the `__replace` above. In kolt that is every notice (a direct message or a mention) arriving on an open page: the client throws applying `Notice.kind`, and from then on that page's mirror of the account store stops updating live until a reload, so unread marks, the notification count and desktop notifications never fire. The "not reproduced without a dropped connection" in B745 held only because no such set happened in that session. The rec and the pin stand; add to the pin a whole-record `Set` over a held struct with a str-backed enum field, with no reconnect, and check that the mirror keeps applying the frames after it.
