# B763 — Native: two `let` views alive at once into one value, through two different struct keys held in values (`let u = &mut p[j]; let v = &mut p[k];`), reach rustc as E0499; JS is correct

- status: open - filed 2026-11-26 (lane `keys-s1b`'s find, left open by it; reproduced by the integrator on local `next` @e43933b0)
- kind: backend defect (native: a checked program is refused by rustc, reported as "a BACKEND defect")
- area: crates/vilan-rust (struct keys, B711 S1b; view bindings)

Repro:

```
struct P {
	a: i32,
	b: i32,
}

fun main() {
	mut p = P { a = 1, b = 2 };
	let j = P.a;
	let k = P.b;
	let u = &mut p[j];
	let v = &mut p[k];
	u += 1;
	v += 10;
	print(p.a + p.b);
}
```

JS prints `14`. Natively each view is `vilan_rt::key_mut(&access, &mut p)`, which borrows the whole of `p`, so the second is rustc's `E0499: cannot borrow p as mutable more than once at a time`. The field form (`&mut p.a`, `&mut p.b`) builds, because Rust sees the two fields apart; a key held in a value chooses its place at run time, as a list element does.

What S1b already does for the neighbouring shape: a CALL handed two loans into one value, one `&mut` and one through a held key (`both(&mut p[j], &mut p[k])`), is refused by name. The `let` form needs to know that both views are live at once, which the emitter does not track.

The same class exists without keys and is as old as native views: a field view and a list-element view of one value alive together (`aliased_field_and_element_views_e0499.vl` in the lane's scratch).

Options: (a) refuse by name once the emitter can ask whether an earlier view of the same root is still live; (b) lower a view through a held key to the promoted-cell form the backend already uses for aliased roots (F124), so both views build and behave as JS does. (b) is the complete answer and is what Vilan's "no exclusivity" rule asks for; (a) is the small one. Rec: (a) now, (b) with the general aliased-views work. Size S for (a).
