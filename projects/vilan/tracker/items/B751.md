# B751 — Native: a view fallback BOUND to a name and then read with `*` is rustc E0614 - `let found = shelf.count(5).unwrap_or(&zero); print(*found + 1);`, and the checker accepts both `found + 1` and `*found + 1`

- status: open
- kind: native backend defect (cargo refuses) + an ambiguity in the checker (is the binding a view?)
- area: the B649/F99 corner: a generic `T` bound to a view (`Option<&i32>::unwrap_or`), crates/vilan-rust (how the bound result is typed), `check_view_value_reads`

`Option<&i32>::unwrap_or(&zero)` answers a `&i32` at the type level, and B577/B685 read the payload or the fallback out where the option is CONSUMED. Bound to a name instead, what `found` is depends on who you ask: the checker lets it be read both as a value (`found + 1`) and through a star (`*found + 1`), JS has a number, and the native emission has an `i32` that `*` cannot dereference (E0614). Decide what the binding is (B649 deliberately leaves the `&` alone because the parameter's `T` IS a view) and make the checker say it: either the binding is a view (then `found + 1` is the `write *` refusal and native keeps a reference) or it is a value (then `*found` is refused with a diagnostic that says so). Pin both spellings on both backends.
