# E232 — inlay hints on the line being EDITED are cleared on-type, so the whole line JUMPS the moment typing starts. Two doors, the owner's words: (1) keep the hints on the current line that sit BEFORE the cursor and clear only those after it; or — preferred — (2) make hints BEHAVE and never clear them on-type: typing before a hint shifts it right by the typed width instantly, typing after it does nothing; a new line above shifts it down one line, typing on any line below does nothing to it — i.e. a hint's anchor follows the document's edits like any other position until the next analysis replaces the set

Rec: door (2). VS Code already keeps a provider's hints in place and shifts their positions with edits until it re-requests; the jump means OUR side answers an empty (or short) set for the dirty line before analysis catches up — find that answer and stop it: the server keeps serving the LAST analysed set for a document whose analysis is stale, mapped through the edits since (the LSP's own position mapping — the document keeps the edit log the keystroke path already has), and replaces it whole when the analysis lands; a hint whose anchor was DELETED by an edit is dropped, nothing else is. Door (1) is the fallback if mapping through edits proves costly: split the line at the cursor. Pins in the lsp harness: type at the start of a hinted line → the hint moves right by one column and its text is unchanged; type after it → unchanged; insert a line above → the hint moves down one line; type on a line below → nothing; delete the hint's anchor → gone; the analysis landing → the fresh set.
