# B184 — trait annotations on STRUCT FIELDS, under a one-instantiation-per-program rule

- status: OPEN — owner-proposed 2026-09-01; DISCUSSION REQUIRED before any build
- kind: design
- area: Type system & the type solver
- source: the owner, off the kolt store.vl migration (the `[expose] … : Signal<…>` fields)

The owner's sketch: allow `field: SomeTrait<…>` as a CHECKED
CONSTRAINT (B161's reading extended from `let` to fields), with the
implementation requirement that ALL instantiations of the struct use
the same concrete type for the field — the struct stays monomorphic,
the field's real type inferred once program-wide from its
construction sites. Effectively a program-inferred generic parameter
the author never writes.

For the discussion: (1) the spelling that exists today is the
explicit generic (`struct Store<S: Signal<T>>`) — what the sugar buys
is not writing S at every use; (2) the whole-program inference is a
new solver shape (construction sites unify globally; two sites with
different concrete types must refuse NAMING BOTH SITES, and the
refusal must survive incremental/LSP analysis where "the program" is
a moving target); (3) generated code (the service macro) reads field
types at macro time — B182's cascade territory — so the grounding
must land before expansion or the macro must read the inferred type;
(4) the reactive paper's §7.3 parameter sugar is the same family and
is also unbuilt — if either ships, they should share semantics and
ship together or in order. The kolt exhibit is the motivation: store
fields WANT the trait spelling; today they name `SignalCell` (fine)
or go generic (noisy).
