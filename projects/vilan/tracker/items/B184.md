# B184 — trait annotations on STRUCT FIELDS, under a one-instantiation-per-program rule

- status: OPEN — owner-proposed 2026-09-01; DISCUSSION REQUIRED before any build
- RULED 2026-09-05 (owner): Q3 answered — the hidden argument prints as `C<A>`/`C<B>` (B218). With rev 2's case-4 verdict (per-binding, VALID) the sugar is buildable: bare grammar (no `impl` keyword), fields only in v1 (return position stays a question), byte-identical emission over a hidden type parameter. Order 28 lane b184-b218.
- kind: design
- area: Type system & the type solver
- source: the owner, off the kolt store.vl migration (the `[expose] … : Signal<…>` fields)

The owner's sketch: allow `field: SomeTrait<…>` as a CHECKED
CONSTRAINT (B161's reading extended from `let` to fields), with the
implementation requirement that ALL instantiations of the struct use
the same concrete type for the field — the struct stays monomorphic,
the field's real type inferred once program-wide from its
construction sites. Effectively a program-inferred generic parameter
the author never writes.

For the discussion: (1) the spelling that exists today is the
explicit generic (`struct Store<S: Signal<T>>`) — what the sugar buys
is not writing S at every use; (2) the whole-program inference is a
new solver shape (construction sites unify globally; two sites with
different concrete types must refuse NAMING BOTH SITES, and the
refusal must survive incremental/LSP analysis where "the program" is
a moving target); (3) generated code (the service macro) reads field
types at macro time — B182's cascade territory — so the grounding
must land before expansion or the macro must read the inferred type;
(4) the reactive paper's §7.3 parameter sugar is the same family and
is also unbuilt — if either ships, they should share semantics and
ship together or in order. The kolt exhibit is the motivation: store
fields WANT the trait spelling; today they name `SignalCell` (fine)
or go generic (noisy).

## The owner 2026-09-03 — questions for the paper

1. Would an `impl Trait` grammar (`x: impl TraitType` vs `x:
   StructType`) help? "I know it would but it comes at the cost of
   extra noise. Is the value high enough? You'd have to learn how
   traits as type annotations work anyways, so I don't see a huge win
   from requiring it."
2. Under the one-instantiation rule, decide each:
```vilan
trait X {}
struct A {}
impl A with X {}
struct B {}
impl B with X {}
struct C { x: X }
{ let c1 = C { x = A {} }; let c2 = C { x = A {} }; }   // valid in theory
{ mut c1 = C { x = A {} }; c1 = C { x = A {} }; }        // valid in theory
{ mut c1 = C { x = A {} }; c2 = C { x = B {} }; }        // invalid
{ let c1 = C { x = A {} }; let c2 = C { x = B {} }; }    // valid or not?
```

## Paper 2026-09-03 — proposal/trait-typed-fields.md revision 2: BUILD the PER-BINDING rule, spelled bare

Revision 1's order was carried out ([[B188]] closed, [[B182]] shipped,
[[B186]] shipped) and the owner re-asked. Revision 2 finds that THREE
rules fit "all instantiations use the same concrete type", and only the
fourth case tells them apart: (a) program-wide, `C` monomorphic;
(b) per binding, `C` is really `C<impl X>`; (c) dynamic — ruled out,
trait objects were DECLINED 2026-08-07 and the emission probe shows a
value is a bare array with nowhere for a vtable to live.

**The finding: the language already decided the four cases one level
down.** `let a: X = A {}` and `let b: X = B {}` in one scope both run
(B161); `mut a: X = A {}; a = B {}` is refused naming the initializer;
`fun tell(v: X)` takes an `A` and a `B` in one program (B186). That is
(b) — and under (b) the feature is SUGAR over `struct C<S: X> { x: S }`
with byte-identical emission, so revision 1's whole-program
reservations do not apply: they were objections to (a).

Verdicts: case 1 valid; case 2 valid; case 3 invalid (as written a
plain scope error — `cannot find 'c2'`; as intended the desugaring
already refuses `Expected C<A>, but got C<B>` with the initializer
note); **case 4 VALID** — so `fun tell(c: C)` is generic over the
hidden parameter, monomorphized per argument. The price: (b) does NOT
deliver revision 1 §5.3's two kolt sites (module-level `Context<Prefs>`,
a bare return type), the one thing (a) buys.

Grammar: **bare `x: Trait`, no `impl`** — both shipped positions are
bare, the LSP already paints a trait `interface` and a struct `struct`
in the same annotation position (probed), and Rust's `impl` earns its
keep only by contrast with `dyn`, which vilan declined.

Scope: ONE lane, ten pins specified. 32 probes. Four owner questions
(case 4 itself; the return position in or out; how the hidden argument
prints — B186's "trait's name displays" yields `Expected C, but got C`
at a field and must be deviated from; and whether to file the bycatch
first). **Bycatch, all pre-existing, all reproduced with WRITTEN
generics:** two garbage runs — `swap(A, B)` prints `A/7`, and
`f(B { n = 9 })` prints `9` through a declared `: str` — both from
`reconcile_type`'s `(_, Generic)` arm binding a generic the body has no
right to bind; and NO duplicate top-level type declaration is refused
at all (trait+struct, struct+struct, trait+trait, struct+enum), so
`x: N` resolves by declaration order.
