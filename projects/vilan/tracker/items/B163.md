# B163 — `if`-expression arms are never unified: `if c { 1 } else { "two" }` types and runs

- status: OPEN — found by the a32-paper lane's probes (Order 22), FIX-NOW;
  in-order lane running
- kind: bug
- area: Type system & the type solver
- source: reactive-traits.md §8.1, probed on 0.39.0

`let mixed = if condition { 1 } else { "two" }; print(mixed + 1)` compiles
and prints `two1`; `fun pick(c: bool): i32 { if c { 1 } else { "two" } }`
compiles and returns `"two"` — an accepted program computing with the wrong
type, the class a checker exists to refuse. `match` LEGS ARE unified
(probed); `if` arms are not — the fix aligns the two on one rule. This is
independent of the reactive arc but a prerequisite for B161's ruled
semantics ("branches must unify to ONE type"), which currently rests on a
rule that does not exist. Estate census before the fix: any program
accidentally relying on un-unified arms stops compiling (family breaking or
miscompile per the honest §7.2 test — the emitted program was wrong, so
miscompile-shaped; the lane argues it).
