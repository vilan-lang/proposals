# B317 — a type's ASSOCIATED FUNCTION cannot be bound to a bare name by ANY form, against the spec: spec/names.md:98–99 says `use path` "binds names from an already-visible type's namespace without loading (variants, statics)", but `use Length::rem;` refuses with "`use` requires a namespace (a module or an enum)", and the import forms — `import std::style::Length::rem;`, `import std::style::Length::{ rem, px };`, a re-export `export import std::style::Length::rem as rem;` / `export use Length::rem as rem;` — all refuse with "cannot find `rem` in the imported path" (probed 2026-09-12), while an ENUM'S VARIANTS travel exactly these paths (`import std::option::Option::{ self, Some, None }`, prelude.md §8). `collect_importables` lists `variants` for an enum and nothing for a struct's `impl`, and `use` fences the subject to a module or an enum. Generalise both rows to a type's SELF-LESS functions (`rem`, `px`, `zero`, `new`), from the module that declares the impl, so `rem(1f)` is spellable and an app's prelude module can re-export `Length::rem as rem`. Methods with `self` stay refused, with a message that says so

**Mechanism.** The importable row for a struct/enum gains the self-less functions of its `impl` blocks (the ones whose first parameter is not `self`), keyed by the impl's declaring module — for std and for every type whose impls sit beside it that is the type's own module, so `std::style::Length::rem` resolves like `std::option::Option::Some`; an EXTENSION impl's functions are importable from the extending module under the same `Type::f` tail. Trait-provided statics (`T::default()`) are out of scope — they are not the type's namespace. `use` lifts its namespace fence from "module or enum" to "module, enum or struct" and binds the same rows without loading, exactly as it does variants.

**Binding.** The free name binds the associated function's own entity (the same Id), so go-to-definition, references and rename on `rem` land on `Length::rem` — the invariant names.md:93–96 states for `as`. Organize Imports prunes/keeps the path like any leaf. The "cannot find `rem` in this scope; import it first (…)" steer may name a `Type::f` path. Completion offers the functions under the type's path in an import statement.

**Messages.** A `self` method under either form: "`Length::text` takes `self` — a method is called on a value, not imported" (curated). Everything else keeps its message.

**Pins.** direct `import Type::f`, the brace set with `as`, `use Type::f` and `use Type::{ f as g }`, an `export import Type::f as g` re-export consumed by a second file (the prelude shape), an extension impl's static from the extending module, the `self`-method refusal, enum variants unchanged, LSP go-to-definition/rename through the alias (`vilan-lsp` rename pin in the `as` shape). Docs: names.md:98–99 already promises it — the sentence gains `import` beside `use`; the prelude page's custom-prelude example gains one `Length::rem as rem` line.
