# M124 — A `.derive` on a `dyn Source<X>` still costs ~4.4k type slots per attempt (8.6k before M118): asked which arguments the object provides `Flow` at (a trait that is not the object's own), `trait_args_candidates` reconciles the object against every `Flow` implementor through the erasure arm, and one answer in the suite DEPENDS on such a nominal echo

- status: OPEN — filed 2026-10-05 (perf-47's find, Order 47)
- kind: PERFORMANCE (MEDIUM) — a trait object's provider question
- area: Performance & footprint

M118 answers an object's own trait from the object. For a blanket-provided trait (`impl type S: Source<type T> with Flow<T>` over a `dyn Source<X>`) the scan still runs, and every nominal `Flow` implementor that also implements `Source` reconciles with the object through the erasure arm (`type_implements_trait_at` over every provider, minting each instantiation). Filtering nominal subjects out for a `dyn` receiver (they can never be the impl selected for an object) brings the probe to 153 slots — but changes one answer: in `a142_s4_filter_map_and_any_over_transients` a `dyn` receiver's provided arguments came out `bool` from a nominal echo and `T` (unground) from the blanket alone. Probe: `upstream(): dyn Source<St<Option<i32>>>` then `upstream().derive(|x: St<Option<i32>>| 1)`, `--explain-cost`. A solver question first (what an object provides a blanket trait at), then the filter. Sizing S–M.
