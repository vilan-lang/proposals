# F169 — gfx host on X11: an input event is sometimes left unread until the next X event (about 1 run in 5 of a release build under xvfb with software Vulkan)

- status: open
- kind: bug (native runtime; gfx host event loop)
- area: crates/vilan-rt-gfx/src/host (the winit loop), winit 0.30 X11 backend, Mesa's X11 present path

Observed: an injected key, or the window close, produces no turn; the program sits in `epoll_wait` with the event already sent, and a later pointer move delivers the stuck event. HYPOTHESIS, not proven: Mesa's X11 present path (possibly on its own queue thread) reads the shared X connection, so events land in the client-side queue while winit waits on a socket that is no longer readable. First step: prove or refute it (strace or a counter on wake reasons; check whether the stuck event is in Xlib's queue; try a present mode with no WSI thread). Candidate fixes, in order of preference: wake the loop once shortly after each present so the queue is drained (a bounded `WaitUntil`, back to `Wait` after); a low-rate idle wake while a window is open; an upstream winit report. Exit: 200 runs of the release list example with injected keys lose none; a pin if one can be made deterministic. Check a real GPU and Wayland separately: the hypothesis says they may not share the defect.
