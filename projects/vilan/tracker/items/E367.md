# E367 — `asset::read` in a DEPENDENCY resolves against the source root of the package being built, so a library cannot read its own files at compile time

- status: OPEN - filed 2026-11-09 (kolt, hoisting `src/search-dict` into a `[library]` package)
- kind: bug or design gap (const evaluation; packages)
- area: Tooling / packages
- renumbered: filed as E362 on the local branch `kolt-mirror` (kolt-side session); synced to main as E367 on 2026-11-16, because main's E362 is another item. Kolt's sources cited the old number until its v0.56.0 patch.

Kolt's search dictionary is a library (`search-dict/`, `[library] name = "search_dict"`) whose `lookup(word)` runs inside `const` and reads a sharded table with `asset::read(i"search-dict/{shard}.txt")`. Moved out of the app's `src/`, the read still resolves against the APP's source root, whoever declares the call:

```
// dict/src/lib.vl  ([library] name = "dict")
import std::web::asset;
export *;
fun lookup(word: str): str { asset::read(i"data/{word}.txt") }

// app/src/main.vl  ([package] with dict = { path = "../dict" })
import dict;
fun main() { print(const dict::lookup("a")); }
```

`vilan run app` reads `app/src/data/a.txt`; with only `dict/src/data/a.txt` present it fails: "cannot read `data/a.txt` (resolved against the package root to `./src/data/a.txt`)". The library's own tests (`vilan test dict/src`) resolve against `dict/src` instead, so the same call reads two different places depending on what is being built.

Kolt's workaround: the generated data lives in `search-dict/data/`, and both source roots hold a symlink to it (`src/search-dict -> ../search-dict/data`, `search-dict/src/search-dict -> ../data`). A link works because the escape check is lexical.

Rec: resolve `asset::read` (and `bundle`) against the source root of the package that DECLARES the call site, as module paths already are. A consumer that wants its own file passes the text in. Pin: the two-package program above printing the library's file.

Related: a dependency's `[[build.hook]]`s never run, so the dependent's manifest has to declare the hook that generates a library's sources and name the library's folder in `outputs`. That is documented (spec 11.4) and works, but together with this item it means a library with generated or data parts isn't self-contained.
