# B590 — `[T; n].len()` answers `i32` where every other length in the language answers `usize` (I5 S2 moved std's signatures; `len` on an array is a compiler fold, `Expr::ArrayLen` typed `primitive_struct_type("i32")`, so the census never saw it): `let m: usize = a.len()` and `xs.len() + a.len()` are refused, and `a[a.len() - 1]` checks, runs on JS and is refused by rustc (`usize - i32`)

- status: OPEN — filed 2026-10-09 (papers-49's find, Order 49)
- kind: solver: a type (XS; breaking in principle, estate 0 edits)
- area: Type system & the type solver

Repro (`finds/array_len_answers_i32.vl`, vilan 0.46.0): `let a: [i32; 3] = [1, 2, 3]; let m: usize = a.len();` -> "Expected usize (an index: a position, a length or a count), but got i32 instead"; `xs.len() + a.len()` -> "`+` adds two values of the same type, but the operands are `usize` and `i32`"; `a[a.len() - 1]` checks (B591's hole) and prints 3 on JS, while natively the fold renders Rust's `(a).len() - (1i32)` and rustc refuses E0308/E0277. Inside `impl [i32; 3] with Size { fun size(self): usize { self.len() } }` the same refusal (p29). fixed-arrays.md §10 typed `len()` as `i32` "matching `List.len()`"; I5 S2 (v0.41.0) made `List::len()`, `Tuple::len()` and every std length `usize`, and the intercept (analyzer.rs `resolve_method_call`, the `Type::Array` + `len` arm ~52377) and its type (`Expr::ArrayLen(_, _) => self.primitive_struct_type("i32")`, ~44119) were left. Fix: type it `usize` (the native emission is already Rust's `usize` `.len()`; JS reads the literal or `.length`). Estate: 4 `.len()` calls on arrays (3 in the corpus' fixed-arrays.vl, 1 in the tour), all passed to `print`: no edit, no golden; the compiler's own pins asserting `i32` move. Sizing XS; solver-49 can take it beside B582.
