# D16 — The docs still say a `match` cannot be an operator operand, two cycles after B231 made it one: the tour (control-flow.md, "One edge to know: a `match` can't sit directly inside a larger operator expression. Bind it to a local first.") and the gotchas page ("`match` can't be an operator operand. `(match x { … }) + 1` → bind the match to a local first") — and the gotcha's own example of the failing form is the spelling that works

- status: OPEN — filed 2026-10-19 (kolt's rich text editor: `local > 0 && match .. { .. }` compiled and behaved, against the docs)
- kind: documentation (S)
- area: Documentation

vilan 0.52.0, all checked: `gate && match value { .. }` and `let plus = 1 + match .. { .. };` compile and evaluate correctly (B231, closed 2026-09-05, admitted block-likes as operands); `(match v { .. }) + 1` works anywhere; the one refusal left is a `match` that BEGINS a statement (`match v { .. } + 1` as a body's tail), which B248 records and whose diagnostic already gives the right fix ("parenthesize the block-like form — `(match x { .. }) + 1`"). So the docs are wrong twice: they forbid what works, and the gotcha names the working parenthesized form as the broken one.

Rewrite both to the rule as built: a `match` (like `if`, `for`, `{`) is complete at its closing brace, so in STATEMENT position an operator after it starts a new statement; parenthesize it there (or bind it). Anywhere else it is an ordinary operand. Sites: docs/tour/control-flow.md (§`match`, "One edge to know"), docs/appendix/gotchas.md (Language, first bullet). A doc test pinning `flag && match ..` would keep it from drifting again.
