# M176 — `Request::body_stream(): Reader` - a request body read incrementally (`next(size): Bytes`, like `std::fs::Reader`), the cap enforced as it reads, so an upload costs a chunk of memory instead of its whole size

- status: OPEN - filed 2026-10-26 (http-55's follow-up, Order 55; RULED as a follow-up at GO, R-g)
- kind: feature (std::http; M) - M164's follow-up, R-g
- area: Standard library

M164 made the body capped and LAZY (read on the handler's first `bytes()`), but a body that is read is still read WHOLE into memory. Measured (one upload, peak RSS delta `VmHWM`, `MALLOC_ARENA_MAX=1`, debug native): JS 25 MiB read whole costs 56,284 kB after M164 (81,872 kB before - `Buffer.concat` now sized); native 25 MiB costs 25,500 kB after (a 15 MiB upload cost 63,600 kB before: the inbox was cloned per poll while waiting); a body refused or never read costs ~0 (JS 1,812 kB, native 20 kB, where both paid the whole upload before). Kolt's server held 135,952 kB peak after a 5 MB and a 20 MB upload (74,008 kB with both refused). Ask: `request.body_stream(): BodyReader` with `async fun next(self, size: usize): Option<Bytes>` - the node side a `data`/`pause` pump (`__http_read_body`'s listener, resumed per `next`), natively `BodyRead` answering what the inbox holds up to `size` (the decoder and the per-turn `BODY_SLICE` already exist) - the cap counted as it reads (the refusal is the same `413` + cancellation), `bytes()` and `body_stream()` exclusive (the second to be called after the first refuses). Pins: a 64 MiB upload hashed through `crypto` with peak RSS under a few MiB on both backends; the cap mid-stream; kolt's `(storage.put)` written from the stream.
