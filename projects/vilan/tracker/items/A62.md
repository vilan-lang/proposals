# A62 — `std::router` is write-only: `Routable`/`to_path` renders a route to a URL and `segments()` is the ONLY read helper, so every app hand-writes index arithmetic to parse one back (kolt's `parts.len() > 3 && parts[2] == "task"`) — and no query string or fragment is reachable at all

- kind: feature

kolt/src/routes.vl:22-52, on a route enum written the way the router paper wants (the file's header calls
the URL "a wire format for this enum"):

    // FIXME: Use path helpers and add url parsing helpers to `std::router`. Or, establish
    //        a canonical url parsing format that's easier to read and write than the below.
    fun parse(path: str): Route {
        let parts = segments(path);
        match parts.len() {
            0 => Route::Home,
            _ => {
                if parts[0] == "m" {
                    Route::Messages
                } else if parts[0] == "w" && parts.len() > 1 {
                    match parts[1].parse_i32() {
                        Some(let id) => Route::Workspace(id, parse_workspace(parts)),
                        None => Route::NotFound,
                    }
                } else {
                    Route::NotFound
                }
            },
        }
    }

    fun parse_workspace(parts: List<str>): WorkspaceRoute {
        if parts.len() > 3 && parts[2] == "task" {
            match parts[3].parse_i32() {
                Some(let task_id) => WorkspaceRoute::Task(task_id),
                None => WorkspaceRoute::Overview,
            }
        } else {
            WorkspaceRoute::Overview
        }
    }

WHAT STD HAS TODAY: vilan/std/src/browser/router.vl ships the WRITE direction and all the plumbing —
`trait Routable { fun to_path(self): str }` (:81-83), `link` (:89), `navigate` (:60), `current_path` (:52),
`history_push` (:23), `plain_left_click` (:101), `pending` (:114), `chunk_error` (:124) — and exactly ONE
read helper: `segments(path): List<str>` (:69). Everything above `segments` is the app's, and the index
arithmetic is where a route bug will live: `parts.len() > 3 && parts[2] == "task"` then `parts[3]` reads
like an off-by-one even when it is right.

Note also that no query string or fragment is reachable at all — `location_path()` (:27) is the path only,
so an app that wants `?q=` has to go around std to `window.location`.

THE ASYMMETRY IS THE ITEM: `Routable` makes a route's URL form one declaration in the write direction and
there is no counterpart for reading, so the enum's wire format is stated twice, in two shapes, and can
drift.

THREE CANDIDATE ANSWERS FOR THE OWNER TO CHOOSE BETWEEN (they compose; (c) is needed whichever wins):
(a) matcher helpers over `segments` — a `Segments` cursor with `take(literal): bool`,
    `take_int(): Option<i32>`, `rest()`, so the shape above reads top-down with no indices;
(b) a `FromPath` counterpart to `Routable`, making the enum's URL wire format one declaration in both
    directions (this is what "a canonical url parsing format" most plausibly means, and it is the shape
    that makes the paper's "URL is a wire format for this enum" literally true);
(c) query and fragment access — `location_query()` and a parsed `Query`, plus percent-decoding — which is
    missing outright.
