# A124 — PAPER — `Source` as a PUSH-PULL PIPELINE: every combinator is a cold, stateless NODE (`Map<S, U>`, `Switch<S, I>`, `Combine<..>`), `get()` PULLS through the chain, a notification carries NO value, and state lives only at the ends — the root `Signal` and an explicit `memo()`/`to_signal()` node where sharing or a total value is wanted; a pending value (a task, a fetch) is NOT a `Source` until a fallback makes it total; struct fields hold a pipeline as `dyn Source<T>` (an object over the object-safe core `get`/`on_change`, reopening B4 in that scope only) so a field does not mint a hidden generic. The owner's `reactive2.vl` sketch, made precise; it REPLACES this item's first filing (a read-tracked `computed`), withdrawn below with reasons

- status: OPEN — filed 2026-09-21 as the read-tracked `computed` paper; REWRITTEN 2026-09-22 after the owner's `kolt/src/lib/reactive2.vl` sketch and the eight probes in `sweeps/order39/probes/a124_*.vl`; paper Order 40, rulings R2–R5 before any code

- area: Reactive core & UI

**The sketch, and what it is.** `kolt/src/lib/reactive2.vl` (pseudo-code, does not compile): a `Source<T>` trait with `map` and `sub`; a `Signal<T>` root that owns a value and implements it; a `Map<U, T>` node that implements it and owns nothing; `inspect(label, source: dyn Source<T>)` subscribing at the leaf. It is Kotlin's Flow/StateFlow split with `stateIn` as `to_signal()`, or Rx cold observables plus a BehaviorSubject — named so the precedent's known costs (per-subscriber recomputation, the combineLatest glitch, the initial value at materialisation) are on the table from the start. The owner's seven claims, scored against the record: lazy with no tracking cost (real — because a cold node has nothing to compute until someone subscribes or pulls); async natively (real, the largest ergonomic gain — a pending value is written on `T`, and the `Option` appears once at the fallback instead of threading through every `map`); declarative and inspectable (real — a node tree can be printed and dev-tooled, and middleware such as an equality check or a debounce is a node); no intermediates (real for a single consumer only — where a derivation is shared, a `memo()` node reappears and it IS a cell); arbitrary caching (real, same mechanism); dynamic tracking via a node (real — that is `switch`/`and_then` as nodes, A123, not read-tracking); shorter type names via `dyn` (real, and the one language feature).

**Why the first filing is withdrawn.** The read-tracked `computed` needed an ambient frame consulted on every `get()`, an untracked-callback footgun, and a reversal of `reactive-batching.md`'s explicit-tracking stance. The pipeline keeps that stance INTACT — every dependency is structural, written in the node's type — and gets the same 'one primitive' answer the other way round: not one function that discovers its dependencies, but one trait whose combinators are all the same kind of thing. The claim in the first filing that a lazy pipeline 'doubles the vocabulary' does not hold against the sketch: `Signal` IS a `Source`, the result of `map` IS a `Source`, and only `memo()`/`to_signal()` re-enters state — one vocabulary. What DOES survive from the first filing: totality is not avoided, only relocated — a `to_signal()` of a filtered or pending chain needs an initial value or yields `Signal<Option<T>>` (Kotlin's `stateIn(initialValue)`); and the 'effect + set pair is a state machine with two writers, not a missing combinator' paragraph, kept at the end.

**The model, in five parts.**

1. **The trait.** `Source<T>` carries `get(self): T` and `on_change(self, observer): Subscription` — the object-safe core, exactly today's two requirements (R1 RULED by the owner 2026-09-22: `get` stays on the trait; a `Map` node's `get` is `f(upstream.get())`, which makes every cold chain pull-readable and is the lazy derivation with no tracking machinery). `sub`/`effect`/`scoped_effect` stay defaults over those two. Every combinator is a BLANKET method on `S: Source<T>` returning a concrete node — `map<U>(self, f): Map<Self, U>`, `switch`, `and_then` (A123), `combine`, `filter_map`-shaped ones yielding `Source<Option<U>>` — the spelling today's `flatten` already uses. A combinator is NOT a trait requirement: the return-position existential is refused (B253, RULED keep 2026-09-07; probes a/f below) and a generic requirement is what makes a trait non-object-safe anyway (trait-objects.md P13).
2. **Nodes are cold and stateless.** A `Map<S, U>` holds its upstream and its transform, nothing else; `get` pulls, `on_change` registers downstream through the upstream. N subscribers means N upstream registrations and N evaluations — by design; the consumer that wants sharing writes `memo()`. A stored transform is held plain (a `sync` closure contract is only accepted on parameters — probe h — so the contract is checked at the combinator's parameter, the J2 pattern rpc already uses).
3. **Notifications carry no value; leaves pull.** `on_change`'s observer is invoked once per settle and reads through `get()` — a push-pull protocol (TC39 Signals, Solid 2.0). This is what keeps A110 door 2's contract without giving nodes an identity: a diamond `combine((a.map(f), a.map(g)))` receives two notifications per change of `a`, but every read pulls settled state, so there is no stale pair — only a duplicate call, which door 2's dedup-on-enqueue collapses IF a leaf `sub` mints ONE subscriber id and every upstream registration in its chain shares it (R2 below). Derivation ordering (the bucketed wave) applies to `memo()` nodes only, which are cells with ids.
4. **State at the ends.** The root `Signal<T>` (the owner's `Initial`) owns the value. `memo()`/`to_signal()` is the ONE stateful node: a cell holding the last value, an equality check, subscribed upstream, owner-tied like today's `map` (A28) and marked `as_derivation()` (door 2). It is where a shared derivation, a `get()` in a hot loop, or a heterogeneous collection (part 5) materialises.
5. **Pending values are outside the trait.** A task, a fetch, a stream that has not emitted is NOT a `Source` (it cannot answer `get`). It is its own small struct family with `map`/`then` of its own, and it becomes a `Source` through a fallback op — `pending.or(default): Source<T>` or `pending.optional(): Source<Option<T>>`. That is the Future-versus-Signal split every language has, not the 'Mapper twin' the first filing objected to.

**Fields: `dyn Source<T>`, not a hidden generic — RULED 2026-09-22.** Probe c shows a bare `Source<i32>` field already works today as B184's hidden generic, grounded per literal; probe g shows the cost: a `Holder` over a root and a `Holder` over a mapped node are `Holder<Root>` and `Holder<Dbl<Root>>`, and one list of both is REFUSED — and the hidden parameter is viral through every embedding struct (B184's fixpoint). The owner's ruling: a field holds a pipeline as `dyn Source<T>` — an erased object over the object-safe core — and the bare-trait hidden-generic form need not be allowed at a field that names `Source` once `dyn` exists; virality stays low and heterogeneous collections work. This reopens B4 (trait-objects.md, DECLINED 2026-08-07) in ONE scope: objects over traits whose members are receiver-taking, non-generic and `Self`-free — `Source<T>` qualifies with exactly `get`/`on_change`; the combinators, being blankets over `S: Source<T>`, apply to the object through a blanket `impl dyn Source<T> with Source<T>` (Rust's `Box<dyn Iterator>` shape). §3.5's three revisit criteria are met for the first time by an application: (a) the set of node types is open, (b) the field needs the trait's checked surface, (c) which node a field holds is decided where the literal is built. Q4 of that paper is answered by the ruling (explicit `dyn`, never implicit coercion — P15's evidence stands); Q5 (may an object hold a resource) stays NO in this scope.
