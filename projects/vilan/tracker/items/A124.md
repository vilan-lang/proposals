# A124 — PAPER — a READ-TRACKED derivation, `computed(|| body)`: one derived cell whose dependency set is re-recorded from the `get()`s its body makes on each run — the single primitive that subsumes `map`, `combine`, `flatten`, `switch`/`and_then` (channel.vl:41 becomes `computed(|| message.get()?.author.user().get())`). This is the state/tracking split the owner asks about, located: CELLS hold state; a computed holds a FUNCTION and a dependency set — not a lazy pipeline builder (the iterator analogy breaks on totality). Reverses `reactive-batching.md`'s 'vilan tracks explicitly' stance, which A110 door 2 already half-reversed by adopting Solid's compute→apply split

- status: OPEN — filed 2026-09-21 (the owner's question, mid-Order 39); paper Order 40, a RULING before any code
- kind: paper + ruling
- area: Reactive core & UI

**The owner's question, answered in two parts.** (1) Are we missing primitives? Yes, two, and they are the same missing thing: a DYNAMIC dependency spelled directly — A123 ships them as `switch`/`and_then`. (2) Should state and tracking be split? The intuition is right and the iterator analogy locates the split in the wrong place.

**Why the lazy pipeline (`.mapper()…to_signal()`) is not it.** Three reasons, recorded so the alternative is not re-proposed without them: (a) TOTALITY — the pseudo-code's `.some()` (`map_filter`) has no value to hand `to_signal()` when the source is currently `None`; the example works only because `count` starts `Some(0)`. Iterators have no 'current value', so filter is free there; a signal's `get()` must answer, so a filtered signal needs either a default (`to_signal_or`) or the `Option` back (`SignalCell<Option<U>>`) — at which point it IS `Source<Option<T>>` and `and_then` is the composition (A123). (b) `and_then`/`switch` are NOT pure folds — the inner source changes and the result must re-subscribe — so a lazy pipeline containing one still holds a rolling subscription; fusion saves nothing there. Pure `map∘map` chains are the only thing it fuses, and those cost one cell each, no DOM, no effect. (c) It doubles the vocabulary (every `Source` method needs a `Mapper` twin kept in parity), which is the 'keep adding special methods' problem the owner wants out of, squared.

**Where the split actually is.** In today's design a derivation is a `SignalCell` (state) PLUS a subscription whose dependency is STRUCTURAL — `map` depends on exactly its receiver, `combine` on exactly its tuple, and the only way to depend on something chosen at runtime is `flatten`'s rolling inner subscription. A read-tracked computed splits differently: the CELL is still the state; TRACKING moves out of the combinator's shape into the body's reads. `computed(|| message.get()?.author.user().get())` — one derived cell; on each run the body's `get()`s are recorded (an ambient 'currently computing' frame that `SignalCell::get` consults), the dependency set is diffed against the last run's, subscriptions added/dropped. `map` = a computed reading one source; `combine` = a computed reading a tuple; `flatten` = a computed reading `outer.get().get()`; `switch`/`and_then` = a computed with a `?`. One primitive, and every 'is there a combinator for…' question ends. This is Solid's `createMemo`, Preact's `computed`, Angular's `computed`, and the TC39 Signals proposal's `Computed` — every modern signals library converged here.

**What we said before, and what changed.** `reactive-batching.md` chose explicit tracking to AVOID Solid's discipline (compute→apply split, `untrack`, tracking-scope rules) and get glitch-freedom from dedup-on-enqueue. A110 door 2 (Order 39, landed) then adopted the compute→apply split anyway — derivations to fixpoint, effects after, `as_derivation()` marks — because nested forms needed it. The discipline auto-tracking requires is therefore BUILT; what remains is the ambient frame and the per-`get` branch. The stance should be re-ruled with that on the table, not inherited.

**Costs, honestly.** (i) One branch on every `SignalCell::get` (is a frame active?) — measure on the reactive benchmarks and kolt's `each` rows; Solid pays it everywhere and the JIT handles a monomorphic check well; the native backend pays a thread-local or a `Cell<Option<…>>` in vilan-rt. (ii) The classic footgun: a `get()` inside a callback the body REGISTERS (not runs) is not tracked — `sync ||` bodies and a `[must_use]`-style lint on `.get()` inside a nested closure in a computed body would catch most of it; async reads are correctly untracked. (iii) Conditional reads change the dependency set per run — a feature (the `?` above), and door 2's fixpoint handles the re-wiring inside one wave. (iv) Ordering by creation id (door 2's bucketed ascending run) stays valid: a computed is created after its sources. (v) A112 is untouched — delta derivatives recompute PARTS; a computed recomputes a WHOLE value; both live side by side.

**What to build if ruled yes.** S1 PROBE in std over existing primitives (no compiler change): `computed<T>(body: sync || T): SignalCell<T>` with a `Shared<List<Frame>>` stack, `SignalCell::get` pushing its id into the top frame when one is active, diff-and-resubscribe on run, `as_derivation()` marked, owner-tied like `map`; pins = the four combinators re-expressed and byte-equal in behaviour under the existing turn pins; measure the `get` branch. S2 if the probe holds: `map`/`combine`/`flatten` keep their names as thin bodies over `computed` (or stay as they are — they are correct and cheaper for the static case; measure first). S3 the guide: 'reach for `map` when the dependency is one source; `computed` when the body decides'.

**Rulings asked.** R1 — do we WANT read-tracking at all (reverses the recorded stance; the cost is the per-`get` branch and the untracked-callback footgun; the gain is one primitive)? R2 — if yes, does `computed` REPLACE the structural combinators' bodies or sit beside them? Rec: R1 yes, probe first; R2 beside, with `map`/`combine` unchanged until the benchmark says the branch is free.

**What is NOT a derivation, and stays an effect.** theme.vl:128/145, views.vl:707, channel.vl:370 each pair a source with `.effect(|x| other.set(…))` where `other` is ALSO written by the user (a selection index reset when the filter changes; a form field seeded from data). That is a state machine with two writers, not a transform — no combinator library expresses 'derived default, user-overridable' except as an effect writing a cell (Solid's `createWritableMemo` is the same thing with a name). Those sites are already spelled right; a `reset_on(source, |x| initial)` helper would be sugar, not a primitive. Recorded so 'every effect+signal pair is a missing combinator' is not the reading.
