# B596 — A struct literal evaluates its field initializers in DECLARATION order on the JS backend and in WRITTEN order natively — `Point { y = say("y", 2), x = say("x", 1) }` prints x, y on JS and y, x on native

- status: OPEN — filed 2026-10-09 (lang-a-49's find, Order 49)
- kind: miscompile (S)
- area: Code generation

B452's `walk_siblings_in_order` walks the fields as written and spills an earlier sibling only when a later one lowers to statements; the JS array is then laid out in declaration order, so two plain calls run in layout order. vilan-rust emits a Rust struct literal, which evaluates as written. The two backends disagree on a side-effecting initializer, and the native differential has no probe for it. Fix as B569 S2 did for a tuple literal matched by name (`Program::tuple_literal_layouts`): when the written order is not the layout, bind every unsettled initializer to a `const` in written order, then lay out. Repro: finds/struct_literal_evaluates_in_declaration_order.vl. Sizing S; transformer.

- 2026-10-10 (Order 49 sweep): Order 50 (solver): the JS transformer's struct-literal arm spills fields in written order as lang-a-49 did for by-name tuple literals.
