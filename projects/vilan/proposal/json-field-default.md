# `[default(..)]` on a `[derive(Json)]` field (M174)

- status: PAPER 2026-11-03 (lane papers-56, Order 56; owner questions open; not built)
- item: M174 — a struct that gains a `bool` or a number cannot read JSON stored
  before the field existed; M166 closed the `Option` half only
- lineage: `validating-from-json.md` (I3, the derive's fallible decoder; a shipped
  record that owns no field attribute, so this is a page of its own), M166 (the
  `Option` half, archive.md:2656), `store.md` A142 S7 (`[reactive(..)]`, the one
  field attribute a derive already reads — the template below)
- evidence: vilan `next` @ed9f0db9 (the integration worktree), kolt copy @0de9e2e

## 1. The problem

A derived decoder refuses an object that leaves out any field that is not
written `Option<T>`: the derive emits a presence check per non-`Option` field
(`vilan/std/src/json.vl:972-977`) and M166's exemption is syntactic, the
written name `Option` (`json.vl:928-930`, used at `:973` and `:982-987`). So a
struct that gains `code: bool` can no longer read its own stored values.

kolt's exhibit says so in its own comment (`src/lib/rich_text/style.vl:13-15`):

```vilan
// Its JSON is written by hand: text kept before `code` existed has no such
// field, and a derived reader fills in only a missing `Option` (M166), not a
// missing `bool`.
[derive(PartialEq)]
struct TextStyle { font_family: str, ..., bold: bool, italic: bool,
	underline: bool, strike: bool, code: bool, link: Option<str> }
```

The cost is two hand-written impls, not one: `[derive(Json)]` emits `Json` and
`FromJson` together (`json.vl:992-1002`), so a hand `FromJson` forces a hand
`to_json` too — `style.vl:35-39` (one 600-character interpolation) and
`style.vl:41-77` (37 lines; the five marks read through
`value.has_field(name) && ...unwrap_or(false)`, `:59-60`). A second kolt site has
the same cause: `TableFilter` (`src/task_query.vl:156-188`, "Lenient: what an
older (or newer) filter lacks is left out"), four fields each defaulted to empty.

## 2. What exists today

- **No field attribute is read by the Json derive.** There is no `[rename]` or
  `[skip]`: the built-in attribute table is `KNOWN_ATTRIBUTE_MARKERS`
  (`crates/vilan-core/src/parsing.rs:2582-2603`), and a field parses exactly
  `[internal(..)]`, `[reactive(..)]` and `[expose]`, refusing `[resource]`
  (`parse_struct_field`, `parsing.rs:10478-10512`). A field is the 5-tuple
  `StructField` (`node.rs:1786-1792`).
- **The template is `[reactive(..)]`** (A142 S7), a field attribute that only a
  derive reads, end to end: parser `parsing.rs:10523-10603`, its node type
  `Reactivity` (`node.rs:1800-1820`), the macro value
  `macro_std::meta::Field.reactive_coarse/_name` (`vilan/macro_std/src/meta.vl:67-80`)
  filled at `crates/vilan-core/src/macros.rs:3184-3194`, the formatter
  (`formatter.rs:5537-5560`, `print_reactivity` `:6455`), the grammar
  (`vilan/docs/spec/grammar.md:395-399`, `:576-579`), and its one reader
  (`vilan/std/src/reactive/store.vl:2313-2321`). The analyzer never looks at it.
- **A macro value already carries an expression as written**:
  `GenericParameter.default_` (`meta.vl:96`) is the source slice of `<B = Self>`
  (`macros.rs:3159-3165`).
- **An error inside derived code is re-anchored at the deriving attribute**, with
  "in code generated by this attribute:" in front (`analyzer.rs:55307-55320`).
- `[derive(Default)]` builds every field from its type's `Default`
  (`vilan/std/src/default.vl:40-70`); every scalar, `str`, `List`, `HashMap`,
  `HashSet` and `Option` has one (`number.vl:20..2112`, `default.vl:10-24`,
  `list.vl:207`, `option.vl:273`).

## 3. The design

**Surface.** `[default(EXPR)]` or bare `[default]` before a struct field, in the
same position as `[reactive(..)]` (either side of `[expose]`):

```vilan
[derive(PartialEq, Json)]
struct TextStyle {
	font_family: str, font_weight: str, font_size: f64,
	letter_spacing: f64, line_height: f64,
	[default(false)] bold: bool,
	[default(false)] italic: bool,
	[default(false)] underline: bool,
	[default(false)] strike: bool,
	[default(false)] code: bool,
	link: Option<str>,
}
```

Grammar: `default-attr = "[" "default" [ "(" expression ")" ] "]" ;`. Bare
`[default]` means the field type's `Default::default()`.

**Typed at the field.** The compiler (not the macro) turns each written
expression into a hidden associated function on the struct,
`fun __default_<field>(): <FieldType> { EXPR }` — the `__` prefix the expansions
reserve (`json.vl:1024-1027`) — built from the PARSED expression node, so a
mismatch (`[default("no")] code: bool`) is refused at the expression's own span
with the ordinary "expected `bool`" message, never re-anchored at the derive.
The function runs per decode (a `now()` default is the decode's time), in the
struct's module scope. A bare `[default]` on a type with no `Default` is refused
at the attribute: "`Theme` has no `Default`; write the value: `[default(..)]`".

**What the derive emits.** For a field with a default, no presence check, and
the literal's slot becomes

```vilan
code = if value.has_field("code") { bool::from_json_value(value.field("code"))! } else { TextStyle::__default_code() },
```

(`default_of<T>()` for a bare `[default]` whose type cannot head a path, as
`default.vl:52-58` does). A PRESENT field is decoded exactly as today: a
`"code": "yes"` or a `null` on a `bool` is still refused by name. On an `Option`
field `[default(..)]` replaces M166's `None` for the absent case only.

**What the rest does.** `to_json` writes every field, defaulted or not
(`json.vl:936-948`, unchanged): the default is the reader's, so a value
round-trips. `[derive(Default)]` reads the same attribute, so `TextStyle::default()`
and a decode of `{}`-plus-required-fields agree. `[derive(Wire)]` ignores it (§4).
`[derive(Storable)]` ignores it. A `[default]` on a struct that derives neither
`Json` nor `Default` is a warning ("nothing reads `[default]` here").

**The plumbing.** `StructField` gains a sixth slot `Option<FieldDefault>`
(`Bare | Value(Spanned<Node>)`); `macro_std::meta::Field` gains
`has_default: bool` and `default_: str` (the text as written, `""` when bare),
filled at the three `Field` constructions (`macros.rs:3184`, `:3266-3290`
parameters as constants, `:3351`).

**kolt after.** `style.vl:35-77` (43 lines) go; the struct above carries the
derive. `task_query.vl:156-188` becomes four bare `[default]` fields. One
behaviour change: both hand readers also forgive a PRESENT malformed value
(`style.vl:59-60`, `task_query.vl:175`), which the derive refuses. kolt's own
`to_json` wrote every stored value, so none is malformed; the patch is the
owner's.

## 4. The alternatives, and why not

- **`Option<bool>` in kolt** (M166's own note): works today, but every read site
  of `code` grows an `unwrap_or(false)`, and the type lies — "not set" is not a
  state the style has.
- **Re-anchored derive check** (let the derive splice the text and the checker
  type it in generated code): zero analyzer work, but the refusal lands on
  `[derive(Json)]` with the "generated" prefix (`analyzer.rs:55317`) — the worst
  place for a one-token mistake, and it leaves `[derive(Default)]` to splice the
  same text a second time.
- **A struct-wide `[json(lenient)]`** (absent or malformed → `Default`): the hand
  readers' behaviour, but it swallows a corrupt value silently and needs every
  field type to have `Default`.
- **Wire too**: a `Wire` frame is contract-hashed (both peers built together), so
  a missing field there is a protocol error, not old data.
